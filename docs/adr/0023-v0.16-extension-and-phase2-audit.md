# ADR-023: v0.16 Security Extension + Phase 2 Tool Security Audit (2026-09-02)

**Status**: Active

**Context**:

ADR-022 (v0.15) 建立了 `SystemSecurityHook` 数组作为系统工具的安全钩子。v0.16 在用户决策中废弃了它——`SystemSecurityHook` 与 `SecurityRouter` 并行存在会创建**双轨制**：两条不可见的审批路径绕过 `SecurityRouter` 的 session 隔离 + release 机制。

Phase 2 (web_fetch + encoding + request_user_input) 把三个新工具注册进了 `ToolRegistry`，其中 `web_fetch` 与现有 `SecurityDoor` 的所有工具集都**不重叠**——它需要自己的 SSRF 防线。`request_user_input` 也不命中任何现有门。

我们审计了 8 个交叉问题，结果：**6 ✅ / 2 ⚠️ / 0 ❌**。两个 ⚠️ 是设计选择，不阻断 Phase 2 落地，但需要在文档里明确登记。

---

## Decision

### 1. SystemSecurityHook → 注释保留 + SecurityDoor 接管

**问题**: `SystemSecurityHook` 与 `SecurityRouter` 并行会让审批流绕过 session 隔离。

**决策**:
- 保留 `SystemSecurityHook` 类型定义为**注释块**（`src/shell/registry.ts:118-132`）
- 保留 `systemSecurityHooks: SecurityHook[]` 字段为空数组（`src/shell/registry.ts:160`），向后兼容
- 注释 `registerSystemSecurityHook()` 实现（`src/shell/registry.ts:258-260`）
- 所有 SystemSecurityHook 的功能迁移到 `SecurityDoor`：sensitive-path / dangerous-command / write-approval / browser-tools

**理由**: 同一概念不能在两个抽象里各活一遍——会随时间漂移出不一致行为。注释保留是为了给未来的维护者留指针，避免他们**重新启用**这条废弃路径。

**约束**: 任何新工具安全需求都必须通过 `registry.registerDoor(...)` 实现，不得重新启用 `SystemSecurityHook`。

### 2. SecurityDoor 新增 4 项能力

**a. fullPermission 会话旁路门**:
- `SessionSecurityState.fullPermission?: boolean` 字段
- `SecurityRouter.check()` 在 fullPermission 会话上立即 return
- `ApprovalStore.keyForFullPermission()` 常量用于显式 grant
- Bash 工具通过 `ctx.approvalStore?.isGranted(ApprovalStore.keyForFullPermission())` 检测

**b. release() 钩子**:
- `SecurityDoor.release?(sessionId, toolName): void` 可选方法
- `SecurityRouter.releaseTool()` 在 `ToolRegistry.execute()` 的 `finally` 块调用
- 用于 browser-tools door 释放单会话并发槽

**c. 会话生命周期管理**:
- `SecurityRouter.getSession()` —— 查现有会话（不存在返回 undefined）
- `SecurityRouter.getOrCreateSession()` —— 查或懒创建
- `SecurityRouter.createSession(opts?: { fullPermission })` —— 显式创建（已存在抛错）
- `SecurityRouter.deleteSession()` —— 清理

**d. `ctx.approvalStore` 暴露给工具**:
- `ToolContext.approvalStore?: ApprovalStore` 字段
- `ToolRegistry.execute()` 在 `securityRouter.check()` 之后把 `sessionState.approvalStore` 注入 ctx
- 工具（如 bash）可通过 `ctx.approvalStore` 检查 full-permission grant

### 3. 新增 `createBrowserToolsDoor()`

**目的**: 把 open_url / read_media 这类"外部副作用工具"序列化——每 session 最多 1 个并发。

**实现**: `src/security/doors/browser-tools.ts`，`BROWSER_TOOLS = new Set(['open_url', 'read_media'])`，`release()` 释放槽。

**注册**: `src/extensions.ts:199` 与其他三门并列注册。

### 4. dangerous-command 强化递归检测

**新增覆盖**:
- **here-string** `bash <<< 'rm -rf /'` → 提取 payload 重入 classify
- **here-doc** `bash <<EOF ... EOF` → 正则提取内容块重入
- **subshell ALL match** — `$(...)` 替换原本只匹配第一个
- **echo/printf quoted payload** — `$(echo 'rm -rf /')` → 拆 quoted 部分重入

**理由**: 攻击者会把 rm -rf / 藏在 shell 引号里绕过 first-token 检查；agent 必须能识别嵌套的破坏性命令。

### 5. bash BASH_TIMEOUT_CAP + 全权旁路

**新增**:
- `BASH_TIMEOUT_CAP = 600` 秒
- bash 工具的 `timeout` 参数超过 600s 时：`ctx.approvalStore?.isGranted(ApprovalStore.keyForFullPermission())` 为真则允许，否则拒绝
- 测试覆盖：超时低于 cap 直通；超过 cap 且无 fullPermission 拒绝；超过 cap 但 fullPermission 允许

### 6. Phase 2 工具安全审计结论

| 工具 | 走 SecurityRouter? | 现有门命中? | SSRF/handler 防线 |
|---|---|---|---|
| `web_fetch` | ✅ | ❌ | **工具内部** `validateUrl`/`isSafeIp`/`BlockList` + DNS pin |
| `request_user_input` | ✅ | ❌ | **工具内部** `ctx.requestHandler` 注入校验，缺失时 throw |
| `encoding` (内部增强) | ✅ | ✅ sensitive-path + write-approval 仍生效 | 不适用 |

**`web_fetch` 不在 `BROWSER_TOOLS` 集里（设计选择）**: web_fetch 是服务端 HTTP（无浏览器副作用），与 open_url（客户端浏览器）不冲突。不引入串行化语义是正确的。

**`request_user_input` 不在现有门里（设计选择）**: 无副作用、handler 由 caller 注入，"忘记注入 handler"视为 caller 配置错误而非安全门——plan §4.3 明确。

### 7. ProtocolError retry (loop.ts)

**新增**: `MAX_PROTOCOL_ERROR_RETRIES = 3`，`PROTOCOL_ERROR_RETRY_BASE_MS = 1000`（指数退避）。SSE/网络瞬时失败时自动重试 3 次，避免对话因网络抖动断裂。

**理由**: SSE 长连接断开是 终端用户的高频痛点。3 次重试 + 指数退避是经验值——既不掩盖持续故障，也不浪费在不可恢复错误上。

## 两个 ⚠️ 缺口（已记录，不在本 ADR 解决）

### ⚠️ G1 — request_user_input handler 缺失时只在工具内部 throw

- **症状**: caller 忘记注入 `ctx.requestHandler` 时，工具 throw 干净英文 `request_user_input: no request handler configured`
- **严重性**: 低（不是安全 DoS——无资源耗尽/状态损坏，仅质量降级）
- **当前选择**: 让 throw 走 `wrapTool` → `loop.ts` catch → LLM 看到错误
- **建议改进**（不在 Phase 2 范围）: 在 caller 包装器（宿主应用/TUI）级 validate：当 `request_user_input` 出现在 `systemToolRefs` 但 `IMLoopOptions.requestHandler` 未设置时，启动前 fail-fast 给出更清晰的提示

### ⚠️ G2 — web_fetch 不在 BROWSER_TOOLS 集里

- **症状**: web_fetch 与 open_url 可并发运行
- **严重性**: 信息性（无真实竞态，session 隔离完好）
- **当前选择**: web_fetch 是服务端 HTTP，无浏览器副作用
- **建议改进**（不在 Phase 2 范围）: 如果未来想统一"所有外部输出工具"的并发语义，可把 `web_fetch` 加入 `BROWSER_TOOLS` 集（一个常量的改动）

## Rationale

ADR-022 把 SystemSecurityHook 立为系统工具的安全防线。v0.16 的核心洞察是：**单一权威**比**双轨并行**更可审计。SecurityRouter + SecurityDoor 体系覆盖 system/MCP/skill 三类工具，session 隔离 + release 机制完整，**没有给 SystemSecurityHook 留任何功能空间**。

Phase 2 三个工具的"不命中现有门"是**有意的**——web_fetch 的 SSRF 是网络语义、request_user_input 的 handler 缺失是 caller 配置错误，硬塞进 SecurityDoor 反而会扭曲两个概念。审计结果明确这一点后，把"为什么不注册 door"写进文档，未来维护者不必猜测。

fullPermission 是 Bash 工具的合理 escape hatch——批处理脚本/CI 场景需要无审批长 timeout，但仍然有 session 隔离，不能全开。
