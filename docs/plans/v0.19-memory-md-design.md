> Depends on: v0.18 已实现（渐进式工具披露，1636 tests 绿）
> Blocks: 无（独立功能）
> Status: 计划中
> ADR: ADR-024（D6 记忆系统，需修订）

## 1. 问题

当前 v0.19 存在两个设计错误：

1. **Memory 做成了 LLM 工具**（memory_write/read/search），让 LLM 自己决定何时读写记忆。这等于把系统工程的责任推给了 LLM。
2. **MEMORY.md 注入位置错误**——应该注入到用户消息之后，而非系统提示词之后。

### 1.1 正确的设计（参照 KimiCode + Claude Code）

| 项目 | 做法 | 说明 |
|---|---|---|
| **KimiCode** | AGENTS.md 通过 `${agents_md}` 变量注入到系统提示词模板字符串内部 | 项目级指令，结构稳定 |
| **Claude Code** | MEMORY.md 由 LLM 根据系统提示词指引自主维护，每轮自动注入上下文 | 用户级记忆，动态更新 |
| **我们（修正后）** | MEMORY.md 由 LLM 根据系统提示词指引自主维护，每轮注入到用户消息之后 | 结合两者优点 |

### 1.2 MEMORY.md 的内容

MEMORY.md 是**用户级记忆文档**，包含：

1. **项目索引**：链接到 ADR 文档、计划文档、架构文档的目录
2. **用户偏好**：编码风格、代码品味、工作习惯
3. **决策记录**：用户在项目中的重要决策
4. **日常习惯**：开发流程、测试习惯

### 1.3 注入位置与缓存前缀

```
messages[0] = system prompt                  ← 缓存前缀（稳定）
messages[1...N] = 对话历史                    ← 也是稳定前缀（历史不随轮次变化）
messages[N+1] = user message                 ← 当前轮用户输入
messages[N+2] = MEMORY.md 内容               ← 注入在这里（用户消息之后）
messages[N+3] = runtime/temporal context     ← 当前轮运行时信息
```

- 前缀 = `messages[0...N]`（系统提示词 + 对话历史），稳定 → 缓存命中
- MEMORY.md 和 runtime context 在前缀之后，内容变化不影响缓存前缀结构

**关键修正**：对话历史是稳定前缀的一部分，应该紧随系统提示词之后。当前轮的用户消息和 MEMORY.md 注入到历史之后。

**参照 KimiCode**：
- KimiCode 的系统提醒作为 **user role** 消息注入（用 `<system-reminder>` 标签包裹）
- 注入位置在对话历史之后、当前用户消息之前/之后
- 我们采用类似方式：MEMORY.md 作为 system role 消息注入到用户消息之后

## 7. 注入机制设计

### 7.1 ContextInjector 的 memory injection 改造

当前 `src/im/hooks/injections/memory.ts` 使用 AutoMemory 类。改为读取 MEMORY.md 文件：

```typescript
// src/im/hooks/injections/memory.ts（修正后）

import type { ContextInjectionSource } from '../context-injection.js'
import { readFile } from 'node:fs/promises'

export function createMemoryInjection(opts: { memoryFilePath: string }): ContextInjectionSource {
  return {
    name: 'memory_md',
    priority: 15,  // 在 runtime(10) 之后、temporal(20)之前
    inject: async () => {
      try {
        const content = await readFile(opts.memoryFilePath, 'utf-8')
        return content.trim().length > 0 ? content : null
      } catch {
        return null  // MEMORY.md 不存在时不注入
      }
    },
  }
}
```

### 7.1.1 ContextInjector 位置标记

当前 ContextInjector 把所有消息注入到 system prompt 之后。需要支持位置标记：

```typescript
// src/im/hooks/context-injection.ts 新增
export type InjectionPosition = 'afterSystem' | 'afterUser'

export type ContextInjectionResult = {
  content: string
  position: InjectionPosition
}

// inject 返回结果带位置信息
async inject(ctx: InjectionContext): Promise<ContextInjectionResult[]>
```

### 7.1.2 loop.ts compose 路径修正

**当前顺序**（错误）：
```
system prompt → context injections → user message → history
```

**正确顺序**：
```
system prompt → afterSystem injections → history → user message → afterUser injections
```

修改 `src/im/loop.ts` 的 parts 数组：

```typescript
const injectionResults = await opts.contextInjector.inject({ ... })
const afterSystemInjections = injectionResults.filter(r => r.position === 'afterSystem')
const afterUserInjections = injectionResults.filter(r => r.position === 'afterUser')

const parts: PromptPart[] = [
  { type: 'system', content: opts.systemPrompt + projection.systemSuffix },
  // afterSystem 注入（runtime, temporal）
  ...afterSystemInjections.map(r => ({ type: 'system' as const, content: r.content })),
  // 对话历史紧随系统提示词（稳定前缀）
  ...conversationTurns.map(turn => ({ type: 'turn' as const, message: turnToMessage(turn) })),
  // 当前轮用户消息
  { type: 'userTemplate', content: opts.userTemplate },
  // afterUser 注入（MEMORY.md）
  ...afterUserInjections.map(r => ({ type: 'system' as const, content: r.content })),
  // 其他 parts（stateLine, tools, summaries）
  ...(projection.stateLinePart ? [projection.stateLinePart] : []),
  ...opts.systemToolRefs.map(ref => ({ type: 'systemTool' as const, ref })),
  ...(serverSummary ? [{ type: 'mcpServerSummary' as const, content: serverSummary }] : []),
  ...(opts.dynamicSchemas ?? []).map(ds => ({ type: 'dynamicSchema' as const, ... })),
]
```

### 7.2 注入顺序（最终）

```
messages[0] = system prompt（静态提示词 + 记忆管理指引 + 测试暗号）
messages[1...N] = 对话历史（稳定前缀的一部分）
messages[N+1] = user message（当前轮用户输入）
messages[N+2] = MEMORY.md 内容（priority 15，注入到用户消息之后）
messages[N+3] = runtime context（Session/Agent/Round）
messages[N+4] = temporal context（日期/时区）
messages[N+5] = MCP server summary
messages[N+6] = dynamic schema
```

**关键**：对话历史 `messages[1...N]` 是稳定前缀的一部分，紧随系统提示词之后。当前轮的用户消息和 MEMORY.md 注入到历史之后。

## 8. 去掉 MAX_CONCURRENT=2

### 8.1 当前状况

| 机制 | 位置 | 控制什么 |
|---|---|---|
| `MAX_CONCURRENT_TOOL_CALLS = 2` | memory-layers.ts:97 | 全局硬编码——每批最多 2 个工具 |
| browser-tools door | security/doors/browser-tools.ts | per-tool——浏览器工具限制 1 并发/会话 |
| SecurityRouter.check | security/router.ts | per-session——每个工具调用前检查 |

### 8.2 修改方案

去掉 `MAX_CONCURRENT_TOOL_CALLS` 常量，`executeToolCalls` 改为无界并发：

```typescript
// 修改前
for (let i = 0; i < toolCalls.length; i += MAX_CONCURRENT_TOOL_CALLS) {
  const batch = toolCalls.slice(i, i + MAX_CONCURRENT_TOOL_CALLS)
  ...
}

// 修改后
const results = await Promise.all(
  toolCalls.map(async (tc): Promise<ToolTurn> => { ... })
)
```

SecurityDoor 已经处理了 per-tool 并发限制（如 browser-tools 限制 1 并发），不需要全局硬编码。
