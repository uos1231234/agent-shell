# v0.42 — MEMORY.md / ARCHITECTURE.md when-to-read 机制

> Depends on: v0.41 已实现（goal 模式）。既有注入链 `src/im/hooks/injections/`（memory.ts / architecture.ts）+ `loop.ts` composePrompt 的 afterUser 注入点 + `registerSystemAgentTools`（系统工具注册面）。
> Blocks: 无（独立功能）
> Status: 计划中

## 0. 一句话总结

把 MEMORY.md / ARCHITECTURE.md 从"**每轮全量注入**"改为"**有变化时给提示（when-to-read hint），模型决定读取后全量拉取喂给上下文**"，复用 mailbox 的 unread→read→markread 闭环语义，但在**既有 ContextInjector 注入点内**实现为可选字段，不破坏上下文组装架构。

## 1. 问题

当前 `createMemoryInjection()`（`src/im/hooks/injections/memory.ts`）与 `createArchitectureInjection()`（`architecture.ts`）**每轮都全量读取文件内容注入**到 afterUser 位置（`loop.ts:252`）：

- MEMORY.md / ARCHITECTURE.md 是工作区的长期资产，可能很长。
- 每轮全量注入 → **每个用户提问都要把整份文档塞进上下文** → 大文档下 token 浪费 + 对模型的干扰（系统提示词/每轮消息被迫全量阅读）。
- 多数轮次根本不需要记忆文档内容——模型只需知道"有这么个文档、什么时候该去读"。

**与现有先例的张力**：v0.19 曾拍板"Memory 不应该是 LLM 工具，让 LLM 决定何时读写 = 把系统工程责任推给 LLM"（`v0.19-memory-md-design.md:14`）。但 v0.19 之后演进出两条 **when-to-read 先例**，方向已经部分回摆：

1. **load_tools 渐进式披露**（`src/im/tools/load-tools.ts`）——不注入全量 schema，系统提示词只列清单 + 描述写明触发点（"任务需要当前工具集之外的能力时调用"），模型按需拉取完整定义。
2. **injectTextSkills 的 `whenToUse`**（`loop.ts:263-270`）——文本 skill 有 `whenToUse` 字段时以 `<!-- when_to_use: ... -->` 注释注入，模型据此判断何时读取/使用。

**本项目决策（2026-09-13 用户拍板）**：不是让 LLM 自己想起来读，而是**加一个 if-else 触发机制**——**保持对文档文件的监控，一旦变化就自动产生未读提醒**（类似 mailbox 的 "you have N unread" hint），模型看到提醒→决定读取→**读取时不是用 read 工具翻文件，而是全量拉取文件内容喂给上下文**→读完提醒消失（markread 语义）。

**关键边界（用户明确）**：
- **B 形态**：独立的 `memory_hint` / `architecture_hint` 可选字段 + 专用工具（`memory_read`），**不碰 mailbox 收件箱**（mailbox 是跨代理邮件，MEMORY.md 是宿主工作区文档，语义不同）。
- **在既有注入点上增强，不破坏架构**（用户明确：这里本身就有注入点，要在注入点上增加功能，而不是另起炉灶）。
- **不必钩子那么严谨**：不需要 fs 轮询守护进程，只要"文档有变化时就自动提醒"。

## §1 约束

### 1.1 状态机/上下文组装顺序绝不破坏

- `loop.ts` composePrompt 的 parts 顺序（`loop.ts:239-262`）是**不可干预的固定收尾**：system → afterSystem 注入 → history → user message → afterUser 注入 → stateLine → tools → summaries → schemas。本设计**只在 afterUser 注入点内向注入内容追加可选 hint 字段**，不改 parts 数组结构、不改顺序。
- 仍遵守 AGENTS.md 最高铁律：对 loop 主循环的任何修改必须用户明确同意。本计划**不加任何 loop guard / 阈值 / 状态机字段**，loop.ts 唯一改动点是"afterUser 注入内容的追加（可选字段）"，且此改动可被注入源内部完成（注入源返回的 content 自含 hint），**loop.ts 甚至可能零改动**——见 §4。

### 1.2 复用既有注入点，不另起炉灶

- 不在 ContextInjector 体系之外新建旁路。`memory_read` 工具注册走 `registerSystemAgentTools`（既有系统工具注册面，`register.ts:75-139`），经 wrapTool 统一报错路径。
- hint 字段挂在 `createMemoryInjection()` / `createArchitectureInjection()` 的注入输出上，由注入源自己携带 unread 状态。

### 1.3 不触碰 mailbox 收件箱

- mailbox（`src/im/mailbox/mailbox.ts`）是跨代理通信（send→read→markread，有 `from`/`to`/`subject`/`body`），MEMORY.md 是宿主工作区文档，没有"发件人"。**不把文档塞进 mailbox 收件箱**，不占 `MAX_INBOX_SIZE`/`MAX_BODY_LENGTH` 容量。
- 复用的是 mailbox 的**闭环语义**（unread→read→markread），不是它的数据结构。

### 1.4 可选字段 = 向后兼容

- hint 字段**可选**：无 `workDir` / 文档不存在 / 未变化 → 不产生 hint，行为与现状完全一致（注入源返回 null 或纯内容）。
- `memory_read` 工具新增是**加法**，不影响既有 toolRefs 清单；不改变既有工具行为。

### 1.5 system-agent 不维护文档

- `static-prompt.ts:228`（MINIMAL）已声明"子代理永远不维护 MEMORY.md/ARCHITECTURE.md"。本设计的 unread 状态由**宿主工作区注入源**维护，与子代理无涉。子代理走 v0.34 D13 共享同一 `contextInjector`（`register.ts:125`），其注入行为与工作代理一致，但 `memory_read` 工具子代理是否持有由 toolRefs 过滤决定（见 §7 决策待拍板项）。

## §3 架构

### 3.1 when-to-read 闭环（用户拍板形态）

```
                    ┌─────────────────────────────────────────────┐
                    │  宿主工作区（workDir）                        │
                    │  MEMORY.md  /  ARCHITECTURE.md               │
                    └───────────────┬─────────────────────────────┘
                                    │ 文件内容 + mtime（注入源读取）
                                    ▼
        ┌──────────────────────────────────────────────────────┐
        │  createMemoryInjection / createArchitectureInjection │  ← 既有注入点增强
        │  （ContextInjector source，会话生命周期单例）           │
        └─────────────────┬────────────────────────────────────┘
                          │ 每轮 inject()：
                          │  · 读文件、对比上次 mtime/哈希
                          │  · 变化 → 置 unread=true
                          │  · unread=true → content 尾部追加 hint
                          │  · unread=false → 只返回引导内容（或 null）
                          ▼
        messages[...] afterUser 注入位置（loop.ts:252，结构不变）
                          │  content 含：引导信息 + [可选] "⚠ 文档有未读变化"
                          ▼
        LLM 看到 hint → 决定读取 → 调用 memory_read 工具
                          │
                          ▼
        ┌──────────────────────────────────────────────────────┐
        │  memory_read 工具（新，registerSystemAgentTools 注册） │
        │  · 全量拉取 MEMORY.md 内容返回给模型（一次性喂全）      │
        │  · 置 unread=false（markread 语义）→ 下次 hint 消失    │
        └──────────────────────────────────────────────────────┘
```

### 3.2 unread 状态归属

unread 状态由**注入源实例**持有（`createMemoryInjection()` 在装配时构造一次，`assembly.ts:701`，会话生命周期内同一实例）。注入源内部维护 `lastSeen`（上次读取的文件 mtime + 长度/哈希），每次 `inject()` 时对比。

可选：跨会话恢复时该状态是否需要落盘（见 §7 待拍板）。默认不落盘（unread 是"本轮流程内的提示"，重启后回到无提示基线，与 §6.15 的 thinking live-only 精神一致）。

## §4 设计原则

### P1：复用注入源 = 封装未读，不改 loop

把 unread 状态、mtime 对比、hint 追加**全部封装在注入源内部**（`memory.ts` / `architecture.ts`）。注入源本来就可以在 `inject()` 里做任意逻辑并返回不同 content——**loop.ts 无需改动**，composePrompt 的 afterUser 注入点天然消费注入源返回的 content。

例外：若希望 hint 与"引导段"分离得更干净（引导段始终在、hint 只在变化时）——但注入源只返回一段 content，合并即可，仍是注入源内部事。**loop.ts 零改动是本设计的硬目标**（避开状态机铁律的触碰面）。

### P2：mtime 对比驱动变化检测，不做 fs 轮询

用户明确"不必钩子那么严谨"。变化检测 = **注入源每次 `inject()` 时 `stat()` 文件的 mtime/大小**，与上次记录对比，不同则 unread=true。天然随每轮注入触发，无需额外定时器/守护进程。代价：变化发生在两轮之间时，到下一轮才被感知——可接受，因为 hint 本来就是在"下一轮组装"时展示。

### P3：读取 = 全量拉取喂上下文，不给文件路径让模型自己翻

用户明确"不是让他自己读取，而是决定读取之后全量拉取文件给他"。`memory_read` 不做"返回路径让模型 read"，而是**直接读取 MEMORY.md 全文返回**（≤ 合理上限，超限截断 + 头部戳，与 databus 截断口径一致）。模型一步拿到完整内容，无需二次工具调用。

### P4：markread 语义 = 指令明确，不靠猜测

读完要显式清未读。`memory_read` 调用即视为"已读"（置 unread=false）——与 mailbox `markRead`（`mailbox.ts:215-242`）的"读过置 read"一致。不清零的唯一路径是"文档又变了"（下一轮 mtime 再变化会重新置位）。

### P5：hint 是引导，不是行为规范

hint 措辞遵循 §6.28 提示词工程原则：**只种"什么时候去看"的画面**（触发点/价值瞬间），不写 DO NOT / Never 这类规范式红线。例如："**当你要基于项目的跨会话记忆/架构决策做判断、或发现记忆可能已过时时**，调用 memory_read 拉取最新记忆全文。" 不加"必须/禁止"。

### P6：与 ARCHITECTURE.md 对称

`createMemoryInjection` 与 `createArchitectureInjection` 代码同构（都读 workDir 下同名文件、afterUser、单例注册）。**两者一并改造**，共用同一套变化检测 + hint + read 工具模式，避免两种文档两种待遇。

### 5.2 修改：`src/im/hooks/injections/memory.ts`（createMemoryInjection）

```typescript
// 新增内部状态
type MemoryDocState = {
  lastMtimeMs: number
  lastSize: number
  unread: boolean
}

export function createMemoryInjection(): ContextInjectionSource {
  const state: MemoryDocState = { lastMtimeMs: 0, lastSize: 0, unread: false }
  return {
    name: 'memory_md',
    priority: 15,
    position: 'afterUser',
    inject: async (ctx) => {
      if (!ctx.workDir) return null
      const filePath = join(ctx.workDir, 'MEMORY.md')
      const st = await stat(filePath).catch(() => null)  // 变化检测
      if (!st) return null
      if (st.mtimeMs !== state.lastMtimeMs || st.size !== state.lastSize) {
        state.lastMtimeMs = st.mtimeMs; state.lastSize = st.size
        state.unread = true  // 文档变了 → 未读
      }
      const content = await readFile(filePath, 'utf-8')
      // 关键改动：hint 只在 unread 时追加；不变时……见 §4 P1 的变体
      return buildContent(content, state)  // 引导 + 可选 hint
    },
    // 暴露 markRead 给 memory_read 工具（接线见 §7）
  }
}
```

**变体（P1 的两个落法，需拍板，见 §7）**：
- 变体 A（默认不注入/每轮纯引导）：`inject()` 返回"引导段 +（unread 时）hint"，模型看到 hint 就调 memory_read。doc 内容**不再每轮注入**（省 token，符合用户初衷）。
- 变体 B（每轮仍注入引导，但内容只按需读）：与变体 A 同，只是引导段的措辞承载"文档有 X，变化时看我 hint"。

## §7 决策信息

### 已决定（用户拍板 2026-09-13，✅ 全部落地）

| 决策 | 内容 |
|---|---|
| 形态 | 独立 hint + 按需拉取，不碰 mailbox 收件箱 |
| 覆盖范围 | MEMORY.md 与 ARCHITECTURE.md 一并改造（对称） |
| 架构落点 | 在既有 ContextInjector 注入点上增强——**合并为一个 `when-to-read` 注入源**（三选一需同时知道两文档未读状态，用户确认合并；原 memory.ts / architecture.ts 删除） |
| 触发 | **内容哈希** ≠ 已读基线 → 未读（能感知增删）；LLM 读取后把当前哈希写入基线（markread + 重新计数） |
| 选项 | **三选一同时给**：A = 读取 MEMORY.md 全文 · C = 读取 ARCHITECTURE.md 全文 · B = 暂不读取 |
| 读取语义 | 模型下一轮回复以选项字母开头 → 注入源自 `ctx.conversationHistory` 自解析（**不依赖 loop 传值，零新工具，不动状态机**）→ 全量拉取喂进上下文 |
| 解析宽严 | 宽松：NFKC 归一全角 + 空白/标点/加粗/中文引导词（选/选择/答/答案）前缀；行首独立 token，"API"/"Apple" 不误判 |
| 注入形态 | 变体 B：引导段每轮常驻（极短），全文只在选 A/C 那轮注入 |
| 状态归属 | per-agentId 分桶（子代理与工作代理各自未读视图，防子代理随机 "A..." 误消费父代理 pending）；不落盘（重启回基线） |
| 防重复消费 | lastHonoredText 守卫——工具轮链中最后带文本 assistant 不变时不重复消费同一回复 |
