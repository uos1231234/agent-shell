## 0. Goal

Let the working agent (and end users) **define and run their own sub-agents** — lightweight, guard-controlled, single-shot agents that share the working agent's tool registry but run in isolated loops with a controlled Databus visibility boundary.

Two definition modes:
1. **Config-driven**: JSON files at `~/.databus/agents/<name>.json`, loaded at startup.
2. **Tool-driven**: `define_subagent` tool call at runtime, optionally persisted to disk.

Sub-agents are invoked via `run_subagent`. They run under their own guard loop, share a Databus for cross-sub-agent visibility, and **must not** pollute the working agent's canonical conversation or private Databus.

**Success criterion**: A working agent can define a reviewer sub-agent with `echo` + `databus_query`, run it with an input, and receive a string output — while the sub-agent's tool turns project into a shared bus that other sub-agents (and the working agent, read-only) can query, but never into the working agent's own Databus.

## 1. Constraints

This section is N hard constraints from ADR-016/017, landed commits, and user decisions.

1. **Guard-controlled.** Sub-agents run through `runIMLoop` with the full guard suite (token, step, tool-call, elapsed, error-rate). No bypass path. `[已验证: loop.ts guards are not optional]`
2. **Shared Databus is read-only for the working agent.** The working agent reads sub-agent tool events via `databus_query` / `databus_subscribe` against the shared bus. The working agent never writes to the shared bus. `[计划设计]`
3. **Compressor does not act on sub-agents.** Sub-agent loops use `noopSystemAgent` for compressor/warehouse/recall — they have no system agents of their own. No nesting. `[已验证: system-agent.ts line 128-132]`
4. **No nesting.** A sub-agent's `systemAgents` are all `noopSystemAgent`. Calling `compress_block` / `ask_recall` from a sub-agent throws at runtime. `[已验证: system-agent.ts line 172-175]`
5. **Tools from the existing registry only.** `toolRefs` are validated against `registry.listSystemTools() + listSkills() + listMCPServers()` at config load time. No new tool definitions. `[已验证: config.ts line 47-57]`
6. **Two config modes.** Disk (`~/.databus/agents/<name>.json`) and runtime (`define_subagent`). Both produce the same `SubAgentConfig` shape. `[已验证: registry.ts + define-subagent.ts]`
7. **ToolRegistry registration at startup.** `define_subagent` and `run_subagent` are registered once via `registerSystemAgentTools`. The tools themselves are closures over `SubAgentRegistry` + deps. `[已验证: register.ts line 57-69]`
8. **StateLine does not store sub-agent configs.** Sub-agent configs live in `SubAgentRegistry` (in-memory + disk). StateLine remains the working agent's state projection only. `[计划设计]`
9. **No new guard / metric / config fields (ADR-015).** Sub-agents reuse the existing `ShellConfig` (with optional overrides via `config?: Partial<ShellConfig>`). No `SubAgentGuard` or `subAgentMetric`. `[已验证: config.ts line 19, system-agent.ts reuses createConfig]`
10. **Do not touch `compose.ts`.** Sub-agent prompts are built through the same `compose()` path as the working agent. `[已验证: loop.ts shared]`
11. **New tools via `wrapTool` + `requireReason`.** Both `define_subagent` and `run_subagent` go through the same wrap path as v0.9/v0.10 tools (runtime `reason` validation). `[已验证: define-subagent.ts line 40, run-subagent.ts line 48]`
12. **Synchronous sub-agent call.** `run_subagent` awaits `agent.run()` and returns the output string. No async dispatch, no mailbox-based result delivery. `[已验证: run-subagent.ts line 72-79]`
13. **Declarative config.** `SubAgentConfig` is `{ name, systemPrompt, toolRefs, config? }` — no imperative logic, no function fields. Behavior emerges from prompt + tools + LLM. `[已验证: config.ts line 13-20]`
14. **Follow `ask_recall` pattern.** `run_subagent` closes over deps, creates a `SystemAgent` at call time, runs it, returns `result.output`. Same factory, same lifecycle. `[已验证: run-subagent.ts structure matches ask-recall.ts]`

## 3. Architecture

### 3.1 Information flow

```
┌─────────────────────────────────────────────────────────────┐
│                    Working Agent Loop                         │
│  databus = mainDatabus (private — working agent writes here) │
│  ctxDatabus = [mainDatabus, subAgentRegistry.sharedDatabus]  │
│  → ctx.databus = MultiDatabus([main, shared]) (read-only)    │
│      ↓                           ↓                           │
│  [main bus:                 [shared bus:                     │
│   working agent's           sub-agent tool turns,            │
│   own tool turns]           read-only for working agent]     │
│                                                              │
│  Tool: run_subagent ──→ creates SystemAgent                  │
│         │                    │                               │
│         │   agentConfig:     │                               │
│         │     databus = subAgentRegistry.sharedDatabus       │
│         │     (private projection bus for this sub-agent)    │
│         │     sharedDatabus = [sharedDatabus, workingDatabus]│
│         │     → ctxDatabus = MultiDatabus([shared, working]) │
│         │                    │                               │
│         │              runIMLoop(sub-agent loopOpts)         │
│         │                    │                               │
│         │              sub-agent tool turns project          │
│         │              into sharedDatabus (shared bus)       │
│         │                    │                               │
│         ←──────────── result.output (string)                 │
└─────────────────────────────────────────────────────────────┘
```

**v0.11.1 update**: `ctxDatabus` now accepts `Databus | readonly Databus[]`. When an array is passed, the loop wraps it in `MultiDatabus` (see §9.1). Both the working agent and sub-agents can read from multiple buses simultaneously through a single `ctx.databus` — no dual-bus logic in tools (D8/D11 preserved).

### 3.2 Two-Databus boundary (CRITICAL design)

The plan specifies a **two-Databus separation** per agent loop:

| Databus | Role | Who writes | Who reads |
|---------|------|-----------|-----------|
| `loopOpts.databus` (private) | This agent's tool-turn projection | This agent's loop (via `appendCanonicalTurn`) | This agent's tools via `ctx.databus` (merged) |
| `loopOpts.ctxDatabus` (shared/ctx) | Other agents' tool turns, read-only context | Other agents' loops | This agent's tools via `ctx.databus` (merged) |

**The key mechanism**: `ctx.databus = opts.ctxDatabus ?? opts.databus`.

- When `ctxDatabus` is set, `ctx.databus` points to the shared/contextual bus (so the agent's tools can read other agents' events).
- `loopOpts.databus` remains the private bus where this agent's own tool turns are projected.
- When `ctxDatabus` is not set (working agent, built-in system agents), `ctx.databus` falls back to `opts.databus` — the agent reads its own bus, unchanged behavior.

**v0.11.1 amendment (§9)**: `ctxDatabus` now accepts `Databus | readonly Databus[]`. When an array is passed, the loop constructs a `MultiDatabus` merged view, so `ctx.databus` can carry both the private bus and the shared bus simultaneously. This closes the architecture gap where a single `ctxDatabus` forced an either/or choice between reading one's own bus and reading the shared bus. The working agent now reads `[mainDatabus, sharedDatabus]`; sub-agents read `[sharedDatabus, workingDatabus]`. Tools still read only `ctx.databus` — they are unaware of the merge (D11 preserved).

**Why this matters**: If we directly pass the working agent's Databus as `loopOpts.databus` to a sub-agent, the sub-agent's tool turns would be appended to the working agent's bus — polluting it. The `ctxDatabus` separation keeps projection private and context shared.

### 3.3 Roles

| Role | Responsibility | Databus access |
|------|---------------|----------------|
| Working agent | Main loop, drives sub-agents | private bus (own) + ctxDatabus (shared, read-only) |
| Sub-agent | Single-shot task execution | sharedDatabus (private projection) + working agent's bus (ctxDatabus, read-only) |
| SubAgentRegistry | Config store + sharedDatabus owner | Owns `sharedDatabus` instance |

### 3.4 Sub-agent lifecycle

```
define_subagent("reviewer", {prompt, toolRefs})
    → validateSubAgentConfig(cfg, registry)
    → SubAgentRegistry.register(cfg, diskDir?)
    → (async) writeToDisk if diskDir

run_subagent("reviewer", "check this code")
    → SubAgentRegistry.get("reviewer")
    → createSystemAgent({
        databus: subAgentRegistry.sharedDatabus,   // private projection
        sharedDatabus: workingAgentBus,             // read-only ctx
      })
    → agent.run({ messages: [{role:'user', content: input}] })
    → return result.output ?? '(sub-agent produced no output)'
```

## 4. Design Principles

1. **Config is declarative, not imperative.** A sub-agent config is data, not code. No function fields, no callbacks. The sub-agent's behavior emerges from `systemPrompt + toolRefs + LLM`, exactly like built-in system agents. This makes configs serializable to JSON and loadable from disk without `eval`.

2. **Two-Databus separation, not bus merging.** The plan uses `ctxDatabus` on `IMLoopOptions` (not `sharedDatabus` on `ToolContext`) to separate "where my tool turns go" (private `databus`) from "what I can read" (`ctxDatabus`). This is a single-field addition to `IMLoopOptions` with a fallback `??`, not a new ToolContext field. **Rationale**: D8 explicitly says "ctxDatabus on IMLoopOptions (don't touch ToolContext type)" — ToolContext is at the bottom of the dependency graph and should not accumulate role-specific fields.

3. **SubAgentRegistry owns the sharedDatabus, not the loop.** The shared bus is a registry-level singleton: all sub-agents created from the same registry share one bus. This is a deliberate choice for cross-sub-agent visibility (sub-agent B can query sub-agent A's tool events). The working agent reads this bus via `ctxDatabus`.

4. **Sub-agents are single-shot, like system agents.** Each `run_subagent` call creates a fresh `SystemAgent` via `createSystemAgent`, runs it once, and discards it. No state accumulates across calls. The sub-agent's conversation memory is fresh per run. Only the shared Databus persists across sub-agent runs.

5. **No nesting, enforced by noopSystemAgent.** Sub-agents get `noopSystemAgent` for all three system agent slots. Any attempt to call `compress_block` / `ask_recall` / `record_curated_block` from a sub-agent throws a clear error. This is a hard boundary, not a soft limit.

6. **Disk is fire-and-forget for runtime definitions.** `define_subagent` with `diskDir` writes asynchronously (`void writeToDisk`). The config is immediately available in memory; disk is best-effort persistence. Disk load at startup (`loadFromDisk`) is synchronous and blocking.

### Already decided (with rationale)

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | Sub-agent = `createSystemAgent` + `runIMLoop` | Reuse the existing factory. No new agent type. Same guard suite. |

## 8. Implementation Audit (post-commit `5d6ca8e`)

This section records the violations found when comparing the committed implementation against the plan above. Each violation has a severity and a fix.

### V1 [CRITICAL] — `ctxDatabus` missing from `IMLoopOptions`; `sharedDatabus` added instead

**Plan (D8, §3.2, §5)**: `IMLoopOptions.ctxDatabus?: Databus` with `ctx.databus = opts.ctxDatabus ?? opts.databus`.

**Implementation** (`loop.ts:97-99, 323-324`): Added `sharedDatabus?: Databus` to `IMLoopOptions` and `ctx.sharedDatabus = opts.sharedDatabus` to the ctx construction. `ctx.databus` is still `opts.databus` — no fallback mechanism.

**Impact**: The two-Databus boundary does not exist. Tools read two separate buses via two separate ToolContext fields, not one contextual bus via a loop-level fallback.

**Fix**: Replace `sharedDatabus` with `ctxDatabus` on `IMLoopOptions`. Change ctx construction to `databus: opts.ctxDatabus ?? opts.databus`.

### V2 [CRITICAL] — `ToolContext.sharedDatabus` added (violates D8)

**Plan (D8)**: "ctxDatabus on IMLoopOptions (don't touch ToolContext type)".

**Implementation** (`tool-context.ts:15`): Added `sharedDatabus?: unknown` to `ToolContext`.

**Impact**: ToolContext accumulates a role-specific field. `databus_query` and `databus_subscribe` now have dual-bus merge logic that should not exist.

**Fix**: Remove `sharedDatabus` from `ToolContext`. Remove dual-bus logic from `databus_query` and `databus_subscribe`. They read only `ctx.databus` (which is the ctxDatabus-or-private bus after V1 fix).

### V3 [CRITICAL] — `system-agent.ts` uses `databus?` to replace private bus; no `sharedDatabus` → ctxDatabus wiring

**Plan (§5, D9, D10)**: `createSystemAgent` should accept `sharedDatabus?: Databus` → wire to `loopOpts.ctxDatabus`. The private `databus` (where this agent projects tool turns) should remain private (per-run fresh, or injected `subAgentRegistry.sharedDatabus` for sub-agents).

**Implementation** (`system-agent.ts:65, 73, 111`): Added `databus?: Databus` opt. When provided, it **replaces** the private bus entirely (`opts.databus ?? new DatabusClass()`). No `sharedDatabus` opt exists. No `ctxDatabus` wiring exists.

**Impact**: When `run_subagent` passes `subAgentRegistry.sharedDatabus` as `databus`, the sub-agent's tool turns project into the shared bus (correct for cross-sub-agent visibility), BUT the sub-agent has no ctxDatabus — it cannot read the working agent's tool history. The two-Databus separation is collapsed into one bus.

**Fix**: 
- Rename `databus?` opt to keep it (it's the private/injected bus for sub-agents).
- Add `sharedDatabus?: Databus` opt → wire to `loopOpts.ctxDatabus`.
- `loopOpts.databus` = the injected `databus` (or fresh private bus).
- `loopOpts.ctxDatabus` = `opts.sharedDatabus`.

### V4 [MAJOR] — `run_subagent` passes `sharedDatabus` as the sub-agent's only bus; no working agent bus as ctxDatabus

**Plan (D10, §5)**: `run_subagent` should pass:
- `databus: subAgentRegistry.sharedDatabus` (private projection bus)
- `sharedDatabus: workingDatabus` (read-only ctx: sub-agent sees working agent history)

**Implementation** (`run-subagent.ts:65`): Passes only `databus: subAgentRegistry.sharedDatabus`. No working agent bus is passed. `RunSubagentDeps` does not include `workingDatabus`.

**Impact**: Sub-agents cannot read the working agent's tool history. The plan's D10 (sub-agent ctx = working agent's bus) is not implemented.

**Fix**: Add `workingDatabus: Databus` to `RunSubagentDeps`. Pass `sharedDatabus: deps.workingDatabus` to `createSystemAgent`.

### V5 [MAJOR] — `databus_query` / `databus_subscribe` have dual-bus merge logic

**Plan (D11)**: Tools read only `ctx.databus`. The ctxDatabus mechanism provides the contextual view.

**Implementation** (`databus-query.ts:34-53`, `databus-subscribe.ts:44-97`): Both tools read `ctx.databus` AND `ctx.sharedDatabus`, merge results.

**Impact**: This logic only works because of V1/V2 (the `sharedDatabus` ToolContext field). After fixing V1/V2, this dual-bus logic is dead code that references a removed field.

**Fix**: Remove dual-bus logic. Restore to single-bus read from `ctx.databus`.

### V6 [MINOR] — `createMinimalIM` uses `sharedDatabus` opt instead of `ctxDatabus`

**Plan (§5)**: `createMinimalIM` should accept `ctxDatabus?` and wire to `IMLoopOptions.ctxDatabus`.

**Implementation** (`minimal.ts:46, 67-69`): Uses `sharedDatabus?` opt.

**Fix**: Rename to `ctxDatabus?`. Wire to `IMLoopOptions.ctxDatabus`.

## 9. v0.11.1 Amendment — P0 MultiDatabus closure + P2 security hardening

**Applied on**: working tree after commit `6af1805`. Supersedes the single-`ctxDatabus` limitation discovered when V1-V7 were tested end-to-end.

### 9.1 P0 — MultiDatabus architecture closure

**Problem**: After V1-V7 fixes, `ctxDatabus` accepted only a single `Databus`. This forced an either/or choice:
- Working agent: read own bus OR read shared sub-agent bus — not both.
- Sub-agent: read shared bus OR read working agent bus — not both.

The plan's D10 (sub-agent reads working agent history) and D12 (working agent reads sub-agent events) could not both be satisfied simultaneously.

**Solution**: `ctxDatabus` now accepts `Databus | readonly Databus[]`. When an array is passed, the loop constructs a `MultiDatabus` — a read-only merged view that deduplicates by turn id, sorts by `at` timestamp, and re-applies `limit`. All underlying buses are already projection copies (tool-only), so merging is safe.

| Agent | `databus` (private write) | `ctxDatabus` (merged read) |
|-------|---------------------------|----------------------------|
| Working agent | `mainDatabus` | `[mainDatabus, subAgentRegistry.sharedDatabus]` |
| Sub-agent | `subAgentRegistry.sharedDatabus` | `[sharedDatabus, workingDatabus]` |
| System agents | fresh private bus | `undefined` (fallback to private) |

**New file**: `src/im/multi-databus.ts` — `MultiDatabus` class implementing `turns()`, `query()`, `subscribe()`, `evictByIds()` as merged views over multiple `Databus` instances.

**Modified files**:
- `loop.ts`: `ctxDatabus?: Databus | readonly Databus[]`; ctx construction wraps arrays in `MultiDatabus`.
- `system-agent.ts`: `sharedDatabus?: Databus | readonly Databus[]` (passes through to `loopOpts.ctxDatabus`).
- `run-subagent.ts`: `sharedDatabus: [subAgentRegistry.sharedDatabus, deps.workingDatabus]`.
- `minimal.ts`: auto-wires `ctxDatabus = [mainDatabus, subAgentRegistry.sharedDatabus]` when `subAgentRegistry` is present.

**New tests**: `tests/im/multi-databus.test.ts` (merge/dedup/sort/limit/subscribe/evict), `tests/im/minimal.test.ts` (auto-wiring).

**Harness**: `examples/sub-agent-harness.ts` — end-to-end demo with scripted streamChat stubs.

### 9.2 P2 — Security hardening (P2.1–P2.8)

All P2 fixes follow the "red test first" principle (修复方案2.md §0.1): a failing test was written, then the code was changed to make it pass.
