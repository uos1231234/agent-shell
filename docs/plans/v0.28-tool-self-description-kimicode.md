## 3. 架构信息（Architecture）

### 3.1 信息流（改动后）

```
               registry（description = 唯一事实源）
                        │
        ┌───────────────┼───────────────────────────────┐
        ▼               ▼                               ▼
 toOpenAIToolSchemas  buildStaticPrompt        buildToolsPayload(registry, refs)
   function.description 工具清单行               {name, description}[]（白名单）
        │               │                               │
  真实 LLM 请求体    系统提示词（session.event      gate.emit session.event
  （模型看到纪律）    'system.prompt' 已到前端）       'tools'（新增，同点）
                                                       │
                                                       ▼
                                          webshell WS 转发 → webapp session-store
                                                       │ session.event 'tools' 分支
                                                       ▼
                                          工具清单展示（MessageList 内 ToolsRow）
```

### 3.2 角色与边界

| 角色 | 位置 | 职责 | 知道什么 |
|---|---|---|---|
| 纪律作者 | `src/im/tools/index.ts` read/edit 定义 | description 文本升级（KimiCode 形态） | 纪律 + 视图约定 |
| schema 出口 | `registry.toOpenAIToolSchemas`（registry.ts:602） | description 原样进请求体 | 无感知（文本变长） |
| 提示词出口 | `section-builder.buildToolingSection`（:62-76） | `- name：description` 行 | 无感知 |
| 协议 payload 构建 | `buildToolsPayload`（webshell/tools-payload.ts 新） | 白名单 → {name, description}[] | 只读 registry |
| 出站点 | `web-host.ts` attachSession（:410 旁） | emit `session.event 'tools'` | 与 system.prompt 同点 |
| 前端消费 | webapp session-store（:322 分支）+ MessageList（ToolsRow） | 存清单 + 展示 | 契约类型 |
| 正确性命门（不动） | `edit.ts` 内容寻址 | oldText 精确匹配当前磁盘 | 磁盘当前内容 |

**展示面边界（形态分层，约束 8）**：上表"前端消费"行仅指 **webapp（开发形态）**——系统提示词（SystemPromptRow）与工具自描述（ToolsRow）是开发工具面，全量展示。**CLI（v0.26 上线形态）是独立宿主实例**：进程内直连 SignalGate、自建装配，不订阅 webshell，`tools` 事件与 `system.prompt` 事件都不进 CLI 订阅集；CLI 界面只呈现对话结果与交互（/命令 / 审批 / picker），不展示系统提示词与工具自描述。

### 3.3 纪律文本要点（写入 description 的内容，源自 KimiCode edit.md / read 视图耦合）

**read.description**（KimiCode Read 输出视图约定）：
- 输出为行号前缀视图 `N<TAB>行内容`（1-based，已是现状 `read.ts` 行为）。
- 声明：该行号视图是 edit 工具 oldText 的事实来源；edit 要求 oldText 来自此视图**去掉行号前缀**后的内容，且与磁盘当前内容精确匹配。

**edit.description**（KimiCode edit.md 精神）：
- 修改目标文件**前必须先调用 read** 读取该文件；
- **不要凭记忆 / 陈旧上下文 / 猜测**构造 oldText（KimiCode 原话精神："DO NOT call Edit from memory, stale context, or a guessed old_string"）；
- **连续修改同一文件时，每次修改前重新 read**（文件内容可能已变）；
- oldText 必须与磁盘当前内容**精确匹配且唯一**——0 次或多次匹配都会被拒绝且文件保持不变（已是 `edit.ts:86-92` 行为，写进描述让模型提前知道）；
- oldText 取自 read 输出视图、**不含行号前缀与行首空白之外的内容**；
- 若意图是创建新文件或整体重写，用 write 而非 edit。

**oldText 参数 description**（edits.items 内）：加"来自 read 输出视图的内容行（去掉行号前缀），须与磁盘当前内容精确匹配"。

> 文本实际措辞落实现时按 agent-shell 现有 description 风格（简洁英文）撰写，纪律句完整保留；两段 description 在 index.ts 顶部提为具名常量（`READ_DESCRIPTION` / `EDIT_DESCRIPTION`，文件内引用，供单测断言）。

## 4. 设计原则（Principles）

1. **纪律的载体是模型必读的 schema，不是旁路提示词**：KimiCode 把纪律写进工具描述 md（经 `?raw` 进 description 字段 → schema → 请求体），模型在每次工具可用清单里看到。agent-shell 的 description 已同时进入 schema 与系统提示词工具清单——升级文本即让纪律在**两条模型可见路径**上同时生效，且零运行时成本。这是"工具自描述"的正解：自描述 = 工具告诉模型自己怎么被正确使用，而不是 harness 替模型记账。
2. **共享文本视图约定（read 行号视图 ↔ edit oldText）是 KimiCode 独有的、我们缺的一环**：KimiCode Read 输出行号 + Edit 描述要求"from the Read output view, without the line-number prefix"（调研 `edit.ts:36-43`），把"模型拿错内容"的概率压到最低。agent-shell `read.ts` 已输出行号视图、`edit.ts` 已精确匹配，缺的只是**把这条约定写进双方描述**——本计划补上，使 read/edit 在模型侧形成闭环。
3. **description 三处同源，零副本**（约束 3）：任何一处可见 ≠ 三处各写一遍。协议 payload 从 registry 读、提示词从 registry 读、schema 从 registry 读——升级只改 `index.ts` 一处。
4. **协议 payload 最小化：name + description，不带 parameters**：前端要展示的是"模型有哪些工具、纪律是什么"（能力面 + 行为面），不是参数 schema。完整 schema 出站会让每条会话信号体积膨胀一个量级（write 的 content 描述、edit 的 edits 结构等），且前端无消费方。未来若前端要做 schema 级工具调用构造器，再加 `session.toolsSchema` 类命令，纯增量。
5. **复用 `session.event`，不新增 GateSignal kind**：`session.event` 是设计上就留的自由事件通道（`event: string`），`system.prompt` 已是先例。新增 kind 会触发 gate / webshell / webapp reducer 的穷尽性 switch 全链改动（v0.21 纪律），收益为零——event 名 + 文档化类型已足够。事件名保留清单写入 `signals/types.ts` 注释（`system.prompt` / `tools` / ...），防未来拼写漂移。
6. **链路测试先 mock 后真 API，确定性断言与行为软验证分离**：mock LLM（无 ARK 也能跑）覆盖"装配链 + 信号 + 前端展示"的确定性部分；真实 API（ARK）只承担两件事——① 请求体确实携带升级 description（可断言），② 模型在引导下先 read 再 edit 的**软验证**（记录序列，违规告警不 fail）。行为级硬断言会把真实 LLM 测试变成 flaky 维护负担（对齐 v0.19 先例）。
