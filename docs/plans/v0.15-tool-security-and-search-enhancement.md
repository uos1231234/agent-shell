## 1. 约束（Constraints）

### 1.1 不可违反的架构契约

1. **SecurityHook 不覆盖系统工具**（`tests/shell/registry.test.ts:401-415`）：
   > `securityHook does NOT apply to system tools (trusted builtins bypass hooks)`
   - 系统工具走 `sysTool.execute(args, ctx)` 直接执行，不经过 `executeGuarded`
   - 这是**设计契约**，不是缺陷。系统工具是 trusted builtins
   - **结论**：新增的系统工具安全检查**不能**通过路由到 `executeGuarded` 实现
   - **v0.15 方案**：新增独立的 `SystemSecurityHook` 数组，在 `execute()` 的系统工具分支运行

2. **wrapTool 是系统工具的唯一 guard 入口**（`src/im/tools/helpers.ts:20-37`）：
   - `wrapTool` = `requireReason` + re-throw
   - 系统工具的 `execute` 已经被 `wrapTool` 包裹，`executeGuarded` 会 double-wrap

3. **panic=abort 等价契约**（ADR-013）：
   - 工具 `execute` 绝不能 throw 未捕获异常 → 必须返回 clean error message
   - `loop.ts:216-230` 的 catch 会格式化 `Tool "X" failed: <msg>`

4. **ADR-015 不新增 guard/metric/config 字段**：
   - 不新增熔断统计字段
   - 安全措施走既有 errorRate/toolRate 熔断

5. **ToolContext 是底层共享类型**（`src/shared/tool-context.ts`）：
   - 可以加 optional 字段（如 `isWikiAgent` 的先例）
   - 不能改已有字段的语义

### 1.2 已锁定的设计

- `SecurityHook` 类型签名：`(args, ctx, toolName) => void | Error`（同步）
- `SystemSecurityHook` 类型签名：`(args, ctx, toolName) => void | Error | Promise<void | Error>`（同步/异步）
- `executeGuarded` 流程：hooks → requireReason → execute → truncate
- `loop.ts` 的 `executeToolCalls` 不感知工具内部安全细节
- `ToolRegistry.execute` 的分发顺序：system → mcp → skill

## 4. 设计原则（Principles）

1. **不动核心 dispatch 逻辑**：`registry.ts` 的 `execute()` 分发顺序不变，系统工具仍然不走 `executeGuarded`
2. **新增而非替换**：安全措施以 hook/独立模块形式叠加，不改动现有工具的核心执行逻辑
3. **纯函数优先**：安全检测逻辑（敏感文件、危险命令）实现为纯函数，便于测试
4. **Fail-closed**：审批通道断开/超时 → Deny（参考 AtomCode `approval_channel_failure_deny`）
5. **Grant scope 差异化**：write/edit 工具级 scope，bash session 级 scope
6. **向后兼容**：现有测试 `securityHook does NOT apply to system tools` 仍然通过
7. **rg 硬依赖**：搜索必须依赖 rg，无 rg 则启动报错
8. **MCP instructions 默认丢弃**：参考 Kimi Code 做法，保证可用性和性能
9. **读写路径分离**：`resolvePath`（write 用，不检查存在性）vs `resolvePathForRead`（read 用，检查 + hint）

## 7. 决策信息（Decisions）

### 7.1 已决定（用户拍板）

| # | 决策 | 结果 | 理由 |
|---|---|---|---|
| D1 | 审批触发范围 | **C** 可配置，默认仅危险命令+敏感路径 | 与 Kimi manual 模式对齐 |
| D2 | 审批超时 | **300s** 超时→Deny | fail-closed 安全底线 |
| D3 | Grant scope | **A** write/edit 按文件路径 scope，bash 按 session scope | 安全且体验好 |
| D4 | not-found hint 范围 | **B** 全局返回（突破 cwd） | 更友好的全局提示 |
| D5 | rg 引入 | **rg 硬依赖** | 大代码库核心场景 |
| D6 | MCP instructions | **默认丢弃 + 可配置 allow** | Kimi 丢弃法保证可用性 |

### 7.2 实现过程中的调整

| # | 调整 | 原因 |
|---|---|---|
| A1 | 读写路径分离：`resolvePath` vs `resolvePathForRead` | write 工具需要创建新文件，不能检查存在性 |
| A2 | 取消 Node grep 保留 | 用户要求一步到位，rg 是硬依赖，两套代码重复 |
| A3 | SystemSecurityHook 独立于 SecurityHook | 遵守现有契约（测试 401-415 行） |
| A4 | 审批 hook stub handler 在 extensions.ts | 未来接线的TODO标记 |
