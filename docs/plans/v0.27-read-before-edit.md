## 1. 约束（Constraints）

这一段是 6 条约束，违反任一条 = 计划不合格。

1. **用户四项拍板（2026-09-07，不可改）**：
   - 作用域：**仅 edit 硬约束**。write / search_replace 豁免硬约束（search_replace 改动集执行前未知，机制上不可行；write 按拍板豁免）。
   - 字段形态：**布尔可接受**，但不得因范围太窄而真实工作不可用——必须验证不同类型文件（UTF-8 / GB18030 / 二进制 / 不存在）在 read→edit 链路的行为矩阵（本计划 §5.3 测试矩阵）；并已对标 KimiCode / AtomCode 成熟方案（结论见 §4.1，两家均无硬机制，见 §7 决策 D1）。
   - "已读"判定：**宽松档**——① 目标文件不存在（新建）免检；② 任何成功的 read（含 offset/limit 分段）都记已读；③ 同一会话已读一次后多次写放行；④ read 失败（文件不存在）不记录。
   - 默认开启策略：**库默认开但仅 edit**。
2. **不引新概念、不引新依赖**：只扩展现有 `ToolDefinition`（同 `parallelSafe` 模式，ADR-025 T8），不新增 guard/metric/config 字段（ADR-015）。状态复用 per-session 机制，不建独立存储。
3. **状态机与协议层不动**：约束失败 = 既有 throw → `wrapTool` → loop 的 `Tool "X" failed: <msg>` 干净英文句子（`loop.ts:454`），计入 errorRate 累计，无特殊化。
4. **三层职责不许跨层**（ARCHITECTURE.md §3）：检查/记录逻辑落在 `src/im/` 工具层；`src/shared/tool-context.ts` 只能 type-import 状态类型（对齐 approval-store 先例，`tool-context.ts:6`）。
5. **edit 既有内容寻址正确性命门保留**：`edit.ts:66-118` 的现场重读 + oldText 0 次/多次拒绝（`edit.ts:86-92`）+ 原子替换逻辑**一行不改**。read-before-edit 是叠加在其上的"行为前置"，不是替代。
6. **fullPermission 不豁免**（默认，见 §7 未决 U1）：该纪律是模型行为质量引导，不是权限门。write-approval door 的 fullPermission 短路（`write-approval.ts:134`）不适用于此处。

## 3. 架构信息（Architecture）

### 3.1 信息流（改动后）

```
        LLM 回合（工具调用批次）
                 │ 恒带 ctx（sessionId）
                 ▼
        loop.executeToolCalls ────────────► registry.execute(name, args, ctx)
        （分桶并发，本计划不改）                     │ getOrCreateSession(ctx.sessionId)
                                                     ▼
                                            sessionState = { approvalStore, readPaths: Set }
                                                     │ ctx.sessionReads = 包 readPaths
                                                     ▼
                                            sysTool.execute(args, ctx)      ← 工厂闭包
                                              │                              │
            ┌─────────────── read ───────────┤                              │
            │  resolvePathForRead(cwd,path)   │                              │
            │  readFile(...) 成功             │                              │
            │  ▼ markRead(realPath, ctx)      │                              │
            │  （读失败抛错→不记录，符合宽松档④）    │                              │
            └────────────────────────────────┤                              │
            ┌─────────────── edit ───────────┘                              │
            │  resolvePath(cwd,path)  → realPath                            │
            │  ▼ assertReadBeforeEdit(realPath, ctx)                        │
            │     · 文件不存在 → 放行（宽松档①；但 edit 本身将 ENOENT——            │
            │       规则对该工具坍缩为"已存在文件必须已读"，见 §4.3）                │
            │     · 文件存在且 ctx.sessionReads.has(realPath) → 放行（宽松档②③）   │
            │     · 存在且未读 → throw 引导文案                                  │
            │  ▼ editFile(...)（内容寻址守卫保留，不改）                          │
            └────────────────────────────────
```

### 3.2 角色与边界

| 角色 | 位置 | 职责 | 知道什么 |
|---|---|---|---|
| **声明方** | edit 工具定义（`tools/index.ts`） | `requiresPriorRead: true` + description 引导 | 自己是写工具 |
| **记录方** | read execute 闭包 wrapper | read 成功后 `markRead` | 只有它知道 resolved 绝对路径 |
| **校验方** | edit execute 闭包 wrapper | 执行前 `assertReadBeforeEdit` | 同上 |
| **状态宿主** | `SessionSecurityState.readPaths` | per-session 已读集合 | sessionId 维度 |
| **注入方** | `registry.execute()` | ctx 挂 sessionReads | 与 approvalStore 同一注入点 |
| **正确性命门（不动）** | `edit.ts` 内部 | 现场重读 + 精确匹配 | 磁盘当前内容 |

### 3.3 路径归一化同口径（唯一性命门）

read 记录与 edit 校验**必须解析到同一字符串**：
- read 用 `resolvePathForRead(cwd, path)`（存在性检查 + notFoundHint），成功才记录；失败（Path not found）在 resolve 阶段抛错，**不会执行到 markRead**（宽松档④天然成立）。
- edit 用 `resolvePath(cwd, path)`（不查存在——edit 对不存在文件由 `editFile` 的 `fsReadFile` 报 ENOENT，`edit.ts:72`）。
- 两者都产出 normalize 后的绝对路径（`path.ts:187-194`），cwd 来自同一工厂闭包 → 记录键与校验键同构。**若未来有人把路径处理移出工厂层或换解析函数，此不变量断裂，纪律静默失效**——DoD 含同口径回归测试（§5.3 用例 1/2 覆盖相对/绝对/带 `./` 三种写法）。

## 4. 设计原则（Principles）

1. **纪律是行为引导，不是正确性命门（对标结论的直接推论）**：AtomCode（L1）与 KimiCode 都**没有**先读硬机制——AtomCode 的 `ToolContext` 无任何文件状态（`tool.rs:167-176`），KimiCode 的 `ExecutableTool` 契约无 precondition 字段（`loop/types.ts:140-159`），read 均零副作用。两家防陈旧靠同一结构：edit 现场重读 + old_string 精确匹配 + 失败文案引导 "Re-read the file"（AtomCode `edit.rs:173-177`；KimiCode `edit.ts:120-121`），外加工具描述 md 里的提示词纪律（KimiCode `edit.md:4` "DO NOT call Edit from memory"）。agent-shell 的 `edit.ts` 已与两家同构。**因此本特性不加新保护线，只加一道"行为前置"**：把两家放在提示词里的纪律（先读再改）升格为工具自描述字段 + 运行时软校验，价值是减少"陈旧 old_string → 0-match 失败 → 引导重读 → 重试"的 LLM 侧轮次浪费，不是数据安全（那是 write 覆盖场景，本轮按拍板豁免）。
2. **宽松档是"可用性"的全部**：用户点名"不要因范围太窄而真实工作不可用"。真实编码流里模型常分段读大文件（offset/limit）后改其中一段、或改完再改同一文件——宽松档②③正是为此：任何成功 read 都算已读、写后不失效。对标两家无硬机制的事实反过来印证：一旦做硬校验，语义必须是宽松纪律而非严格门禁，否则会卡死正常流。**不采用"写后失效"或"仅全量 read 计已读"**（AskUserQuestion 时用户已确认宽松档，此二档会制造无谓 read 轮次）。
3. **状态贴 session、注入贴 ctx、守卫贴工厂**：已读集合放在 `SessionSecurityState`（与 approvalStore 同生命周期、子代理继承父 sessionId 天然共享）；ctx 注入点与 `ctx.approvalStore` 并列（`registry.ts:530-532`），一处接线；守卫包装发生在工厂层是因为**只有工厂闭包持有 cwd**（`tools/index.ts` 每个 execute 内联 `resolvePath`），registry 层无 cwd 无法解析路径。此三点各自只有一个落点，不复制。
4. **无 ctx 直调降级不强制（保守的向后兼容）**：`registry.execute(name, args)` 裸调（无 ctx）是 legacy 路径（`GLOBAL_SESSION` 回退，`registry.ts:20-22,355-363`）。守卫读 `ctx?.sessionReads`，为空则不校验不记录——裸调保持现状语义（`tests/im/tools/index.test.ts:62` 这类工具正确性测试不受影响）。真实 harness 的 loop 工具链恒带 ctx（runIMLoop 组装时注入 sessionId），纪律在真实路径生效。**DoD 必须验证：loop 全链路 ctx 恒为真值；若发现某路径 ctx 为空，该路径纪律不生效需显式暴露。**
5. **fullPermission 不豁免**：write-approval 门的 fullPermission 短路（`write-approval.ts:134`）语义是"跳过人类审批"；read-before-edit 语义是"模型应先看文件再改"，与信任程度无关。豁免会引入第二个入口、测试面翻倍，违反"一层最正确"。留 U1 待用户最终确认。
6. **只动 read 与 edit 两个工具的定义，且 edit.ts 内部零改动**：新增守卫是 execute 闭包外层包装 + 一个共享 helper 文件，不触碰 `edit.ts` 的内容寻址、编码 round-trip guard（`encoding.ts:141-149`）、per-path 串行锁（`edit.ts:25-49`）。

## 5. 模块化引导（Module Guidance）

### 5.1 新文件：`src/im/tools/read-before-edit.ts`

共享 helper，纯逻辑 + 无 I/O（守卫只查 Set，不 stat——stat 由 edit.ts 的既有读盘兜底，见 §5.3 用例 5 说明）。

```ts
// 公开 API（type signature，不含实现）
export type SessionReads = {
  has(absPath: string): boolean
  add(absPath: string): void
}

/** read 工具成功读取后调用。ctx.sessionReads 为空（无 ctx 裸调）时静默跳过。 */
export const markRead = (absPath: string, ctx?: ToolContext): void

/**
 * edit 执行前调用。规则 = 宽松档：
 *  - 目标不存在 → 放行（edit 自己会 ENOENT，规则坍缩见 §4.3）；
 *  - 目标存在且 ctx.sessionReads.has(absPath) → 放行；
 *  - 存在但未读 → throw（文案引导先 read）。
 * ctx.sessionReads 为空 → 不校验（原则 4）。
 */
export const assertReadBeforeEdit = (absPath: string, toolName: string, ctx?: ToolContext): void
```

- 依赖：`ToolContext`（shared，type）；`existsSync` 从 `node:fs`（判断"文件不存在免检"用 stat 而非 try-read——edit.ts 的读盘已兜底，这里只用 `existsSync` 判免检分支，避免双重读盘）。等等——§4.6 说守卫不 stat，§5.1 又要 existsSync，矛盾？**裁决**：edit 目标"不存在"的判定**不做**（宽松档①对 edit 实际不可达：edit 不存在文件必被 editFile 的 fsReadFile ENOENT 拒绝，见 §4.3 注释），所以守卫只查 Set：`!ctx.sessionReads.has(absPath) → throw`。免检分支在 edit 上无意义，不在 helper 里实现——写 helper 时只实现"已存在文件必须已读"一种规则，测试锁定坍缩行为（§5.3 用例 5）。——此裁决写进代码注释。
- 被依赖：`tools/index.ts` 的 read/edit execute wrapper。
