## 1. 约束（Constraints，共 8 条）

1. **信号关唯一中转**（ADR-0026）：P0 不新增 GateSignal kind（产物是前端视图层投影）；P1 只走既有**入站命令通道**（新增 GateCommand kind，走既有 /api/v1/cmd，不加新 HTTP 路由）；P2 纯前端渲染 + 系统提示词模板行。
2. **ADR-015**：不新增 guard/metric/config 字段。
3. **工作区 = 权限边界**（用户拍板 52315b1）：P1 workspace.read 必须**路径包含性检查**——resolve 后必须在会话 workDir 内，越界一律拒绝。
4. web-host 绑定 `127.0.0.1`（web-host.ts:358）→ P1 天然仅 loopback 可用（与 deepseek loopback 门控同构）。
5. **所有契约为加法变更**：GateCommand 新 kind（穷尽性 switch 编译期强制路由）、SignalGateHandlers 加**可选** handler、ToolTurn 加可选字段——全部向后兼容，旧 jsonl 快照无新字段仍可解析。**ToolTurn.args 只活在内存（databus 投影 + gate 信号），不落盘、不进 prompt**（改动②③ 保证，恢复路径走 assistant turn 的 function.arguments）。 **【superseded 2026-09-09】用户拍板推翻本条：args 随落盘全量保留（databus 消费方是 LLM 侧工具活动理解，args 是工具事件语义核心；恢复后内存 Databus 与热路径行为一致），敏感内容明文落盘的取舍写入 docs/用户协议须提及.md 由用户自决。**
6. commit 5254fd5 已删 permission.revoke 全链，**不复活**。
7. 当前基线：1801 tests 绿 / tsc 0 错——完成后不得回退。
8. **产物来源纪律（deepseek 纪律）**：只认**成功的**写文件类工具调用（write / edit / search_replace），从工具参数机械提取路径，**不信模型最终回复的话**；失败调用、读文件、bash 不算；首见顺序去重；同轮先写后改 = 一个条目。

## 4. 设计原则（本计划特定取舍，共 6 条）

1. **产物 = 工具调用事实，不信模型的话**（deepseek 纪律）：只认成功的写文件类调用（write / edit / search_replace，参数均有 `path` 字段），从 args 机械提取，失败调用 / 读文件 / bash 一律不算。
2. **产物是视图层投影，不是新状态**：纯函数 `producedFilesOf(turn)` 从 TurnView.toolCalls 派生，不加新 state、不加新 GateSignal kind——与"UI 是信号的忠实投影"原则（v0.22 §4.1）一致。
3. **实时与恢复同一套派生函数**：producedFilesOf 是纯函数，对实时 reducer 产物和 historyToItems 产物同样适用，重连恢复后 chips 自动复原。
4. **新命令只走既有入站命令通道**（P1）：新增 GateCommand kind 走既有 /api/v1/cmd + gate.command 穷尽性 switch（编译期强制加 case），不加新 HTTP 路由。
5. **工作区是权限边界**（用户拍板 52315b1 的延伸）：P1 workspace.read 必须做路径包含性检查——resolve 后必须位于会话 workDir 内，越界一律拒绝。
6. **契约全部加法变更，向后兼容**：GateCommand 新 kind（穷尽性 switch 编译期强制路由）、可选 handler、ToolTurn 可选字段——旧 jsonl 快照无新字段仍可解析。

- 产物 = **成功的**（!pending && !isError）write / edit / search_replace 调用；读文件、bash、失败调用不算。
- 路径取 `args.path`（三者参数均含 `path` 字段，[已验证]）。
- 首见顺序去重；同轮先写后改 = 一个条目。
- chips ≤ 6，其余「+N 个文件」点击展开。

## 7. 决策信息（Decisions）

| 决策 | 理由 |
|---|---|
| 产物来源 = 工具调用事实（成功才计数） | deepseek 纪律："a produced file must be listed whether or not the model remembered to name it" |

### 附带修复：resync 恢复缝隙（2026-09-07 审查核实，用户拍板纳入 v0.24）

**[已验证]** 前端组装是双路径单源优先模型（非交错）：实时 WS 信号经 `reduceSignal` 增量累积；恢复经 `session.history` → `historyToItems` **整体替换** items 后 WS 接管（turnId 同命名空间衔接）。去重在 `ws-client.ts:90`（`frame.seq <= maxSeenSeq` 拦截）。审查发现恢复路径有一个确凿缝隙：

**缝隙 A（属实）：resync 后内存尚在的会话丢失断线/重启期间的变更。** 触发条件 = 常规场景（断线期间服务端发出 >500 帧致 buffer 挤出，或服务端重启）。代码路径：

1. `stream.ts:97-105`：游标落后致 buffer 挤出 → 发 `{type:'resync'}` 并 **return（拒绝本次 replay）**
2. `ws-client.ts:82-86`：resync 时 `cursors.clear()`（重连后发空 cursor → 服务端会 replay 全 buffer），但 `maxSeenSeq` **未清** → replay 帧被 line 90 全部拦截；后续新帧（seq 继续涨）能正常到达
3. `App.tsx:104-110` onResync → 对每个已知 session `openSession`；`App.tsx:67` 的 gate 是「**本地 items 非空就不拉 history**」→ 内存尚在的会话不补 history
4. 净结果：被挤出 buffer 的帧既不重放也不从 history 补 → **变更丢失，直到用户手动刷新（清空内存走 history）**

**缝隙 B（同源，随 A 修复消解）：user.message 双源。** 实时靠 `appendLocalUserMessage` optimistic 编造（后端无 user.message 信号），恢复靠 history 真源；当前靠同一 gate（"内存有 items 就不拉"）兜住不重复——这正是 A 的成因，改 A 即同时消除 B 的依赖。

**修复方案（前端为主，无需改后端协议）**：

| 项 | 方案 |
|---|---|
| `App.tsx` onResync 恢复逻辑 | resync 时对**内存中所有会话无条件拉 history**（`applyHistory` 整体替换），不再看 items 是否为空。替换语义天然不重复：history 的权威 user/assistant turn 替换 optimistic 占位，`historyToItems` 的 turnId 与 WS 同命名空间，替换后增量无缝接管 |
| 发送中 prompt 的边界 | resync 瞬间若存在未确认的 optimistic user（HTTP 回执未回），history（此刻不含它）替换后该条暂隐；后端处理完成后 WS 信号（turnId 相同）经 `upsertTurn` 重建，不丢。注明即可，不做额外保护 |
| `ws-client.ts` | 不改（resync 语义正确：丢增量靠 history 补）。可在注释中补充"maxSeenSeq 保留是有意的——resync 后 replay 全量被拦，恢复完全依赖上层 history" |
| 测试 | App.tsx 装配层目前**零覆盖**（session-store.test.ts 只测纯函数）。补一个装配级测试：模拟 resync → 已加载会话（items 非空）也被无条件 applyHistory；或提取 onResync 决策为纯函数（`shouldResyncHistory(items)`）单测。DoD 见下 |
