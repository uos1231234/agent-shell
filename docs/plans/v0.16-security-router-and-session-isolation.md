# v0.16 — 安全路由器 + 会话隔离 + 可插拔门禁

> **Depends on**: HEAD `df5328c`（v0.12.4 + v0.15 工具安全 + approval hook 已落地）。
> **Blocks**: v0.16+ production hardening（per-session audit log、door 热插拔 UI）。
> **Plan status**: implementation plan. Code changes must be approved before landing.

---

## 0. 功能定位

**一句话**：在 `registry.execute()` 内部引入一个**安全路由器**，每个会话拥有独立的安全状态，路由器根据 sessionId 查状态、派发可插拔的**门禁策略**（敏感路径、危险命令、写审批等），子智能体继承父会话的 sessionId 从而共享权限上下文。

**解决什么问题**：
1. 当前 `ApprovalStore` 全局共享，多会话串台
2. 当前安全钩子是 push 进数组，无 session 维度，叠加无去重
3. 当前门禁逻辑（sensitive-path / dangerous-command / approval）散落在多个文件，与 registry 紧耦合
4. 子智能体无法继承父会话的审批状态

**不做什么**：
- 不改变 `ToolRegistry` 的外部 API（`registerSystemTool` / `execute` 签名不变）
- 不改变现有 8 个系统工具的 execute 内部逻辑（门禁上移到路由器层）
- 不引入新的 guard/metric/config 字段（ADR-015）

---

## 1. 约束

本节 N 条硬约束，违反即不合格。

1. **Router 在 registry 内部**：Router 是 `ToolRegistry` 的内部机制，不是外部 hook。`execute()` 在系统 hook 之后、工具执行之前调用 `router.check()`。`[用户拍板 Q1=A]`
2. **sessionId 在 ToolContext 上**：`ToolContext.sessionId?: string`，optional 不破坏现有 caller。`[用户确认]`
3. **子智能体继承父 sessionId**：`run_subagent` 不生成新 sessionId，子 loop 的 `ctx.sessionId` 与父相同。`[用户确认 Q3]`
4. **门禁是可插拔策略**：每个门禁实现 `SecurityDoor` 接口，Router 持有 door 列表，按 session 状态依次调用。Router 本身不含检测逻辑。`[用户拍板 Q3=B]`
5. **现有安全检测逻辑零丢失**：`sensitive-path.ts` 的 `isSensitivePath`、`dangerous-command.ts` 的 `checkDangerousCommand`、`approval-hook.ts` 的审批流，全部迁移为 door 实现，行为不变。`[已验证: 现有测试覆盖]`
6. **向后兼容无 sessionId 的 caller**：`ctx.sessionId === undefined` 时，Router 使用一个默认的"全局 session"状态（行为与当前 v0.15 一致）。`[设计决策]`
7. **不新增 module-level singleton**：Router 实例由 `ToolRegistry` 持有，session 状态由 Router 持有。无全局可变状态。`[设计决策]`

## 3. 架构

### 3.1 信息流

```
Tool Call
  │
  ▼
registry.execute(name, args, ctx)
  │
  ├─ 1. parse args (现有)
  ├─ 2. run systemSecurityHooks (现有，不变)
  ├─ 3. router.check(ctx, name, args)  ← 新增
  │     │
  │     ├─ sessionId = ctx.sessionId ?? '__global__'
  │     ├─ state = sessions.get(sessionId) ?? createDefault(sessionId)
  │     │
  │     └─ for door of doors:
  │          decision = door.check(state, name, args, ctx)
  │          if !decision.allow → throw Error(decision.reason)
  │
  └─ 4. tool.execute(args, ctx)  ← 仅在 router 放行后执行
```

### 3.2 模块关系

```
┌─────────────────────────────────────────────────────────┐
│                    ToolRegistry                           │
│  ┌──────────────────────────────────────────────────┐   │
│  │ SecurityRouter                                    │   │
│  │  sessions: Map<sessionId, SessionSecurityState>   │   │
│  │  doors: SecurityDoor[]                            │   │
│  │                                                    │   │
│  │  check(ctx, toolName, args): Promise<void>         │   │
│  │  createSession(sessionId): SessionSecurityState    │   │
│  │  registerDoor(door): void                          │   │
│  └──────────────────────────────────────────────────┘   │
│         │ uses                         │ uses            │
│         ▼                              ▼                 │
│  SessionSecurityState          SecurityDoor (interface)  │
│  ├─ sessionId                  ├─ name: string          │
│  ├─ approvalStore              └─ check(state, name,     │
│  └─ (future: permissionLevel)        args, ctx)          │
│                                  │                       │
│                   ┌──────────────┼──────────────┐       │
│                   ▼              ▼              ▼       │
│            SensitivePath   DangerousCmd   WriteApproval  │
│               Door            Door            Door       │
└─────────────────────────────────────────────────────────┘
```

### 3.3 会话生命周期

```
bootstrapExtensions / createMinimalIM
  │
  ├─ registry.securityRouter.createSession(sessionId)
  │     └─ 新建 SessionSecurityState { sessionId, approvalStore: new ApprovalStore() }
  │
  ├─ registry.securityRouter.registerDoor(SensitivePathDoor)
  ├─ registry.securityRouter.registerDoor(DangerousCommandDoor)
  └─ registry.securityRouter.registerDoor(WriteApprovalDoor)

runIMLoop (working agent)
  │
  └─ ctx.sessionId = sessionId  ← 每轮 tool call 携带

run_subagent
  │
  └─ 子 loop 的 ctx.sessionId = 父 ctx.sessionId  ← 继承，不新建
```

## 4. 设计原则

1. **Router 是 registry 的内在机制，不是外挂**：Router 在 `execute()` 内部运行，不暴露为外部 hook。外部 hook（`SystemSecurityHook`）仍然可以附加在 router 之前运行。

2. **门禁是无状态策略，状态在 Session 里**：`SecurityDoor.check()` 是纯函数（输入 state + args → 输出 decision）。审批缓存、grant 集合等可变状态全部在 `SessionSecurityState.approvalStore` 里。Door 不持有状态。

3. **sessionId 是权限边界的唯一键**：同一个 sessionId = 同一个权限上下文。子智能体继承父 sessionId = 共享权限。不同 sessionId = 完全隔离。

4. **默认 session 兜底**：`ctx.sessionId === undefined` 时使用 `'__global__'` 默认 session，行为与当前 v0.15 完全一致，不破坏现有 caller。

5. **Door 顺序即优先级**：doors 按注册顺序依次调用，第一个拒绝即终止。顺序由 `bootstrapExtensions` 控制。

## 7. 决策信息

### 7.1 已决定（带理由）

| ID | 决策 | 理由 |
|---|---|---|
| D1 | Router 在 registry.execute() 内部 | 所有 tool call 必经之路，无绕过可能 |
| D2 | sessionId 在 ToolContext 上 | 每轮自然携带，optional 不破坏现有 caller |
| D3 | 子智能体继承父 sessionId | 权限边界 = 会话边界；子不需要重新审批 |
| D4 | 门禁是可插拔策略（SecurityDoor 接口） | 新增检测逻辑不改 Router，符合 OCP |
| D5 | 默认 session `'__global__'` 兜底 | 无 sessionId 的 caller 行为不变 |
| D6 | ApprovalStore 直接复用 | 已是 per-instance 类，无需重写 |
| D7 | 旧 `approval-hook.js` 文件保留但不注册 | 回滚安全；新 door 是独立文件 |

实现后独立审查发现 4 个问题，用户逐项拍板，全部已落地：

| # | 问题 | 用户决策 | 落地 |
|---|---|---|---|
| **Q1** | `createSession(workingAgentId)` 重复调用抛错，多会话共享 registry 时第二个会话起不来（P0） | **B** — 每次 `createMinimalIM` mint 一个 UUID sessionId，一次组装 = 一个会话；`getOrCreateSession` 幂等 | `minimal.ts` 加 `securitySessionId?: string` 参数，默认 `${randomUUID()}`；`sessionId` 无条件设置（不再 gate 在 subAgentRegistry 上） |
