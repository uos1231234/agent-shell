# v0.10.1a — Databus Narrowing (role: tool only)

> **Historical plan — implemented in commit `c377e2c`.** The split-store defect this landing introduced is corrected by v0.10.4 ([`v0.10.4-system-agent-autodrive.md`](./v0.10.4-system-agent-autodrive.md)).

> **Parent**: [v0.10.1-index.md](./v0.10.1-index.md)
> **Depends on**: nothing (this is the foundation)
> **Blocks**: §B (mailbox references `ToolTurn` shape) and §C (factory reuses
> narrowed `Databus`)

---

## 0. What this piece does

Make `Databus` accept **`role: 'tool'` only** at the type level, so that any
attempt to write a `role: 'user' / 'assistant'` turn to the databus is a
compile error. The two other roles move to a new `ConversationMemory` type
that lives next to it. This is the type-level enforcement of ADR-016 §2.1's
"Databus is role-bounded" invariant.

## 1. Module: `src/im/databus.ts` (MODIFY)

### 1.1 Public surface (after this piece)

```ts
// Same shape as v0.9, but the parameter is narrower.
export class Databus {
  append(turn: ToolTurn): void                    // ← was: append(turn: Turn)
  turns(): readonly ToolTurn[]                    // ← was: readonly Turn[]
  // The following methods are NEW in v0.10.1:
  subscribe(sourceAgentId: AgentId, onEvent: (turn: ToolTurn) => void): () => void  // returns unsubscribe
  query(filter?: { sourceAgentIds?: AgentId[]; range?: [number, number]; limit?: number }): readonly ToolTurn[]
}
```

### 1.2 `ToolTurn` type (replaces `Turn` for the tool role)

Lives in `src/im/databus.ts` (re-exported from `src/im/types.ts` for §B/§C to import).

```ts
export type ToolTurn = {
  id: string
  role: 'tool'                                    // ← single allowed value
  toolCallId: string
  content: string
  isError?: true
  sourceAgentId: AgentId                          // ← NEW: cross-agent join key
  at: number
}

export type AgentId = string  // 'main' | 'warehouse' | 'compressor' | 'recall' | ...
```

The `sourceAgentId` field is the join key for cross-agent queries (ADR-016
§2.1 invariant: "cross-agent readable"). Every `append` call must supply it.

### 1.3 What v0.9 methods stay, what goes

| v0.9 method | v0.10.1 fate | Why |
|---|---|---|
| `append(turn: Turn)` | `append(turn: ToolTurn)` | Narrowed type — `role: 'user' / 'assistant'` no longer accepted at the type level |
| `turns(): readonly Turn[]` | `turns(): readonly ToolTurn[]` | Same |
| (none) | `subscribe(sourceAgentId, onEvent)` | New — ADR-016 §2.1 "subscribe" read path |
| (none) | `query(filter)` | New — ADR-016 §2.1 "query" read path. The v0.9 `turns()` becomes the unfiltered special case of `query()` |

The v0.9 docs mentioned `last` / `clear` as future methods. v0.10.1 does
not add them; ADR-016 does not require them. If a future plan needs them,
they slot in as private helpers on the class.

### 1.4 Internal storage

```ts
private readonly stored: ToolTurn[] = []
private readonly subscribers: Array<{ sourceAgentId: AgentId; onEvent: (t: ToolTurn) => void }> = []
```

`append(turn)`:
1. Push to `stored`.
2. Notify each subscriber whose `sourceAgentId === turn.sourceAgentId` (or
   whose `sourceAgentId === '*'`, if we later add a wildcard).

`query(filter)`:
- `sourceAgentIds`: if set, filter to turns whose `sourceAgentId` is in the
  list. Default: all.
- `range`: `[startAt, endAt]`. Default: full range.
- `limit`: take the most recent N. Default: all.

`subscribe(sourceAgentId, onEvent)`:
- Push to `subscribers`.
- Return an `Unsubscribe` function (a closure that splices the entry out).
  The v0.10.1 factory (§C) holds the unsubscribe handle; it is never
  serialised.

## 2. Module: `src/im/conversation-memory.ts` (NEW)

The new home for `role: 'user' / 'assistant'` turns. Used only by the
working agent's own `runIMLoop`. The system agents **never** see this
type (ADR-016 §2.1 invariant: "the databus is role-bounded" cuts both
ways — user/assistant is private to the LLM session that produced it).

### 2.1 Public surface

```ts
export type ConversationTurn =
  | { id: string; role: 'user'; content: string; at: number }
  | { id: string; role: 'assistant'; content: string | null; toolCalls?: ToolCall[]; at: number }

export class ConversationMemory {
  append(turn: ConversationTurn): void
  turns(): readonly ConversationTurn[]
  last(): ConversationTurn | undefined
}
```

The shape is the v0.9 `Turn` union minus the `role: 'tool'` variant. The
`isError` flag is gone (it was a `role: 'tool'`-only field).

### 2.2 Why a new type, not "Databus with two stores"

Three reasons:

1. **Type-level enforcement of the cross-agent boundary.** If
   `ConversationMemory` lives in a different file, the system agents
   cannot import it. The cross-agent privacy invariant becomes a
   compile-time fact, not a runtime convention.
2. **No accidental cross-pollution.** A future maintainer adding
   `query()` to `Databus` cannot accidentally return user turns.
3. **Symmetry with the v0.10.3 plan.** v0.10.3 §4's slot 8 (self-databus
   projection of user/assistant turns) injects `conversationMemory.turns()`
   — it does not call `databus.turns()` and filter. The two stores are
   distinct at the call site.

## 3. Module: `src/im/turn.ts` (MODIFY)

### 3.1 What stays, what goes

The current `Turn` union is split:

| Variant | v0.9 file | v0.10.1 file | Why |
|---|---|---|---|
| `role: 'user'` | `turn.ts` | `conversation-memory.ts` | Moved |
| `role: 'assistant'` | `turn.ts` | `conversation-memory.ts` | Moved |
| `role: 'tool'` | `turn.ts` | `databus.ts` (as `ToolTurn`) | Renamed for clarity |

`turn.ts` is **not deleted** in v0.10.1 — it remains the home of
`turnToMessage`, but the input type changes:

```ts
// Before:
export const turnToMessage = (turn: Turn): ChatMessage => { ... }

// After:
export const turnToMessage = (turn: ConversationTurn | ToolTurn): ChatMessage => { ... }
```

The `case 'tool'` branch stays. The `case 'user' / 'assistant'` branches
move to a new `conversationTurnToMessage` in `conversation-memory.ts`
(only used by `loop.ts:167` for the user/assistant injection path).

## 4. Migration: the 3 `runIMLoop` callsites of `databus` (in `loop.ts`)

These are the only places in `src/im/loop.ts` that touch `Databus`. All
three are line-precise.

### 4.1 `loop.ts:167` — inject all roles into the prompt

**Before**:
```ts
...opts.databus.turns().map(turn => ({ type: 'turn' as const, message: turnToMessage(turn) })),
```

**After**:
```ts
...opts.conversationMemory.turns().map(turn => ({ type: 'turn' as const, message: conversationTurnToMessage(turn) })),
...opts.databus.turns().map(turn => ({ type: 'turn' as const, message: turnToMessage(turn) })),
```

The order is preserved (user/assistant first because they were first in
v0.9; tool events second). v0.10.3 may reorder this; that is §C's
decision, not §A's.

### 4.2 `loop.ts:238` — `append(assistantTurn)`

**Before**:
```ts
opts.databus.append(assistantTurn)
```

**After**:
```ts
opts.conversationMemory.append(assistantTurn)
```

### 4.3 `loop.ts:262` — `for (const tr of toolResults) opts.databus.append(tr)`

**Before**:
```ts
for (const tr of toolResults) opts.databus.append(tr)
```

**After**:
```ts
for (const tr of toolResults) opts.databus.append({ ...tr, sourceAgentId: opts.workingAgentId ?? 'main' })
```

The `sourceAgentId` is the **only** field added at the call site. It is
always the working agent's own id (system agents maintain their own
`Databus` instance internally; see §C).

**Type-driven migration, not assertion**: §A also changes the
`executeToolCalls` return type in `loop.ts:88-92` from
`{ turns: Extract<Turn, { role: 'tool' }>[]; errorCount: number }` to
`{ turns: ToolTurn[]; errorCount: number }`. The `tr` variable then is
already `ToolTurn`, the spread `{ ...tr, sourceAgentId }` produces a
plain object literal that TS accepts as `ToolTurn` directly (no
`as` cast needed). The compile error is the assertion.

## 5. New `IMLoopOptions` fields (REQUIRED in v0.10.1)

```ts
export type IMLoopOptions = {
  // ... existing fields (config, registry, databus, streamChat, url, model, systemPrompt, userTemplate, systemToolRefs, mcpRefs, skillRefs) ...

  conversationMemory: ConversationMemory    // NEW. Required.
  workingAgentId: AgentId                    // NEW. Required. Default 'main' if not provided.
  mailbox?: Mailbox                          // NEW. Optional in §A; required in §C.
  // stateLine, projectionConfig, systemAgents — added in §B / §C / v0.10.3
}
```

Two new required fields. Existing callers (the 3 `examples/*.ts` files)
break. §A also ships a `createMinimalIM(opts)` factory in
`src/im/minimal.ts` (NEW, ~30 lines) that wires a `ConversationMemory`,
a no-op `Mailbox` stub, and a working-agent id of `'main'` so the
examples can be updated with a one-line change.

## 6. Existing constraints (do not violate)

1. **ADR-002**: shell has no business fields. `Databus` / `ConversationMemory`
   are IM-level; they do not leak into the shell. The shell still receives
   `FinalPrompt.messages` — it does not know about the two stores.
2. **ADR-003**: the shell still has 3 states. No new state.
3. **ADR-005**: `compose` is unchanged. It still takes `PromptPart[]`. The
   injection at `loop.ts:167` becomes two `parts.push(...)` calls instead
   of one.
4. **ADR-014**: no new `Metrics` field. `sourceAgentId` is a turn field,
   not a metric.
5. **ADR-015**: one evaluation point for guards. Unchanged.
6. **ADR-016 §2.1**: the databus is **role-bounded** and **passive**. This
   piece enforces "role-bounded" at the type level. "Passive" is a
   runtime invariant — `append` does not push to the prompt; only
   `query()` / `subscribe()` callers see the contents. The new methods
   are the explicit access points; the v0.9 `turns()` method stays
   because `loop.ts:167` uses it for the prompt injection (which is a
   pull, not an auto-push).

## 7. Tests (~8 new / modified)

| File | Test | Asserts |
|---|---|---|
| `tests/im/databus.test.ts` | `appends and reads tool turns in insertion order` | `role: 'tool'` round-trips through `append` / `turns` |
| `tests/im/databus.test.ts` | `rejects user/assistant at the type level` | Compile-fail test: `// @ts-expect-error` on a `role: 'user'` append. **The test file is the type check.** |
| `tests/im/databus.test.ts` | `query filters by sourceAgentId` | Two agents append, query with one id returns only that agent's turns |
| `tests/im/databus.test.ts` | `query respects limit` | 100 turns, query with `limit: 10` returns the 10 most recent |
| `tests/im/databus.test.ts` | `subscribe fires on append matching sourceAgentId` | Two agents, subscribe to A, append to A and B, callback fires only on A |
| `tests/im/databus.test.ts` | `subscribe returns an unsubscribe handle` | Calling the handle stops future callbacks |
| `tests/im/conversation-memory.test.ts` (NEW) | `appends and reads user/assistant turns` | Same as v0.9 databus test, but for `ConversationMemory` |
| `tests/im/conversation-memory.test.ts` | `rejects tool role at the type level` | Compile-fail test |
| `tests/im/loop.test.ts` | `end-to-end: assistant turn lands in conversationMemory, tool turn lands in databus` | One `runIMLoop` round with 1 user message + 1 tool call; assert the two stores' contents |

The two "compile-fail" tests are unusual: the test file itself contains
a `// @ts-expect-error` line that asserts the narrowing. If a future
maintainer accidentally widens the parameter, the test file **fails to
compile** — which is the assertion.
