### #4 详细：SessionStart/SessionEnd 链接协议 done

**核实结果**：
- 协议 `{ type: 'done' }`（SSE `[DONE]`）在 `call.ts:83` 被消费但仅做 `break`（空操作）
- shellCall 返回 → 循环继续。协议 `done` **已经穿透状态机**，但无显式 hook 通知

**你的 insight**："协议已经穿透了，不需要状态机额外做功，只需同步二者状态"。

**方案**：
- `call.ts:83` case 'done' → emit `TurnEnd`（per-turn，协议 done 触发）
- loop setup → emit `SessionStart`
- loop finally → emit `SessionEnd`
- 扩展 HookEvent 类型：`'SessionStart' | 'TurnEnd' | 'SessionEnd' | 'PreToolUse' | 'PostToolUse'`

### #5 详细：architecture.ts 根目录文档名匹配触发

**核实结果**：
- `MEMORY.md` 是**根目录固定文件名**匹配（不是配置路径）：系统提示词写死"你有一个跨会话记忆文档 MEMORY.md"（static-prompt.ts:78）
- `ARCHITECTURE.md` 同样存在于根目录，但当前是纯人类可读文档
- 当前 architecture.ts 接受 `opts.architectureFilePath` 参数（配置路径），与 MEMORY.md 的"根目录固定文件名"模式不一致

**你的 insight 正确**：architecture 注入应该和 MEMORY.md 一样，匹配根目录下的 `ARCHITECTURE.md` 文件名。

**方案**：
- architecture.ts 改为**固定读取根目录 `ARCHITECTURE.md`**（不是配置路径）
- 解析 `## 架构文档` 字段，提取引用的子文档路径
- 字段存在 → 读取子文档并注入；字段不存在 → 不注入

### 关键合并机会：#1 ShellTerminatedError

```
当前功能路径（guard-trip，:768-779）：
  if (hits.length > 0) {
    state = 'Tripped'
    return { terminated: true, reason: 'guard-tripped', ... }  ← 没有通知 hook
  }

死路径（:600-618）原本要做的：
  catch ShellTerminatedError:
    await callHook(afterShellCall, { error: e, ... })  ← 通知 hook

  if (hits.length > 0) {
    state = 'Tripped'
    // 通知 hook：让 hook 知道为何终止（原本死路径的能力）
    await callHook(afterShellCall, { error: null, hits, state, ... })
    return { terminated: true, reason: 'guard-tripped', ... }
  }
```

## 后续任务（v0.20 系列后续）

### Part 1: SecurityDoor 的 Hook 化（消除独立 router 层）

**insight**：SecurityDoor 应该取代 `systemSecurityHooks` 的 hook 点位，不是维持独立 router 层。保持 Loop 的钩子形态统一。

**对比研究（KimiCode/AtomCode）**：
- **AtomCode**：Chain-of-Responsibility，middleware 可 Proceed/Allow/Deny，Allow 短路剩余
- **KimiCode**：Priority Chain，policy 按序跑，第一个非 undefined 胜出
- **agent-shell 当前**：Deny-Override，全跑全查，任意 deny 阻断

**三种语义都是合理的**，但互不相同。agent-shell 的 deny-override（所有 door 都跑，任意一个 deny 就阻断）是最保守的——适用于"多个安全维度任意一个不通过就阻断"的场景。

**位置**：`registry.execute()` 系统工具分支（原 dead loop 位置）

```ts
// 当前（独立层）：
await this.securityRouter.check(ctx, name, args)

// 改为（hook 形态，复用 systemSecurityHooks 点位）：
for (const door of this.securityDoors) {
  const decision = await door.check(sessionId, state, name, args, ctx)
  if (!decision.allow) {
    this.releaseTool(sessionId, name)
    throw new Error(decision.reason)
  }
}
```

**迁移内容**：
- `SecurityRouter.sessions` → `ToolRegistry.sessions`
- `SecurityRouter.doors` → `ToolRegistry.securityDoors`
- `securityRouter.check()` → registry.execute 内直接遍历
- `securityRouter.releaseTool()` → registry 内直接遍历 doors 调用 release()
- 删除 SecurityRouter 类（`src/security/router.ts` 标记废弃）

**保留语义**：deny-override（全跑全查）+ check-release 配对（finally）+ 会话状态隔离

### Part 2: 四个解耦点匹配现有 hook（不改上下文组装顺序）

**约束**：不改变当前上下文组装顺序（system → afterSystem injections → history → userTemplate → afterUser injections → stateLine → tools → summaries → dynamicSchemas → skillText）。

| 解耦点 | 匹配 hook | 具体做法 |
|---|---|---|
| **composePrompt** (55 行) | → **HOOK 1 beforeShellCall 的服务对象** | 抽出为纯函数 `composePrompt(opts, state): PromptParts`。输出加入 HOOK 1 的 ctx，hook 可改写 prompt |
| **shellCall + retry** (110 行) | → **HOOK 2/2b afterShellCall 的核心职责** | 抽出为纯函数 `executeShellCall(opts, prompt, hook1, log): ShellCallResult`。内部包含 streamChat + retry + HOOK 2/2b 调用 |
| **roundState 四散** | → **通过 hook ctx 传递** | 封装为 `RoundState { state, metrics, turns, lastMetrics, advance(), bumpTurn() }`。作为 callHook 的 ctx 字段 |
| **appendAssistantTurn + fireDriveCoordinator** | → **HOOK 3 afterGuards 之后的固定收尾** | 抽出为 `finalizeRound(result, state)`。位置在 HOOK 3 之后、HOOK 4 之前 |

**解耦后的循环骨架**：

```
while(true) {
  state.bumpTurn()
  prompt = composePrompt(opts, state)                    ← 抽出（纯函数）

  hook1 = await callHook(hooks?.beforeShellCall, { prompt, state, ... })
  ← hook1 可改写 prompt / 提供 syntheticResponse / block

  result = await executeShellCall(opts, prompt, hook1, log)
  ← 抽出（含 streamChat + retry + HOOK 2/2b）

  guards = runGuards(...)
  hook3 = await callHook(hooks?.afterGuards, { guards, state, ... })

  finalizeRound(result, state)
  ← 抽出（appendAssistantTurn + fireDriveCoordinator）

  hook4 = await callHook(hooks?.beforeToolExecution, { ... })
  toolResults = await executeToolCalls(...)
  hook5 = await callHook(hooks?.afterToolExecution, { ... })
}
```

### T8: parallelSafe(args) 扩展（保留不删除）

**insight**：category 桶是静态的（bash 永远是 command），但同一工具的不同调用安全 profile 可能不同（`grep` 只读 vs `cargo build` 写操作）。AtomCode 的 `parallel_safe(&self, args) -> bool` 提供了逐参数判定。

**方向**：
- ToolDefinition 新增可选 `parallelSafe?: (args: unknown) => boolean`
- executeToolCalls 中：effectiveConcurrency = parallelSafe?.(args) ? ∞ : CONCURRENCY_LIMITS[category]
- category 桶是默认/保守值，parallelSafe 是精确覆盖

**与 Part 1 关系**：T8 是 Part 1 的叠加层，不是替代。先有 category 桶（粗），再叠加 parallelSafe（细）。
