# v0.42 长程代码任务 benchmark：2M 累计上下文、压缩召回与智能体树

> Depends on: v0.41 goal 模式、G0/G1/G2/G3 压缩梯度、databus stamp 召回、AgentTree/family-bus、headless `--goal`
> Blocks: 长程真实模型跑批、agent-shell 与单代理基线的 A/B 报告、后续 v0.43 多智能体信息架构优化
>
> 本文是任务与评测计划，不修改代码。2M 指一次会话的累计 token-equivalent，不是单次请求超过 1M guard。

## 1. 约束（Constraints）

本段是 **8 段约束**。

1. **[已验证]** goal 生产接线由 `tests/host/edge-assembly-goal.test.ts` 覆盖；本地聚焦验证为 11 个文件、170 个测试通过，`npm run typecheck` 通过。benchmark 使用既有 `goal.set` / `--goal` / `beforeComplete`。
2. **[已验证]** `src/shell/config.ts` 的 `maxTokens` 是单次 request 上限，默认 1,000,000；2M 指累计工作量。
3. **[已验证]** goal hook 顺序是 judge -> G1 -> G2 -> continuation；judge 在压缩前读取完整 canonical。
4. **[已验证]** `ConversationMemory` 保存完整有序工作历史；`Databus` 只保存 tool turns，并提供 stamp、toolName、keyword、sourceAgentIds 过滤。
5. **[已验证]** 被压缩的工具结果必须能通过 `databus_query({ stamp })` 取回全文；只返回头尾不算召回成功。
6. **[已验证]** AgentTree 的子代理通过 family databus 共享同族工具事件，父代理通过 mailbox/databus 查询取得交接证据。
7. **[已读未验]** `cli/headless.ts --goal` 具备批处理入口，但连续多段、跨进程 resume、最后一次 compression drain 后再退出的完整 2M 跑批仍需首次验证。
8. **[推测]** 足够多的完整 user-to-user task blocks 应能触发 G1 watermark 和 400K 后 G2 position trigger；实际次数以 NDJSON 事件和 StateLine 落盘为准。

## 3. 架构信息（Architecture）

### 3.1 公开基准借鉴

本任务吸收三类公开 benchmark 的可验证部分：

| 公开基准 | 借鉴的测试形态 | 在本任务中的落点 |
|---|---|---|
| SWE-bench | 真实工程 issue、跨文件修改、测试判定 patch 是否正确 | Atlas Sync 的真实 bug、兼容性与隐藏测试 |
| Terminal-Bench | 在真实终端里读写文件、执行命令，由环境 verifier 判定 | CLI 导入、恢复、故障注入和最终磁盘状态 |
| LongCodeBench | 长上下文代码理解、定位和修复 | 2M 累计材料、分散事实、压缩后精确召回 |

这里借鉴的是任务结构和程序化验收，不声称本任务与这些 benchmark 的分数可直接横向比较。

### 3.2 被测任务

准备一个隔离的 TypeScript monorepo，名称暂定 `atlas-sync`。它模拟一个已经运行多年的事件同步服务：

| 子系统 | 内容 | 任务中的真实问题 |
|---|---|---|
| `packages/protocol` | event envelope、版本兼容、校验 | 新旧 schema 兼容边界不一致 |
| `packages/ingest` | JSONL/CSV 导入、分片、重试 | 重试重复写入，跨分片顺序不稳定 |
| `packages/store` | event log、snapshot、索引 | 崩溃后 snapshot 与 log 不一致 |
| `packages/merge` | 冲突合并、去重、时钟 | 同一事件在三种来源下结果不同 |
| `packages/worker` | 并发 worker、checkpoint | checkpoint 不是原子提交 |
| `packages/cli` | `atlas import`, `resume`, `verify` | CLI 只报告完成，不报告不确定状态 |
| `packages/api` | 查询和回放接口 | 查询读到半提交状态 |
| `packages/fixtures` | 历史版本、坏数据、失败日志 | 关键证据分散在大量文件中 |
| `tests/contract` | 对外兼容测试 | 隐藏测试依赖旧行为 |

任务标题：**实现 Atlas Sync 的可恢复、幂等、可审计导入管线**。

主代理初始要求：

> 修复并完成 `atlas import --resume`：支持旧版事件、分片重试、崩溃恢复、重复导入幂等、冲突确定性合并和可审计报告。不能破坏现有 API 与旧 fixture。完成前必须运行类型检查、全部测试和一次从空目录到恢复完成的真实 CLI 演练。最终报告必须区分已验证、未验证和不确定项。

### 3.3 信息流

```text
主代理 goal
  |
  +-- schema scout -------- protocol / fixtures
  +-- storage scout ------- store / worker / recovery
  +-- test scout ---------- contracts / CLI / hidden edges
  |
  +-- mailbox + family databus 交接证据
  |
主代理整合 -> 修改代码/测试 -> 运行测试和故障注入
  |
G0 热区 -> G1 本地信封 -> G2 N-to-1 -> G3 M3 归档
  |
databus 保留工具全文和 stamp，后期按 stamp/keyword 精确召回
  |
独立 judge 读取全量 canonical，not_met 生成 continuation
```

### 3.4 四阶段任务脚本

| 阶段 | 主代理必须完成 | 长程设计意图 |
|---|---|---|
| A. 侦察 | 建立模块地图，找出 6 个根因候选，不得马上改代码 | 跨源码、文档、历史 fixture |
| B. 分工 | 并行启动 3 个 scout：protocol、persistence、verification | 测量 AgentTree 并行收益和交接质量 |
| C. 实现 | 改造导入、checkpoint、merge、CLI、测试，保持 backward compatibility | 真实跨包 coding task |
| D. 破坏性验收 | 注入中断、重复导入、坏分片、旧 schema、冲突顺序，根据失败继续修复 | 强制 goal 续跑、压缩后召回 |

### 3.5 2M 工作量构造

不要把 2M token 直接塞进一份提示词。使用可复现 fixture 和多轮工具证据：

| 来源 | 目标规模 | 说明 |
|---|---:|---|
| 源码、注释、设计文档、历史迁移 | 650K | 真实阅读和定位材料 |
| 12 组输入 fixture 与失败日志 | 850K | 成功、重复、崩溃、旧版本、冲突样本 |
| 测试输出、类型错误、CLI 回放报告 | 500K | 第一次方案允许失败，必须读取证据再修 |
| 子代理报告、mailbox、审计证据 | 180K | 必须含路径、符号、命令、证据戳 |
| 最终回归与恢复演练 | 250K | 第二次压缩后仍召回早期事实 |
| **累计目标** | **2.43M** | token-equivalent，以 runner 统计为准 |

硬要求：

- 至少 30 个完整任务 block。
- 至少 12 次 goal judge，至少 6 次 `goal_block_merged`，至少 2 次 `envelopes_distilled`。
- 至少 40 个超过工具结果 ceiling 的可召回证据，其中 20 个必须在 G2 之后再召回。
- 至少 2 次跨进程 resume，至少 1 次在工具结果完成但主代理尚未消费回执附近恢复。
- 每次出站 request < 900K token-equivalent；超过则 benchmark 失败。

## 4. 设计原则（Principles）

1. **任务结果必须是可执行终态。** 通过隐藏 verifier、完整测试、CLI 回放和磁盘状态检查判定，不以自然语言报告作为完成证据。
2. **2M 是累计信息流，不是单次超限。** 这样测的是 harness 如何持续管理工作记忆。
3. **召回必须是必要动作。** 在早期工具输出中埋入旧字段兼容规则、失败分片 ID、禁止改动的 API 行为；后期隐藏测试要求恢复这些事实。
4. **压缩必须可观测且可追溯。** 记录 G1/G2 事件、源 stamp、raw archive 和召回结果，不接受静默丢失。
5. **子代理负责发现，不负责无证据宣告完成。** scout 输出必须带文件路径、符号、命令、结果或 databus stamp。
6. **并行分工必须减少总成本。** 三个 scout 处理不相交信息域；主代理只在复核失败时重复扫描。
7. **goal judge 只检查完成条件，不代替工作代理。** judge 无工具、读取全量 canonical，并把 not_met 理由变成下一轮提醒。

## 5. 模块化引导（Module Guidance）

本 benchmark 不新增 agent-shell 生产模块；新增的是隔离目标仓库和 runner。

| 文件/模块 | 公开 API | 依赖谁 | 谁依赖它 |
|---|---|---|---|
| `benchmark/atlas-sync/` | 目标仓库源码、fixture、测试 | Node/TypeScript | 主代理及 scout |
| `benchmark/runner.ts` | `runScenario(opts): Promise<RunReport>` | headless CLI、临时目录、事件收集 | 跑批脚本、A/B 对照 |
| `benchmark/verify.ts` | `verifyRun(dir): Promise<VerificationReport>` | git diff、测试命令、状态文件 | runner、外部验收 |
| `benchmark/needles.ts` | `loadNeedles(): readonly Needle[]` | 固定事实清单 | 召回准确率验证 |
| `benchmark/baseline.ts` | `runSingleAgentBaseline(opts)` | 同一模型、同一 repo、无子代理/无压缩 | A/B 报告 |
| `benchmark/report.ts` | `writeReport(report, path)` | NDJSON、验证结果 | 最终评测报告 |

```ts
type Needle = {
  id: string
  fact: string
  sourcePath: string
  requiredPhase: string
  recallBy: "databus_query" | "state_query" | "mailbox"
}

type RunReport = {
  passed: boolean
  cumulativeInputTokens: number
  peakRequestTokens: number
  compressionEvents: number
  recalledNeedles: string[]
  missingNeedles: string[]
  subagentCount: number
  toolCalls: number
  verifier: VerificationReport
}
```

## 7. 决策信息（Decisions）

### 已决定

- 任务类型：真实风格的跨包可恢复导入管线，不做纯代码问答。
- 上下文规模：累计 2.43M token-equivalent，单次请求低于 900K。
- 压缩验证：至少 6 次 G1、2 次 G2，且 G2 后必须有早期证据召回。
- 召回判据：按 needle 的精确内容或结构化字段比对；只返回“找到了”不算命中。
- 树形判据：至少 3 个 sibling scout 并行；比较串行基线和树形运行的 wall time、工具调用、重复读取量。
- 恢复判据：两次跨进程 resume 后最终 verifier 通过，且 databus args 仍可消费。
- 基线：single-agent/full-history 与 agent-shell/goal/tree 使用同一目标仓库和模型配置。
- 状态机边界：不改 `DEFAULT_CONFIG`、guard、loop 主循环、goal 阈值或宿主覆盖逻辑。

### 未决 / 待用户拍板

- 目标仓库是新建 `benchmark/atlas-sync`，还是选现有开源 TypeScript 项目做受控 fork。
- 是否允许 scout 写权限；建议默认只读，只有主代理改代码，避免把并行效率与冲突解决混在一起。
- 真实跑批使用哪一个模型及预算；建议先 deterministic mock smoke，再做一次真实模型完整跑批。
- 2.43M 最终采用 provider usage 还是 agent-shell CJK-aware wire estimate；建议同时记录两者。

## Definition of Done

- [ ] 目标仓库、fixture、隐藏 verifier 和 runner 落盘，且不污染 agent-shell 生产源码。
- [ ] 一次完整 run 累计工作量超过 2M，峰值 request 低于 900K。
- [ ] 日志证明 G1/G2 实际触发，不只证明测试桩存在。
- [ ] 至少 40 个 needle 中 90% 以上在压缩后精确召回；关键 20 个全部命中。
- [ ] 至少 2 次跨进程恢复后最终 verifier 通过，且无重复副作用。
- [ ] 三个 scout 通过 AgentTree/family databus/mailbox 完成交接，主代理能引用证据。
- [ ] goal judge 至少经历一次 not_met -> continuation -> met，且不能被完成文本绕过。
- [ ] single-agent baseline 与 agent-shell/tree run 的 token、工具调用、重复读取、wall time 和通过率都有对照报告。
- [ ] `npm run typecheck`、现有 goal 聚焦测试和 benchmark 专项验证全部通过。
- [ ] 报告明确区分 `[已验证]`、`[已读未验]`、`[推测]`，不把模型声称完成当作证据。
