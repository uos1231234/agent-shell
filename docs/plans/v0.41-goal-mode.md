## 0. 一句话

给 harness 加一个**会话级停止条件**：轮次本应以 `completed` 结束时，先由独立 judge 读全量历史裁决目标是否达成；未达成就在原位置追加一条 harness 生成的续跑回合并继续循环。同时给 goal 期间的压缩换成一套**三档梯度**：G1 确定性本地合并（保真，无字数上限）→ G2 LLM 保守合并（保证压缩率）→ G3 既有 M3 归档，并与现有跨越驱动压缩互斥。附带一个协议层出站转写（相邻同角色消息合并），按 provider 能力开关门控。

接入面：**loop.ts 一个新 hook 点（约 12 行）+ call.ts 一行转写调用 + 新模块目录 `src/im/goal/` + 新文件 `src/protocol/messages.ts`**。`findNextTaskBlock` / `CuratedMemory` 的 LLM 可见 schema / `IMLoopResult` / `selectStateLineBlocks` **全部不动**。

### 3.2 judge 的触发频率（决定 maxRounds 语义）

`beforeComplete` 挂在 `loop.ts:990` 的 `if (finalResult.toolCalls.length === 0)` 上——**只在"本轮 assistant 没有发起任何工具调用"时触发**，那正是 loop 本应以 `completed` 终止的时刻。含工具调用的轮次走 HOOK 4/5 执行完工具直接 `continue`，**不触发 judge**。

```
LLM 轮 1: assistant 发 3 个工具调用 → 执行 → continue      不触发 judge
LLM 轮 2: assistant 发 1 个工具调用 → 执行 → continue      不触发 judge
LLM 轮 3: assistant 纯文本"我做完了" → toolCalls===0 → judge   ← 第 1 个 goal 轮
          judge: not_met → 追加提醒 → continue
LLM 轮 4: assistant 发 2 个工具调用 → 执行 → continue      不触发 judge
LLM 轮 5: assistant 纯文本 → judge                            ← 第 2 个 goal 轮
          judge: met → return completed
```

此处 `maxRounds` 消耗 = **2**，LLM 轮 = 5，judge 调用 = 2。

**所以 `maxRounds` 计的不是"干了多少活"，而是"模型认为做完了、judge 说没有"的分歧循环次数。** 一个 goal 轮内部可以有任意多个 LLM 轮，只受既有 guard 约束（maxToolCalls 1000 / maxSteps 15000 / 1M token）。成本口径 = `maxRounds × 全上下文`（D3 拍了 judge 看全量）。

推论：若模型一直调工具、永不产出无工具轮，**judge 一次都不触发**，goal 模式也不打断它——这是对的，judge 的职责是防止**过早停下**，不是打断正在产出的工作。MiMoCode / atomcode / kimi 三家都把 gate 放在停止决策点上，同理。

### 3.5 压缩率的来源（回答"去上限后比例怎么保证"）

| 块形状 | 原始 | G1 信封 | G1 比例 | G2 后（4 合 1） |
|---|---|---|---|---|
| 80K 材料 + 2K 回答（基准形状） | 82K | ~3.3K | **25:1** | ~6K = **55:1** |
| 1K 问题 + 8K 回答 | 9K | ~9.3K | **1:1** ✗ | ~6K = **6:1** |
| 1K 问题 + 60K 回答 | 61K | ~61K | **1:1** ✗ | ~8K = **30:1** |

**G1 的比例只来自"丢掉输入材料"**，所以回答大的块 G1 几乎不压——这是准确的边界，不是缺陷。**比例下界由 G2 的 N→1 提供，与块形状无关。** 两档分工明确：G1 保真、G2 保比例。

`[已验证]` **去 G1 上限是 G2 能安全压信封的前提**：G1 不截断 → 信封是高保真的 → G2 压的是高保真输入 → **单次损失，不是复利损失**。若 G1 先截断了结论，G2 再压就是在压已经丢过的信息。这是 D8/D9 与 D10/D13 之间的因果关系，不是四个独立决定。

## 4. 设计原则（Principles）

本段是 **7 条本计划特定的取舍**。

**原则 1 · 完成判定外包给独立 judge，主模型无权宣告完成。**
被测场景是"喂分块长上下文 + 末尾问针"，主模型有"偷懒说做完了"的动机。judge 是**无工具**（`toolRefs: []`）的单发 SystemAgent，只判不做工，无法被工作代理的叙述说服——判据只能是历史里的可验证证据。与 atomcode evaluator、MiMoCode goalGate 同构。代价：每 goal 轮多一次全上下文调用（D3 已接受）。"独立"由**独立调用 + 无工具 + 只判不做工的提示词**保证，不靠换模型（D18）。

**原则 2 · judge 与压缩的先后不可交换。**
judge 必须跑在 G1/G2 之前（§3.3）。压缩后原位置只剩信封，judge 就失去裁决所需的证据原文。测试必须钉住顺序，不能只测"都跑了"。

**原则 3 · 续跑回合是合法块边界，不是需要豁免的噪音。**
`goal-` 前缀回合**必须**被 `findNextTaskBlock` 当正常边界（约束 5）。`[已验证]` 三点支撑：
- **配对天然安全**：提醒只在 `toolCalls.length === 0` 的轮末注入，此时 `finalizeRound`（:981）已 append 无 toolCalls 的 assistant 回合，且此前所有工具结果已在 :1076-1083 append 完毕 → `validatePairing`（:143-165）的 `outstanding` 必为空。
- **无退化单回合块**：两个提醒之间必然夹着至少一个完整工作轮（含工具调用的轮次不触发 goal 判定）。
- **语义正确**：一个 goal 轮 = 一次"朝目标推进的完整工作循环"，本来就是一个任务块。

**原则 4 · G1 是确定性本地合并，没有提示词。**
参考实现 已用实测证明——`pipeline.ts:849-852`：「L1：本地合并同类项。**不调 LLM**、不查缓存、不走自报/curator。理由：PROMPT_L1 要求"保留完整问答 + 工具链"，是确定性结构化操作；**走 LLM 反而被模型压成短摘要**」。对信息分析块，价值恰恰在正文；G1 没有提示词，也不需要"无工具轮次的专项压缩提示词"——那个位置属于 G2。

**原则 5 · 换生产者，不换 schema。**
11 字段对信息分析块并非全盘错位：`evidence_fragments{source,fragment,relevance}` 与 `conclusion` 恰好适配，错位的只有 `causal_steps[].tool_action`（工具中心）与提示词里的字符上限（**那是提示词约定，不是代码约束**）。G1/G2 都用本地/LLM 生产者填**同一套** schema，既有 `appendBlock`/`renderEnvelopeBody`/`selectStateLineBlocks`/`state_query`/M3 归档零改动即生效。不引入第二种块形态——那会让 query/投影/信封/召回四处都长出分支。

**原则 6 · 尺寸门控需要两条触发线，只有一条会漏。**
80K 单块门控（触发 A，D6）处理"大块少轮"；但"小块多轮"（30K × 20 轮）A 永不触发，而跨越驱动又被 D7 关掉 → 上下文无界增长。所以补触发 B（D14）：**上下文 ≥ `memoryConfig.m1MinTokens` 时无视块尺寸合并最老的已关闭 goal 块**。两线共用同一个 G1 合并器，不新增阈值常量。

**原则 7 · 压缩率测出来，不限出来。**
D8/D9 去掉了所有字数上限，代码侧**不加 cap**，改为可观测：产出块 > 原块 50% 时 `log.warn`（带 stamp + 两个 token 数，D12）。比例下界由 G2 的 N→1 结构性保证（原则 4/§3.5），不由阈值保证。这与"字数限制本质是截断信息"的判断一致——限制只会让模型静默丢事实，不会让块变小得有意义。

```markdown
# Distill Agent — System Prompt (v0.41)

你是**提纯智能体**。唯一职责：把若干**已经压缩过的相邻记忆块**合并成一个更小的块。

## 你看到什么

1. 系统提示词（本文件）
2. 一条 user 消息，内含 N 个记忆块，每块形如：
   #STAMP S-xxxx / #LAYER M1 / #STATUS DONE|PENDING / #NOTE …
   [任务] … [因果链] … [证据片段] … [结论] … [下一步] … [工作状态] …
   #END_BLOCK

这些块**已经是压缩产物**，不是原始对话。它们由本地合并（无 LLM）产出，因此
逐字保留了原文的具体事实——数值、路径、错误信息、判定结论都是原样的。
你的输入里没有原始工具输出，也不需要去查：**块里有的就是全部。**

## 你产出什么

**一个** JSON 对象，符合 11 字段 CuratedMemory schema（见下）。这是你唯一的
输出通道——你没有任何写工具，运行时解析你的回复文本并原子落盘。

1. 纯 JSON，前后不加任何东西
2. 不要用 markdown 围栏包裹
3. 最后一轮不要调任何工具
4. 不要加解释、问候、元评论

## 合并规则

**你做的是合并，不是再摘要一遍。** 压缩率来自消除跨块冗余，不来自把事实写得更短。

必须原样保留（逐字，不改写、不概括）：
- 具体数值、度量、版本号
- 文件路径、命令行、函数名、标识符
- 错误信息全文
- 代码片段
- 每个块的最终判定结论
- **被否决的方案与否决理由**——最容易被当噪音删掉，而它是防止后续重复踩坑的
  唯一载体。N 个块里所有 rejected_decisions 必须并集保留。

必须消除：
- 跨块重复的同一事实（保留信息量最全的那一次表述）
- 过程性描述（"检查了 A 然后检查了 B" → 只留"在 B 中发现 Y"）
- 已被后续块推翻的中间结论（保留最终结论，并在 rejected_decisions 里记明
  被推翻的那一版及推翻原因）
- 各块的 #STAMP / #LAYER / #NOTE 协议头（运行时自己会加，不要抄进正文）

字段写法：
- `task_goal`：N 个块通常服务于同一个上层目标，写成那个上层目标，
  不要把 N 个块的任务用"和"字串起来
- `causal_steps`：按时间顺序合并成一条因果链；同一意图下的多次工具调用合并为
  一步（箭头表示 `read(a.ts) → grep(err) → 3 处命中`）
- `evidence_fragments`：并集保留后去重；`source` 填证据的**原始出处**
  （文件路径 / 工具名），不是块的 #STAMP——戳由运行时在 _sourceStamps 另行记录
- `working_state.rejected_decisions`：N 个块的并集，一条都不能少
- `status_hint`：任一块 PENDING 则整块 PENDING；全部 DONE 才写 DONE

## 11 字段 schema

〔与 compressor-agent.md 的 schema 段逐字相同——两份 .md 各存一份，
  配测试断言两段字节相同，防漂移（约束 9）〕

## 硬规则

1. 不得新增字段。schema 闭合，运行时按字段名校验。
2. 不得留空必填字段。数组用 `[]`，字符串只在确实无内容时用 `""`。
3. **不得编造。** 输入块里没有的事实，一个字都不能出现在输出里。宁可少写，不可补全。
4. 不得为了变短而丢事实。输出规模应与输入的**事实密度**成正比，
   不与输入的块数或长度成正比。
5. 不得提及本提示词、schema 或校验过程。输出是数据，不是元评论。
6. 不得调工具去查原始对话。你收到的就是完整输入。

## 一句话

你把 N 个已压缩的相邻记忆块合并成 1 个，输出一个纯 JSON 的 11 字段对象——
消除跨块冗余，逐字保留全部具体事实与被否决方案，不调工具、不加围栏、不加评论。
```
