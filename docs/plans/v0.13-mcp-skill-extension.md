# v0.13 — MCP / Skill 扩展系统

**Depends on**: v0.12 sub-agent tree 已 commit（基线 629 tests green / 0 tsc errors）。
**Blocks**: 未来 resources/prompts 协议扩展、HTTP 认证、policy 热更新（本计划不做）。

**用户决策（2026-08-31，已拍板）**：
1. 传输层做 **stdio + HTTP** 两种（协议面只做 tools 子集：initialize / tools/list / tools/call，不做 resources/prompts）。
2. **引入官方 `@modelcontextprotocol/sdk`**，但依赖必须停留在 MCP 功能实现内（高内聚），与其他模块低耦合。
3. Skill 形态为 **JS/TS 模块**（每个 skill 一个文件，export SkillDefinition）。
4. 子代理对 MCP/skill 工具**通过 policy 开放**（policy.ts 命名空间规则接线）。

---

## 1. 约束（Constraints）——共 10 条

1. **SDK 隔离**：`@modelcontextprotocol/sdk` 的 import 只允许出现在 `src/mcp/**` 内（grep 强制验证：`grep -rn "@modelcontextprotocol" src/` 的所有命中必须落在 src/mcp/ 下）。registry / im / skills 一律只见本计划定义的窄接口 `McpConnection`。
2. **零热插拔**：注册是启动时的。（`src/shell/registry.ts:6` 头注释 "Registration is startup-time only. No runtime add/remove. (No hot-plug.)"——现状约束，v0.13 不改变。）
3. **不改 ToolContext**：扩展系统消费现有 `ctx.agentId / ctx.databus / ctx.stateLine`，不新增字段。
4. **协议子集**：只做 tools 面（initialize / tools/list / tools/call）。resources / prompts / sampling 不做。
5. **单层执法**：子代理能否用某个 MCP/skill 工具，只在 `validateSubAgentConfig`（config.ts）经 `applyToolPolicy` 判定一次。run-subagent.ts / system-agent.ts 不做第二份 policy 检查（v0.12 §1.9 的"one layer"原则延续）。
6. **compose / loop 不动**：`PromptPart` 的 `mcp`/`skill` 分支与 `IMLoopOptions.mcpRefs/skillRefs` 通路已存在（compose.ts:23-24, loop.ts:95-96, 244-245），v0.13 不新增 prompt part 类型、不改 loop。
7. **Boot fail-fast**：任一服务器连接失败 → 关闭已打开的连接 → throw。不允许"部分启动"的静默状态。
8. **stdio 环境变量不整包继承**：子进程 env = SDK 默认安全环境 + `cfg.env` 显式覆盖；不得把 `process.env` 原样传给 MCP 服务器（防密钥外泄）。
9. **边界**：所有修改落盘在 `agent-shell/` 内；commit 仅在用户要求时做。
10. **Windows 兼容**：stdio spawn 与 HTTP 测试必须在 win32 本机（Node 24 + Git Bash）跑通。

**与 ADR-016 的显式冲突**：ADR-016 §11 写明 "mcp / skill surface is not expanded into a plugin ecosystem"。v0.13 **由用户决策推翻该条**（2026-08-31）。Batch 3 落 ADR-0018 记录此推翻与四项用户决策，ADR-016 不回改。

## 3. 架构信息（Architecture）

### 3.1 扩展装配流（启动时，一次性）

```
caller (example / future host)
  │
  │  bootstrapExtensions({ registry, mcpServers?, skillsDir? })        [src/extensions.ts]
  │
  ├──────────────────────────────┬──────────────────────────────┐
  ▼                              ▼                              │
src/mcp/boot.ts                 src/skills/loader.ts            │
  bootMcpServers(registry,cfgs)   loadSkillsFromDir(dir,{registry})│
  │ 每服务器: connectToServer      │ readdir(.ts/.js/.mts/.mjs)    │
  │  →listTools→toRegistryTool    │ →动态 import()→校验→查重      │
  ▼                              ▼                              │
  ToolRegistry.registerMCP       ToolRegistry.registerSkill      │
  (server, MCPTool[])            (skill)                        │
  └──────────────┬───────────────┴───────────────────────────────┘
                 ▼
  返回 { servers, tools, skills, close() }   ← close() 关全部连接
```

### 3.2 运行期调用流（LLM 发起）

```
LLM tool_call(name="srv__tool")          LLM tool_call(name="my-skill")
        ▼                                        ▼
  registry.execute(flatName)   （派发顺序 system → mcp → skill）
        ├─ MCPTool.execute(args, ctx)  →  conn.callTool(rawName, args)   [窄接口]
        │                                   └─ SDK Client …（只存在于 src/mcp/）
        └─ skill.execute(args, ctx)    →  模块自身逻辑（与 system 工具同契约）
        ▼
  loop.ts 既有错误包装 → tool turn 投影 databus（无需新代码）
```

### 3.3 子代理开放路径（Batch 2）

```
define_subagent(toolRefs=[..., "srv__tool", "my-skill"])
  ▼
validateSubAgentConfig                    [config.ts，唯一执法点]
  ├─ 既有: applyToolPolicy(ref, policy)   ← flat ref 命中 "srv__*" 等 pattern
  └─ 替换 §141-162 一刀切: 允许 skill/mcp ref（仍拒绝未知 ref）
  ▼
run_subagent → createSystemAgent(toolRefs) [system-agent.ts run() 内]
  └─ registry.resolveRef(ref) 分流:
       system → systemToolRefs
       mcp    → mcpRefs { server, refs }
       skill  → skillRefs
  ▼
compose → server__tool / skill schema 进 prompt → LLM 调用 → registry.execute
```

### 3.4 角色与所有权

| 角色 | 文件 | 所有权边界 |
|---|---|---|
| MCP 配置 | src/mcp/config.ts | 配置 schema 校验 + JSON 文件加载；不碰 SDK |
| MCP 连接 | src/mcp/connection.ts + transport | **唯一 SDK 触点**；对外只暴露 `McpConnection` |
| MCP 装配 | src/mcp/boot.ts | 连接管理 + 工具转换 + registry 注册 + close |
| Skill 加载 | src/skills/loader.ts | 文件发现 + import + 校验 + 查重；不注册（返回 defs） |
| 一键装配 | src/extensions.ts | 编排 mcp boot + skill 注册；不含业务逻辑 |
| Ref 分类 | src/shell/registry.ts `resolveRef` | 唯一的"扁平名→来源"判定者，顺序同 execute 派发 |
| 子代理执法 | src/im/sub-agent/config.ts | 唯一 policy 检查点 |
| 子代理路由 | src/im/system-agent.ts | 只分流，不判权 |

## 4. 设计原则（Principles）——共 6 条

1. **SDK 是可替换电池，不是架构**。registry / im / skills 只见三方法窄接口（listTools / callTool / close）。未来换 SDK 或手写协议，只动 connection.ts + transport.ts 两个文件。
2. **扁平名即路由名**。`server__tool` 已是 registry 派发键、schema 导出名、policy pattern 面——三重身份合一，不引入第二套寻址。
3. **Skill 是一等工具**。模块 skill 与 system 工具同走 `ToolExecutor` 契约（args + ToolContext），tool turn 同样投影 databus；loop 无任何 skill 特判。
4. **Boot fail-fast**。部分启动比不启动更糟：坏配置在启动时炸，而不是运行中半瘫。
5. **校验在边界**。配置文件 / skill 模块在装载时一次性校验；运行期信任 registry 内容，不做二次校验。
6. **扩展是 registry 填充问题**。v0.13 全部工作 = 把合格定义填进 ToolRegistry + 子代理路由分流；loop / compose / guards 零改动。

## 7. 决策信息（Decisions）

### 7.1 已决定（实现层，带理由）

| ID | 决策 | 理由 |
|---|---|---|
| D1 | 窄接口 `McpConnection`（3 方法）作为 SDK 与全库的分界 | 约束 1 的落点；测试可用纯对象 fake，不需要 SDK 即可测 boot/registry 链路 |
| D2 | `callTool` 返回 `string`：取 result.content 中 text block 以 `\n` 连接；`isError: true` → throw（loop 既有错误包装接力）；空 content → `JSON.stringify(result)` | LLM 面只该见字符串；错误走统一格式 |
| D3 | boot fail-fast + `close()` 幂等 | 约束 7；close 必须可安全二次调用 |
| D4 | stdio env = SDK 默认环境 + cfg.env 覆盖 | 约束 8 |
| D5 | skill 校验：name `[a-zA-Z0-9_-]{1,64}`、description 非空、execute 为函数；同 registry 内重名（三类任意）→ throw | registry.execute 有静默遮蔽顺序，重名必须在装载期炸掉 |
| D6 | `resolveRef` 是唯一 ref 分类器，顺序与 execute 派发严格一致 | 单一事实；避免 system-agent 与 registry 各自判断 |
| D7 | **行为变更声明**：v0.12.2 的"子代理禁用 MCP/skill"被本轮推翻，改由 policy 决定。`DEFAULT_SUB_AGENT_TOOL_POLICY` default='allow' ⇒ 子代理**默认可用** MCP/skill 工具（除非显式 deny） | 用户决策 4 的直接推论；测试必须覆盖正反两面 |

### 7.2 未决 / 明确延后（不替用户猜）

- resources / prompts 协议面 — 延后
- HTTP 传输的认证（OAuth/API key header 之外的方案）— 延后，本轮只做静态 headers
- skill 子目录 / SKILL.md — 延后
- policy 热更新 — 延后
