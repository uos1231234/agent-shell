## 0. What this piece does

Provide a **per-agent, in-memory, FIFO message queue** that the runtime
and the 3 system agents can use to coordinate asynchronously. The
mailbox is the LLM-mirror of the human inbox (ADR-016 §1.3): a hint
appears at the agent's next turn ("you have N unread"), and the agent
actively calls `mailbox_read` to see the content. No auto-injection.

## 1. Module: `src/im/mailbox/mailbox.ts` (NEW)

### 1.1 Public surface

```ts
export class Mailbox {
  // Send a message to one or more agents. Returns the assigned MailItem.id.
  send(msg: { from: AgentId; to: AgentId | AgentId[]; subject: string; body: string; replyTo?: string }): string

  // Read the inbox of one agent. FIFO order. Default: unread only.
  readOwnInbox(agentId: AgentId, opts?: { unreadOnly?: boolean; limit?: number }): readonly MailItem[]

  // Mark all currently-unread items in an inbox as read. Idempotent.
  markRead(agentId: AgentId, ids?: readonly string[]): void

  // Cheap count for the runtime's "you have N unread" hint.
  hasUnread(agentId: AgentId): boolean

  // Total inbox length (read + unread). For diagnostics.
  inboxSize(agentId: AgentId): number
}
```

### 1.2 Storage

```ts
private readonly inboxes: Map<AgentId, MailItem[]> = new Map()
private nextId: number = 0
```

`inboxes` is lazy-initialised: an agent's inbox array is created on
first `send` to that agent. `nextId` is a monotonic counter; combined
with the high-resolution `Date.now()` for `sentAt`, ids are unique
within a session and sortable.

### 1.3 `send` semantics

1. Assign a unique `id` (`M-${++nextId}-${Date.now().toString(36)}`).
2. Set `sentAt = Date.now()`, `read = false`.
3. For each recipient in `to`:
   - Create the inbox array if missing.
   - Push the **same** `MailItem` reference (the inboxes are not deep
     copies; they share the MailItem object). This is a v0.10.1
     simplification — a future plan may add deep copies if mutability
     concerns arise.
4. Return the assigned `id`.

A `send` to an unknown `AgentId` (e.g. a typo) is **allowed** in v0.10.1:
the inbox is created on the fly. The factory (§C) is responsible for
not creating agents with typos; this is a defence in depth, not a
validation gate.

### 1.4 `readOwnInbox` semantics

1. Get the inbox array; return `[]` if none.
2. Filter: `opts.unreadOnly !== false ? item.read === false : all items`.
3. Sort: by `sentAt` ascending. (Stable FIFO; `Array.prototype.sort` is
   stable in modern V8.)
4. Take: `opts.limit ? slice(0, limit) : all`.
5. Return as `readonly MailItem[]`.

`readOwnInbox` does **not** mark items as read. The agent must call
`markRead` explicitly. This decoupling is the LLM-mirror of human email:
the agent may "preview" without committing to having seen it.

### 1.5 `markRead` semantics

1. Get the inbox array; return if none.
2. If `ids` is omitted, mark all `read: false` items as `read: true`.
3. If `ids` is provided, mark only those items in the inbox whose
   `id` is in the list. (Unknown ids are silently skipped — the agent
   may have already read them; race conditions are not a concern in
   single-threaded v0.10.1.)

### 1.6 `hasUnread` semantics

`return inboxes.get(agentId)?.some(item => !item.read) ?? false`

Cheap O(n) scan. With realistic inbox sizes (≤ 100 messages per
session), this is fine. If profiling later shows a hot path, v0.10.5
can switch to a counter.

## 4. Why these 3 design decisions (one paragraph each)

### 4.1 Why `Map<AgentId, MailItem[]>` and not a single array

If the mailbox were one array, every `hasUnread` would scan all messages
across all agents. Per-agent storage is O(1) lookup for the runtime's
hint, O(1) inbox creation, and FIFO per agent is naturally preserved.
Cost: a `Map` instead of an `Array`. Both fit in memory; the `Map` is
the right shape.

### 4.2 Why `readOwnInbox` does not mark as read

Two reasons:

1. **LLM-mirror**: a human can preview their inbox without committing.
   An LLM agent that accidentally calls `readOwnInbox` (e.g. in a
   loop) should not be punished by silently marking everything read.
2. **Idempotency**: a re-read of the same inbox returns the same items
   in the same order. If `readOwnInbox` mutated state, a retry-after-error
   would silently miss items.

The agent explicitly calls `markRead` when it has decided to act on the
messages. This is the LLM equivalent of clicking "mark as read" in
Gmail.

### 4.3 Why the hint is at the system-prompt tail, not a separate message

ADR-016 §1.3. The hint is **part of the system prompt**, not a separate
`role: 'user'` message. Reasons:

- The system prompt is the agent's identity contract; adding a hint to
  it is "the runtime is telling you something about your environment",
  which is the same shape as the agent's own system prompt.
- A separate `role: 'user'` message would look like the user typed
  "you have 3 unread" — which is misleading. The hint is not user
  content; it is runtime metadata.

The injection point is **not in §B** — §B provides `hasUnread`; the
runtime calls it from the system-prompt-tail append in v0.10.3 §4 step
3. §B does not know about system prompts.

## 5. Existing constraints (do not violate)

1. **ADR-016 §2.3 invariant 1 (privacy)**: A cannot read B's inbox.
   Enforced by the API: there is no `readInbox(agentId)` method, only
   `readOwnInbox(agentId)`. The agent's own `runIMLoop` always passes
   its own `workingAgentId`.
2. **ADR-016 §2.3 invariant 2 (FIFO)**: items stored in `sentAt` order;
   `readOwnInbox` returns them in that order. Enforced by the sort
   on read.
3. **ADR-016 §2.3 invariant 3 (no injection)**: `hasUnread` only
   returns a boolean. The runtime (v0.10.3) appends a string to the
   system prompt; §B does not do that.
4. **ADR-002**: the mailbox is IM-level. It does not leak into the
   shell. `IMLoopOptions.mailbox` is the only way the shell sees a
   mailbox reference, and the shell does not import it.
5. **ADR-016 §3.3**: the mailbox is shared across all agents. The
   factory (§C) passes the **same** `Mailbox` instance to all 3
   system agents, and the same instance is the working agent's
   `opts.mailbox`. The mailbox is one global queue; the `agentId`
   is the routing key.
6. **No persistence** (ADR-016 §2.3 lifecycle): the mailbox is
   in-memory. `Map` is re-initialised on every `runIMLoop` start.
   Cross-session messages go via the databus (tool-field projection
   is persistent in v0.10.2) or the state-line (curated memory is
   persistent in v0.10.2), not via the mailbox. §B does not need a
   `load` / `save` interface.

## 6. Variable catalog (what §B introduces vs uses)

### 6.1 Introduced

- `Mailbox` class — the queue store
- `MailItem` type — the wire shape
- `inboxes: Map<AgentId, MailItem[]>` — internal store
- `nextId: number` — monotonic id counter

### 6.2 Imports from elsewhere (consumes, does not redefine)

- `AgentId` from `src/im/databus.ts` (§A)
- `Date.now()` — wall clock; sufficient for FIFO ordering within a
  single process. If two sends in the same millisecond become a real
  concern, switch to `performance.now()` for `sentAt` and use `nextId`
  as the tiebreaker.

### 6.3 Not yet wired in §B (deferred to §C / v0.10.3)

- `mailbox_send` / `mailbox_read` tool wrappers — §C, registered to
  the working agent's `ToolRegistry`
- System-prompt-tail hint injection — v0.10.3 §4 step 3
- Cross-agent wiring (passing the same `Mailbox` to 4 agents) — §C
- `IMLoopOptions.mailbox` field — added by §C as a **required** field;
  §A leaves it optional (a v0.10.1 caller that does not use the
  mailbox can omit it)

**Privacy invariant is a compile-time test**: §B does not export a
`readInbox(agentId)` method. There is no test to write — the
absence of the method is the assertion. A future maintainer who
adds the method will have to think twice (the type system
will not stop them, but the absence will be conspicuous in code
review).
