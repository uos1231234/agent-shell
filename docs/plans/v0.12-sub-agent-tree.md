# v0.12 Plan — Hierarchical Sub-agent Tree (Codex-style Family Isolation)

> **Depends on**: HEAD `804896f` (v0.11.3 boundary alignment, 562 tests green). ADR-016 (information-flow architecture), ADR-017 (sub-agent Databus boundary + P2 hardening).
> **Blocks**: v0.12+ production hardening (cross-branch audit logging, per-family quotas, sub-agent metric aggregation).
> **Plan status**: implementation plan. Code changes must be approved before landing.
> **Scope**: replace the flat `SubAgentRegistry.sharedDatabus` with a per-parent family bus, introduce an `AgentTree` for parent/sibling identity, and enforce that mailbox+Databus visibility is limited to the same parent lineage.

---

## 0. Goal

Establish a **tree-structured sub-agent hierarchy** similar to OpenAI Codex:

- Every sub-agent instance has exactly one parent (the agent whose `run_subagent` call created it).
- A sub-agent can **directly communicate only with its parent** and **its own children**.
- Sub-agents that share the same parent (siblings) can **share a Databus** and **send mail to each other**.
- Sub-agents from different branches (cousins, uncles, nephews) are **strictly isolated**: they cannot see each other's Databus events and cannot exchange mail.

**Success criterion**: A working agent spawns two reviewer sub-agents. They can read each other's tool events and mail each other. A third sub-agent spawned from a different parent cannot read the reviewers' Databus and cannot mail them; any attempt is rejected at runtime.

## 1. Constraints

This section is N hard constraints from ADR-016/017, landed commits, and the user requirement.

1. **Two-bus projection/context separation remains.** The private projection bus (`loopOpts.databus`) and the contextual read bus (`loopOpts.ctxDatabus`) are structurally distinct. `[已验证: ADR-017 §3]`
2. **Tools read one bus.** `ToolContext.databus` is a single object (concrete `Databus` or `MultiDatabus`). No new `ToolContext` field is introduced for tree navigation. `[已验证: ADR-017 §2, §5 invariant 2]`
3. **Loop decides visibility.** Bus composition is resolved at `runIMLoop` construction time via `ctxDatabus`. Tools stay bus-blind. `[已验证: loop.ts:338-351]`
4. **No new guard / metric / config fields (ADR-015).** Sub-agents reuse the existing `ShellConfig` with optional overrides. `[已验证: config.ts POSITIVE_INT_FIELDS]`
5. **Sub-agents are strictly more constrained (P2).** All P2.1–P2.8 boundaries remain in force. New boundaries P2.9–P2.11 extend but do not relax this principle. `[已验证: ADR-017 §4]`
6. **System agents stay on the main chain.** The three ADR-016 system agents (warehouse/compressor/recall) do not participate in the sub-agent tree and are created without tree wiring. `[已验证: ADR-017 §3.3]`
7. **`define_subagent` defines templates, not instances.** `SubAgentConfig.name` remains a template name. Each `run_subagent` call mints a unique instance id under the tree. `[已读未验: 与当前 v0.11 行为一致，需用户确认]`
8. **Mailbox privacy invariant is preserved.** There is no `readInbox(agentId)` tool; agents can only read their own inbox. `[已验证: mailbox.ts:67]`
9. **No defense-in-depth layering.** One layer of tree-policy enforcement in `AgentTree` + `Mailbox`; verify via tests rather than adding redundant checks in every tool. `[来自 AGENTS.md §4]`
10. **Backward compatibility for non-tree callers.** Callers that do not opt into `AgentTree` continue to work with the v0.11 flat shared bus for one release cycle (deprecated, not removed). `[设计决策，待实现验证]`

## 3. Architecture

### 3.1 Information-flow diagram

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Root / Working Agent                          │
│  id = 'main' | depth = 0                                              │
│  ownDatabus     ← mainDatabus (private projection)                    │
│  familyDatabus  ← children share this bus                             │
│  ctxDatabus = [ownDatabus, familyDatabus]                             │
│         │ run_subagent('reviewer-a')                                  │
│         │ run_subagent('reviewer-b')                                  │
│         ▼                                                             │
│  ┌─────────────────────────────┐    ┌─────────────────────────────┐  │
│  │ Child A (reviewer-a-1)      │◄──►│ Child B (reviewer-b-1)      │  │
│  │ depth = 1                   │sib │ depth = 1                   │  │
│  │ ownDatabus = root.family    │lings│ ownDatabus = root.family   │  │
│  │ familyDatabus = new Databus │    │ familyDatabus = new Databus │  │
│  │ ctxDatabus = [own, parent.own]   │ ctxDatabus = [own, parent.own] │
│  └─────────────────────────────┘    └─────────────────────────────┘  │
│         │ run_subagent('worker')                                      │
│         ▼                                                             │
│  ┌─────────────────────────────┐                                      │
│  │ Grandchild A1 (worker-1)    │  CANNOT see cousin G2's bus          │
│  │ depth = 2                   │  CANNOT mail cousin G2               │
│  │ ownDatabus = A.familyDatabus│                                      │
│  │ ctxDatabus = [own, A.own]   │                                      │
│  └─────────────────────────────┘                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 AgentNode ownership table

| Field | Owner | Who writes | Who reads | Lifetime |
|---|---|---|---|---|
| `ownDatabus` | The agent's own loop | This agent's tool turns | This agent's siblings (via their `ownDatabus`), this agent's children (as their `ownDatabus`), parent (via `ctxDatabus`) | Session |
| `familyDatabus` | The agent's node | This agent's children | This agent's children, this agent itself (via `ctxDatabus`) | Session |
| `id` | AgentTree | Immutable | All tools (as `sourceAgentId` / `ctx.agentId`) | Session |
| `parent` / `children` | AgentTree | Immutable after creation | Mailbox router, tree queries | Session |

### 3.3 Visibility rules

For any agent node `N`:

- `loopOpts.databus = N.ownDatabus` — where `N`'s tool turns are projected.
- `loopOpts.ctxDatabus = [N.ownDatabus, N.parent.ownDatabus]` — what `N`'s tools can read.
  - Root has no parent, so `ctxDatabus = [root.ownDatabus, root.familyDatabus]`.
- Parent `P`'s tools read `ctxDatabus = [P.ownDatabus, P.familyDatabus]`, so `P` monitors all its children.
- Siblings read the same `N.ownDatabus` (because it equals `P.familyDatabus`), so they see each other.

### 3.4 Mailbox routing rules

`Mailbox.send` rejects any message where sender/recipient are not in the same direct lineage up to grandparent:

Allowed if:
- `from === to` (self-mail, useful for reminders).
- `from` is the parent of `to`.
- `to` is the parent of `from`.
- `from` is the grandparent of `to` (skip-generation).
- `to` is the grandparent of `from`.
- `from` and `to` share the same parent (siblings).

Rejected otherwise (cousins, uncles, nephews, great-grandparents, unrelated agents).

`Mailbox.systemSend` bypasses route checks (framework-internal only), but still obeys capacity limits P2.6.

## 4. Design Principles

1. **One tree, one source of truth.** `AgentTree` is the single authority for parent/sibling relationships. Both Databus composition and mailbox routing derive from it. No second copy of the hierarchy in `run-subagent.ts` or `Mailbox`.

2. **Parent owns the family bus.** The `familyDatabus` is created by the parent node and handed to its children as their `ownDatabus`. This makes "siblings share a bus" a mechanical consequence of tree construction, not a runtime merge rule.

3. **Instance id separates runs from templates.** `SubAgentConfig.name` is a template name; `run_subagent` mints a unique instance id (`<name>-<counter>`) so that repeated runs of the same template produce distinct tree nodes and distinct `sourceAgentId` values.

4. **Mailbox route check is opt-in by tree injection.** `Mailbox` works without an `AgentTree` (backward compat). When an `AgentTree` is injected, route checks activate. This avoids forcing every existing caller to construct a tree.

5. **No new `ToolContext` fields.** Tree navigation stays out of `ToolContext`. Agents see only their own `ctx.agentId`, `ctx.databus`, and `ctx.subAgentDepth`. The tree is invisible to tool implementations.

6. **Fail closed on missing tree nodes.** If `run_subagent` cannot find the current `ctx.agentId` in the tree, it throws. If a recipient is unknown to the tree, the mailbox rejects the message. Unknown agents are untrusted agents.

7. **Deprecated flat shared bus remains for one cycle.** `SubAgentRegistry.sharedDatabus` is kept as a fallback when `agentTree` is not bound, but new code uses the tree. This gives existing tests and callers a migration window.

### Not introduced (explicitly rejected)

- **No `ToolContext.tree` or `ToolContext.parentId`** — tree navigation is not a tool concern.
- **No `AgentNode.conversationMemory`** — each `SystemAgent.run()` still creates a fresh `ConversationMemory` per invocation.
- **No new guard types** — depth guard P2.3 still uses `subAgentDepth`; tree does not add guards.
- **No cross-session persistence of the tree** — tree is in-memory and session-scoped, same as Databus.
- **No dynamic tree reparenting** — once created, a node's parent is immutable.

## 7. Decisions

### 7.1 Already decided (with rationale)

| ID | Decision | Rationale |
|---|---|---|
| D1 | `AgentTree` is the single hierarchy source of truth | Prevents `Mailbox` and `run-subagent` from maintaining two copies of parent/child relationships. |
| D2 | Parent creates and owns `familyDatabus` | Sibling sharing becomes a mechanical consequence: all children receive the same `ownDatabus`. |
| D3 | `run_subagent` mints a unique UUID instance id per call | Repeated runs of the same template must produce distinguishable tree nodes and `sourceAgentId`s; UUID avoids leaking call order. |
| D4 | Child's `ctxDatabus = [child.ownDatabus, parent.ownDatabus]` | Child sees siblings (via `child.ownDatabus`) and parent context (via `parent.ownDatabus`). |
| D5 | Parent's `ctxDatabus = [parent.ownDatabus, parent.familyDatabus]` | Parent monitors its own history plus all children. |
| D6 | `Mailbox` route check is opt-in by tree injection; when active, allow parent/child and grandparent/grandchild (skip-generation) mail | Preserves backward compatibility; skip-generation lets a child escalate to grandparent while still blocking cousins/uncles. |
| D7 | `systemSend` bypasses route checks | Framework-internal senders (drive-coordinator, databus_subscribe bridge) must remain functional. |
| D8 | `define_subagent` remains a template definition | Keeps the existing declarative config model; instances are created at `run_subagent` time. |
| D9 | Flat `sharedDatabus` is deprecated, not deleted | One-release migration window for existing callers and tests. |

### 7.2 Resolved by user

| Question | User choice | Rationale |
|---|---|---|
| Skip-generation mail to grandparent? | **Yes, but only to grandparent** | Allows escalation while keeping the boundary tight (no great-grandparent, no cousins). |
| Instance id format? | **UUID** | Globally unique and does not leak call order; `crypto.randomUUID()` from Node built-ins. |

### 7.3 Remaining undecided

| Question | Options | Default if not asked |
|---|---|---|
| Should the root working agent be able to see its grandchildren directly (via ctxDatabus)? | Yes (include all descendants in root.ctxDatabus) / No (only children) | No — root sees only children; grandchildren are visible via their parents' family buses if needed. |
| Should self-mail (`from === to`) be allowed? | Yes / No | Yes — useful for agent self-notes. |
