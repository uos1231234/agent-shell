## 0. Goal

[已验证 against current source] The current implementation has two independent stores: `ConversationMemory` accepts only `user`/`assistant`, while `Databus` accepts only `tool`. `loop.ts` then appends all conversation turns followed by Databus turns, which can place `tool` results after later assistant messages and break OpenAI tool-call pairing.

[用户已确认的目标] Make the working conversation a **single canonical ordered sequence** containing every `user`, `assistant`, and `tool` turn in exact append order. Databus becomes a **tool-only projection copy** of that canonical sequence for cross-agent query/subscribe. It is not a second source for reconstructing the working prompt.

v0.10.4 then completes the auto-drive around that canonical sequence:

1. At the M0/M1 boundary (>=200K), find one complete task block deterministically: one `role:'user'` turn through the turn immediately before the next `role:'user'` turn, containing every intermediate assistant and tool turn. The block is eligible only when it contains at least one `role:'tool'` turn.
2. Pass that already ordered block directly as `SystemAgent.run({ messages })`. Do not re-query Databus, sort by timestamp, join by `toolCallId`, or ask the LLM to discover the boundary.
3. After the compressor successfully persists the record, evict that exact range from the canonical sequence and evict the exact projected tool ids from Databus.
4. At the M2/M3 boundary (>=900K), the warehouse agent archives curated M1/M2 blocks as already decided in the preceding plan. M3 content remains email/recall-only.

**Success criterion**: A captured protocol request always has the normal OpenAI order `user -> assistant(tool_calls) -> tool -> assistant -> ...`; a scripted crossing compresses only a complete user-to-next-user span that contains a tool turn; the compressor receives that exact `ChatMessage[]`; successful persistence removes the same block from canonical memory and its Databus projections; failed persistence leaves both untouched.

## 1. Constraints

This section contains the hard constraints from ADR-016, landed commits, and the user-confirmed correction. The implementation must not reinterpret them.

1. **Canonical sequence is the only ordering authority.** `ConversationMemory` is retained as the existing public name, but its stored sequence becomes `user | assistant | tool` in the exact order in which turns were appended. No timestamp sort, array merge, or `toolCallId`-based reconstruction is allowed for working context or task-block delivery.
2. **Databus is a projection, not a second history.** For every working/system-agent `role:'tool'` appended to canonical conversation, the runtime writes a structurally equivalent tool-only copy to Databus. Databus remains cross-agent readable and tool-only. It never owns user/assistant turns and never supplies a duplicate tool message to the working prompt.
3. **One write path for tool turns.** Production loop code must use one named helper for canonical append plus Databus projection. Do not leave two unrelated `append()` calls at call sites where one can be forgotten or reordered. User/assistant input may be seeded into canonical memory directly; tool results always use the projection helper.
4. **Protocol order is non-negotiable.** The working prompt and every system-agent prompt must be built from the canonical sequence, translated with `turnToMessage`, and passed to `compose()` in that order. An assistant message with `tool_calls` must be followed by its tool result(s) before a later assistant message.
5. **Task-block boundary is deterministic and user-anchored.** A candidate starts at a `role:'user'` turn and ends immediately before the next `role:'user'` turn. It includes every canonical turn in that interval. The driver does not ask the LLM to find the boundary.
6. **Tool-turn eligibility is required.** A user-to-next-user span with no `role:'tool'` turn is not a compression block for this drive. `findNextTaskBlock` must continue scanning for the next complete eligible span instead of inventing a boundary from assistant text or token count.
7. **Pairing validation precedes delivery and eviction.** A candidate is eligible only if its internal sequence has no leading tool, no tool without a preceding matching assistant `tool_call`, and no assistant `tool_call` without its required tool result. The canonical sequence is the source used for this validation.
8. **Compress then evict.** The driver passes the exact block to the compressor first. It evicts only after the record tool reports successful persistence. Any failure sends a mailbox notice and leaves canonical memory and Databus projection copies unchanged.
9. **Eviction uses canonical range and exact projection ids.** Never infer the Databus deletion boundary from `at`, and never use `evictOlderThan()`. The block range is found in canonical memory; the removed tool-turn ids are then removed from Databus.
10. **M1/M2/M3 trigger policy remains the prior user decision.** >=200K starts the compression drive; 500K is not a third crossing; >=900K starts archive. M1/M2 schema slack remains. The existing M2 policy of summarizing earlier curated M1 material is not redesigned by this storage correction.
11. **M3 remains non-injected.** M3 summaries are persisted and announced through mailbox/recall. They are not appended to the canonical working prompt or state-line projection at M3.
12. **System agents keep private stores.** A system agent receives the delivered `ChatMessage[]` as input, seeds its own canonical conversation in that exact order, and projects only input `role:'tool'` messages to its private Databus. No shared system-agent history is introduced.
13. **No free-text structured-output parser.** Record tools remain the structured-output boundary. The compressor/warehouse provide schema arguments through tool calls.
14. **No new guard, metric, or ShellConfig field.** Existing guards, `MAX_CONCURRENT_TOOL_CALLS = 2`, mailbox, StateLine, and SignalBus semantics remain. The obsolete working-prompt use of `databusMaxTurnsByLayer` is removed rather than left as an unused field. The pre-existing `conversationMaxTokens` field is outside this plan: do not wire it or remove it here; keep its ADR-015 debt explicitly tracked.
15. **No shell/protocol business logic.** `compose.ts` remains a generic ordered `PromptPart[] -> FinalPrompt` mapper. The canonical ordering logic belongs in `src/im/`.
16. **Historical commits are not rewritten.** v0.10.3/v0.10.3.1 records remain historical. v0.10.4 explicitly fixes the currently landed prompt-assembly defect; it does not pretend the old implementation already had the new invariant.

## 3. Architecture

### 3.1 Canonical sequence and Databus projection

```text
caller seeds user turn
          |
          v
+--------------------------------------------------------------+
| ConversationMemory = canonical ordered conversation          |
| user -> assistant(tool_calls) -> tool -> assistant -> ...    |
+--------------------------------------------------------------+
          |
          | appendCanonicalTurn(memory, databus, toolTurn)
          | (one structural copy, same tool id/content/source/at)
          v
+--------------------------------------------------------------+
| Databus = role:'tool' projection only                         |
| cross-agent query / subscribe / audit; never prompt history   |
+--------------------------------------------------------------+

working prompt:
  canonical ConversationMemory -> turnToMessage -> compose -> protocol

cross-agent tools:
  Databus query/subscribe -> warehouse/recall callers
```

The canonical sequence is not a fourth information flow. It is the working agent's authoritative conversation log. Databus remains the cross-agent tool-field projection described by ADR-016. The critical rule is ownership: canonical memory owns order; Databus owns a readable tool projection.

### 3.2 Protocol-safe prompt assembly

```text
system + userTemplate + state-line system part + tool definitions
  + canonical turn parts in exact append order
  -> compose()
  -> FinalPrompt.messages
  -> streamChat()
```

`projection.databusTurns` is removed from this path. A tool turn is already present in canonical memory; adding its Databus copy would duplicate it. `context-projection.ts` continues to decide M1/M2 StateLine blocks, mailbox hint, and M3 overflow text only.

A normal multi-step sequence is therefore:

```text
user
assistant(tool_calls=[tc-1])
tool(tool_call_id=tc-1)
assistant(tool_calls=[tc-2])
tool(tool_call_id=tc-2)
assistant(final text)
```

The ordering comes from append order, not from equal `at` values. `at` remains metadata for filtering/audit, never the ordering key.

### 3.3 Deterministic task-block extraction

```text
canonical turns
   |
   +-- scan from first/next user turn
   |
   +-- find the next user turn as exclusive boundary
   |
   +-- inspect every turn in the span
   |      - require at least one tool turn
   |      - validate tool-call/result pairing
   |
   +-- return the exact canonical slice as ChatMessage[]
        (user -> assistant(+tool_calls) -> tool -> ...)
```

`findNextTaskBlock()` returns no block when the next user boundary has not arrived, when the span has no tool turns, or when pairing is invalid. It does not use token count to cut a block. It does not read Databus to fill missing turns.

One successful compression dispatch removes that exact canonical range. The removed tool-turn ids are supplied to Databus exact-id eviction. Because the range came from the canonical sequence and pairing was checked before delivery, no surviving sequence can begin with a tool or retain an assistant tool call without its result.

### 3.4 Auto-drive closed loop

```text
runIMLoop round
   |
   +-- build canonical-only prompt and call working LLM
   +-- append assistant to canonical sequence
   +-- execute tools in existing batches
   |     +-- append each tool to canonical sequence
   |     +-- project each tool to Databus
   |
   +-- tick({ contextTokens, conversation, databus }) [fire-and-forget]
             |
             +-- classify layer / edge and find one eligible block
             +-- compressor.run({ messages: block.messages, metadata })
             +-- compressor calls record_curated_block
             +-- on success: evict canonical range, then exact Databus ids
             +-- on failure: mailbox notice, no eviction

>=900K archive edge
   +-- warehouse receives curated M1/M2 input
   +-- record_m3_summary -> StateLine warehouse slot
   +-- mailbox pointer to working agent
   +-- curated blocks remain on disk; M3 is not injected
```

### 3.5 System-agent input boundary

The driver passes the canonical slice as `SystemAgent.run({ messages })`. `system-agent.ts` maps all four protocol message roles. It seeds user/assistant/tool input into the private canonical sequence in the same order; tool input also gets copied to the private Databus. The inner system-agent loop then builds its own prompt from that private canonical sequence only.

## 4. Design principles

1. **One canonical order, one projection.** The full conversation is stored once as the authoritative sequence. Databus copies only tool entries for cross-agent visibility; no consumer reconstructs order from the projection.
2. **Append order beats timestamp order.** Multiple tool results intentionally share a timestamp in the current loop. Their canonical array position is the only stable protocol order.
3. **Cut by users, qualify by tools.** User turns provide the robust task boundary. A block is compressible only when that boundary is complete and the span contains tool work.
4. **Pass the slice, do not serialize a reconstruction.** The compressor receives the exact `ChatMessage[]` slice that the canonical prompt builder would produce. There is no JSON blob containing duplicated or partial turns.
5. **Persistence before deletion.** The record tool is the commit point. Canonical and projection data remain available on all failure paths.
6. **Exact-range eviction.** Eviction consumes the canonical range and its exact tool ids. It never guesses from timestamps, recent-window caps, or tool-call ownership inferred after the fact.
7. **Projection remains pull-only.** StateLine/mailbox projection is built per round. Databus query/subscribe is for explicit cross-agent use, not a second working-prompt injection path.

## 5. Module guidance

Public APIs are listed as signatures. Implementations must follow the constraints above; do not add fallback layers or alternative ordering paths.

### 5.1 `src/im/conversation-memory.ts` — canonical ordered sequence

```ts
import type { ToolTurn } from './databus.js'

export type ConversationTurn =
  | { id: string; role: 'user'; content: string; at: number }
  | { id: string; role: 'assistant'; content: string | null; toolCalls?: ToolCall[]; at: number }
  | ToolTurn

export class ConversationMemory {
  append(turn: ConversationTurn): void
  turns(): readonly ConversationTurn[]
  last(): ConversationTurn | undefined
  evictRange(startIndex: number, endIndexExclusive: number): readonly ConversationTurn[]
}
```

`turns()` is the canonical order. `evictRange()` removes exactly the half-open range and returns the removed turns so the coordinator can derive the exact projected tool ids. It must not silently remove a neighboring user turn or leave the canonical array with an orphaned tool sequence.

### 5.2 `src/im/databus.ts` — exact projection eviction

```ts
export class Databus {
  append(turn: ToolTurn): void
  turns(): readonly ToolTurn[]
  query(filter?): readonly ToolTurn[]
  subscribe(...): () => void
  evictByIds(ids: readonly string[]): number
}
```

`evictByIds()` removes only projection entries whose `id` is in `ids`. It does not use `at`, `toolCallId`, `limit`, or subscriber callbacks to infer a range. Existing `append()` remains a low-level tool-projection operation; production working/system-agent tool writes go through the canonical append helper below.

### 5.3 `src/im/turn.ts` — one projection write path and one converter

```ts
export type Turn = ConversationTurn | ToolTurn

export const turnToMessage: (turn: Turn) => ChatMessage

export function appendCanonicalTurn(
  conversation: ConversationMemory,
  databus: Databus,
  turn: ConversationTurn,
): void
```

`appendCanonicalTurn()` always appends `turn` to `conversation`; when `turn.role === 'tool'`, it appends a structural copy of that same tool turn to `databus`. It never adds user/assistant to Databus. All production tool-result call sites use this helper. Remove or redirect `conversationTurnToMessage()` so there is no second converter that silently excludes tool turns.

### 5.4 `src/im/context-projection.ts` — StateLine/mailbox only

Remove `databusMaxTurnsByLayer` and `databusTurns` from this working-prompt projection contract. Keep M0/M1/M2/M3 classification, StateLine selection, mailbox unread hint, and M3 overflow suffix. Do not consume or delete the existing `conversationMaxTokens` field in this plan; record it as a separate ADR-015 decision debt.

### 5.5 `src/im/loop.ts` — canonical assembly and writes

- Build `conversationTurns = opts.conversationMemory.turns()` once per round.
- Map those turns with `turnToMessage` into `turn` parts. Do not append `projection.databusTurns`.
- Keep StateLine part placement after `userTemplate` and before tool references.
- Append the assistant response to canonical memory.
- For every tool result, call `appendCanonicalTurn(opts.conversationMemory, opts.databus, toolTurn)` in the existing input order returned by `executeToolCalls`.
- Add optional `driveCoordinator?: DriveCoordinator` if it is not already present. At the end of a round, call `void opts.driveCoordinator?.tick({ contextTokens: estimatedTokens, conversation: opts.conversationMemory, databus: opts.databus })`; never await the background drive in the working request path.
- Keep guard evaluation and tool concurrency behavior unchanged.

### 5.6 `src/im/system-agents/drive-coordinator.ts` — deterministic selector and coordinator

```ts
export type TaskBlock = {
  startIndex: number
  endIndexExclusive: number
  startUserTurnId: string
  boundaryUserTurnId: string
  turns: readonly ConversationTurn[]
  messages: readonly ChatMessage[]
  toolTurnIds: readonly string[]
}

export function findNextTaskBlock(
  turns: readonly ConversationTurn[],
  fromIndex?: number,
): TaskBlock | undefined

export type DriveSnapshot = {
  contextTokens: number
  conversation: ConversationMemory
  databus: Databus
}

export type DriveCoordinator = {
  tick(snapshot: DriveSnapshot): Promise<void>
  stop(): void
}

export type DriveDeps = {
  bus: SignalBus
  compressor: SystemAgent
  warehouse: SystemAgent
  stateLine: StateLine
  mailbox: Mailbox
  workingAgentId: AgentId
}

export function createDriveCoordinator(deps: DriveDeps): DriveCoordinator
export function createNoopDriveCoordinator(): DriveCoordinator
```

`findNextTaskBlock()` scans canonical turns for a user start and the next user boundary. It returns the first complete span that contains at least one tool turn and passes pairing validation. It maps the returned canonical slice directly with `turnToMessage`; there is no `nextBlockBoundary()` returning separate conversation/tool arrays and no `blockToChatMessages()` reconstruction helper.

The coordinator must:

- Track the last classified layer, one in-flight block key, and retry/availability state; do not track a shifting `coveredUserTurnIndex`.
- Dispatch at most one complete eligible block per compression run.
- Pass `block.messages` directly to `compressor.run({ messages: [...block.messages], metadata: { kind: 'compress', zone } })`.
- On successful record-tool completion, call `conversation.evictRange(block.startIndex, block.endIndexExclusive)` and then `databus.evictByIds(block.toolTurnIds)`. Verify that the removed tool ids are the expected ids; do not recompute a timestamp boundary.
- On failure, send a mailbox note and leave both stores unchanged. A retry must reuse a newly observed canonical block, not a second concurrent dispatch of the same block.
- Preserve the prior M2 policy: in the M2 zone, the compressor may summarize earlier persisted M1 curated material according to the existing plan; this does not authorize a second raw-turn reconstruction path.
- At M3, pass curated/archive input to the warehouse, persist through `record_m3_summary`, notify the working agent, and leave curated blocks on disk.

File-local pairing validation must inspect the canonical slice before `SystemAgent.run()`. It must reject a leading tool, a tool whose `tool_call_id` is not outstanding from an earlier assistant tool call, and an assistant tool call that remains outstanding at the end of the slice.

## 7. Decisions

### 7.1 Resolved by user / existing contract

| Decision | Basis |
|---|---|
| Canonical full sequence contains user, assistant, and tool turns in exact append order | User correction in this session; required to avoid split-store protocol hazards |
| Databus contains a copy of every canonical tool turn and remains tool-only | ADR-016 Databus role boundary, clarified by the user in this session |
| Working prompt reads canonical sequence only; Databus is not appended again | Prevents duplicate tool messages and restores normal OpenAI message order |
| Task block = one user turn through just before the next user turn | Existing 参考实现 task-block definition and the prior v0.10.4 decision |
| A compressible block must contain at least one tool turn | User clarification in this session |
| Block extraction is deterministic code, not LLM boundary judgment | Robust user-message anchor; prior v0.10.4 decision |
| Compressor receives the exact pre-cut `ChatMessage[]` slice | User clarification in this session and `SystemAgent.run({messages})` contract |
| Eviction occurs only after successful persistence | Prior v0.10.4 decision; no data loss on failure |
| M1/M2/M3 thresholds and M3 retention policy remain unchanged | ADR-016 and prior v0.10.4 decisions |

### 7.2 Implementation decisions for GLM 5.2

1. **Retain `ConversationMemory` as the canonical store instead of introducing `ConversationLedger`.** This preserves the existing public surface while correcting its role. Its union expands to include `ToolTurn`.
2. **Use `appendCanonicalTurn(conversation, databus, turn)` as the sole production tool-result write path.** This is the smallest abstraction that makes the projection invariant visible and testable without adding a fourth store.
3. **Use canonical half-open ranges plus exact tool ids for eviction.** This avoids unstable timestamps and prevents Databus from guessing which projection entries belong to a task block.
4. **Remove `databusMaxTurnsByLayer` from working-prompt projection.** Once canonical memory already contains tool turns, keeping that cap in the projection would either duplicate messages or create a second partial history. The existing `conversationMaxTokens` field is deliberately left untouched for a separate decision.
5. **Keep `compose.ts` unchanged.** It already preserves ordered turn parts; the defect is in IM storage/assembly, not in the shell mapper.
6. **Treat the current v0.10.3/v0.10.3.1 split assembly as a known correctness bug.** The v0.10.4 implementation must add a protocol-capture regression test before claiming completion.
7. **Preserve the prior M2 semantic decision.** This plan changes the raw task-block transport and storage invariant; it does not silently change what M2 summarizes.

### 7.3 Open decisions

None for this implementation plan. `conversationMaxTokens` remains a separately tracked ADR-015 tension and is explicitly out of scope.
