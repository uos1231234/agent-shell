## 0. What this piece does

Build the `createSystemAgent` factory that turns a `systemPrompt` +
`toolRefs` + `llmStreamChat` into a `runIMLoop`-shaped instance. Wire
the 3 concrete system agents (warehouse / compressor / recall) into
the working agent's `ToolRegistry` via 7 new tool wrappers. Make
`runIMLoop` aware of the 3 system agents so the working agent can
call them as if they were tools.

## 1. Module: `src/im/system-agent.ts` (NEW)

### 1.1 Public surface

```ts
import type { AgentId } from './databus.js'
import type { Metrics, State } from '../shell/metrics.js'  // re-export State from state.ts in the same module
import type { StreamChunk, ChatMessage } from '../protocol/types.js'
import type { ToolRegistry } from '../shell/registry.js'

export type SystemAgent = {
  run(input: { messages: ChatMessage[]; metadata?: Record<string, unknown> }): Promise<{
    output: unknown
    metrics: Metrics
    finalState: State
  }>
  stop(): void
  send(message: ChatMessage): void
}

export const createSystemAgent = (opts: {
  name: AgentId
  systemPrompt: string
  toolRefs: readonly string[]
  llmStreamChat: (url: string, request: { model: string; messages: ChatMessage[]; tools: unknown[]; [k: string]: unknown }) => AsyncIterable<StreamChunk>
  url: string
  model: string
  initialMetrics?: Metrics
}): SystemAgent => { ... }
```

### 1.2 Internal design

`createSystemAgent` returns a `SystemAgent` that wraps a private
`runIMLoop` instance. The wrapping is the **only** new logic; everything
else is `runIMLoop` reuse.

**Storage inside the closure**:

- A `Mailbox` (the agent's own inbox reference; the global mailbox is
  passed in via a side channel — see §3)
- A `Databus` (the agent's own databus, separate from the working
  agent's, with `sourceAgentId = opts.name` stamped on every append)
- A `ConversationMemory` (the agent's own LLM session memory — never
  shared, by §A's invariant)
- The `toolRefs` filtered through the working agent's `ToolRegistry`
  to build the agent's private tool list
- The `state: State`, `metrics: Metrics`, `turns: number` of the inner
  loop

**`run(input)` semantics**:

1. Reset the agent's `ConversationMemory` to start with `input.messages`
   (or append them to the existing memory if the caller has been
   streaming).
2. Call the inner `runIMLoop` with:
   - `systemPrompt: opts.systemPrompt`
   - `userTemplate: ''` (system agents have no user template)
   - `databus: thisAgentDatabus` (separate from working agent's)
   - `conversationMemory: thisAgentConvMem` (private)
   - `workingAgentId: opts.name` (the system agent's own id)
   - `mailbox: sharedMailbox` (the global one)
   - `systemToolRefs: opts.toolRefs`
3. Return `{ output, metrics, finalState }` from the inner loop's result.

**`stop()`**: sets a flag the inner loop checks at the top of each
round. Same mechanism as a future v0.10 implementation, not introduced
here.

**`send(message)`**: appends a `role: 'user'` `ConversationTurn` to the
agent's `ConversationMemory`. The next `run` call sees it. This is the
"interact with a running system agent" hook (e.g. for the recall agent
to receive a follow-up question).

### 1.3 Why the inner `runIMLoop` is a private field, not a returned object

The factory is the only API the caller sees. Returning the inner
`runIMLoop` would leak the working agent's `Databus` / `ConversationMemory`
/ `Mailbox` into the system agent's signature — a cross-agent privacy
violation. The `SystemAgent` interface is the **firewall**.

## 2. Module: `src/im/system-agents/index.ts` (NEW) — 3 concrete instantiations

### 2.1 The 3 imports (already exist as .md files)

```ts
import { WAREHOUSE_AGENT_PROMPT, COMPRESSOR_AGENT_PROMPT, RECALL_AGENT_PROMPT } from '../prompts/index.js'
```

### 2.2 The factory invocations (ADR-016 §3.3 locks the order)

```ts
export const createSystemAgents = (deps: {
  llmStreamChat: SystemAgent['run'] extends never ? never : (
    url: string,
    request: { model: string; messages: ChatMessage[]; tools: unknown[]; [k: string]: unknown }
  ) => AsyncIterable<StreamChunk>
  url: string
  model: string
  mailbox: Mailbox
}): {
  warehouse: SystemAgent
  compressor: SystemAgent
  recall: SystemAgent
} => ({
  warehouse: createSystemAgent({
    name: 'warehouse',
    systemPrompt: WAREHOUSE_AGENT_PROMPT,
    toolRefs: ['databus_query', 'databus_subscribe', 'mailbox_send', 'mailbox_read'],
    llmStreamChat: deps.llmStreamChat,
    url: deps.url,
    model: deps.model,
  }),
  compressor: createSystemAgent({
    name: 'compressor',
    systemPrompt: COMPRESSOR_AGENT_PROMPT,
    toolRefs: ['databus_query', 'state_query', 'mailbox_send', 'mailbox_read'],
    llmStreamChat: deps.llmStreamChat,
    url: deps.url,
    model: deps.model,
  }),
  recall: createSystemAgent({
    name: 'recall',
    systemPrompt: RECALL_AGENT_PROMPT,
    toolRefs: ['databus_query', 'state_query', 'mailbox_send', 'mailbox_read'],
    llmStreamChat: deps.llmStreamChat,
    url: deps.url,
    model: deps.model,
  }),
})
```

The `mailbox` parameter is the **shared** mailbox; each agent's
`createSystemAgent` receives it directly in the factory signature.

## 4. The 7 new tool wrappers (NEW files in `src/im/tools/`)

Each tool wrapper is a small file that:

1. Defines the tool's `parameters: JSONSchema` (per ADR-016 §3.4's
   table)
2. Implements `execute(args, ctx)` where `ctx` is a new context type
   that the working agent's `ToolRegistry` provides at execution time
3. Returns a `role: 'tool'`-friendly result (string or object)

### 4.1 The 7 files

| File | Tool | System agent that backs it | v0.10.1 status |
|---|---|---|---|
| `databus-query.ts` | `databus_query` | warehouse | Real impl. `execute` calls `warehouse.run({ messages: [{role:'user', content: JSON.stringify(args)}], metadata: { kind: 'databus_query' } })` |
| `databus-subscribe.ts` | `databus_subscribe` | warehouse | Real impl. Returns the unsubscribe handle. |
| `state-query.ts` | `state_query` | warehouse | **Stub**. `execute` calls `warehouse.run(...)` and the warehouse agent's system prompt tells it the `state_query` semantics — but v0.10.1 has no `StateLine` yet, so the warehouse will report "no state available". This is by design; the real impl lands in v0.10.2. |
| `compress-block.ts` | `compress_block` | compressor | Real impl. Calls `compressor.run(...)` with the `block` arg. The compressor's 11-field schema is enforced by its own inner loop. |
| `ask-recall.ts` | `ask_recall` | recall | Real impl. Calls `recall.run(...)` with `{query, scope, limit}`. |
| `mailbox-send.ts` | `mailbox_send` | (direct API) | Real impl. Reads `ctx.mailbox` (passed via the new `IMLoopOptions.mailbox` field), calls `mailbox.send(...)`. |
| `mailbox-read.ts` | `mailbox_read` | (direct API) | Real impl. Same. |

### 4.2 The new `ToolContext` type (NOT ADOPTED in v0.10.1)

> **v0.10.1 revision**: The `ToolContext` type and the
> `ToolRegistry.execute(name, args, ctx?)` signature change were **not
> implemented**. Instead, the 7 new tools capture their dependencies
> (SystemAgent handles, Mailbox, workingAgentId) via closures at
> construction time. `ToolRegistry.execute` remains `(name, args)`.
> The 8 v0.9 tools are untouched. This section is retained for design
> history only.

`ToolRegistry.execute(name, args)` currently takes only `(name, args)`.
v0.10.1 changes the signature to `(name, args, ctx?: ToolContext)`:

```ts
export type ToolContext = {
  mailbox: Mailbox          // the working agent's mailbox reference
  workingAgentId: AgentId
  systemAgents: {
    warehouse: SystemAgent
    compressor: SystemAgent
    recall: SystemAgent
  }
}
```

`ToolRegistry.execute` passes `ctx` through to the tool's `execute`
function. The 8 v0.9 system tools (`read` / `write` / `edit` / etc.)
do not read `ctx`; they continue to work with `(args)` only. The
`ctx` parameter is **optional** with a default of `{}` so existing
callers do not break.

**Why pass `ctx` to tools**: the `mailbox_send` and `mailbox_read`
tools need a mailbox reference; the system-agent-backed tools need
the 3 `SystemAgent` handles. The `ToolRegistry` is the natural
junction — it is the only place the working agent's runtime context
flows into a tool call.

### 4.3 Tool argument shape (ADR-016 §3.4 verbatim)

The 7 tools' `parameters: JSONSchema` are exactly as ADR-016 §3.4
specifies. The `description` field on each tool is the same description
used in the system-agent prompt files (so the model sees consistent
language between the system prompt and the tool schema). This is a
**content** consistency check, not a type one — the plan lists the
descriptions in the system prompt files (already done) and the tool
files must mirror them.

## 5. Module: `src/im/system-agents/register.ts` (NEW) — the wiring

```ts
export const registerSystemAgentTools = (registry: ToolRegistry, mailbox: Mailbox, workingAgentId: AgentId, systemAgents: { warehouse, compressor, recall }): void => {
  registry.registerSystemTool(createDatabusQueryTool(systemAgents.warehouse))
  registry.registerSystemTool(createDatabusSubscribeTool(systemAgents.warehouse))
  registry.registerSystemTool(createStateQueryTool(systemAgents.warehouse))
  registry.registerSystemTool(createCompressBlockTool(systemAgents.compressor))
  registry.registerSystemTool(createAskRecallTool(systemAgents.recall))
  registry.registerSystemTool(createMailboxSendTool())
  registry.registerSystemTool(createMailboxReadTool())
}
```

This is the **single entry point** an application uses to wire the
v0.10.1 tool surface. Combined with `createBuiltinTools({cwd})` from
v0.9, the application ends up with a `ToolRegistry` containing 15
tools (8 v0.9 + 7 v0.10).

## 7. Existing constraints (do not violate)

1. **ADR-002**: shell is pure. The factory wraps `runIMLoop`; the
   shell's surface is unchanged.
2. **ADR-003**: shell has no business fields. `ToolContext.mailbox`
   is a tool-level context, not a shell field. It is constructed by
   the IM (`runIMLoop`) at the call site of `registry.execute`.
3. **ADR-005**: tools are registered at startup, not hot-plugged. The
   7 new tools are registered in `registerSystemAgentTools`, which is
   called at app startup, not inside `runIMLoop`.
4. **ADR-016 §3.3**: factory signature is exactly `{ name, systemPrompt,
   toolRefs, llmStreamChat, initialMetrics }`. The mailbox injection
   happens via the module-level default (§3), not via a new parameter.
5. **ADR-016 §3.4**: the 7 tool names and I/O shapes are exactly as
   specified. The tool wrappers in this plan do not invent new names.
6. **ADR-013**: every tool's `execute` validates its own contract and
   returns a plain-English sentence on failure. The 7 new tool wrappers
   follow the same `wrap()` helper pattern as `tools/index.ts`.
