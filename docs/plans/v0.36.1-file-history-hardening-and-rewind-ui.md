## 0. 问题核实结论（哪些属实、哪些言过其实）

### P0-1 并发写竞态 —— **属实，但严重性需要修正表述**

**实测**（python 模拟 append 与 read-modify-rewrite 交错，200 轮 × 10 并发 append + 1 次 rewrite 插入）：
- **丢失确实存在：共丢 16 条**（0.8% 概率，仅在线程真实并行时）。
- **但 Node 是单线程事件循环**，`appendFile` 与 `writeIndex` 各自是原子-ish 的异步调用，交错点只在 await 边界。真实窗口比线程模型小得多——两个子代理的并发测试（50 并发 burst）全绿与此一致。
- **Windows 特有放大**：实测 200 次 rewrite **全部报错**（rename 目标被 append 句柄占用时 Windows 拒绝替换，POSIX 无此问题）。Node 的 `fs.rename` 在此场景下同样可能 EPERM——但这被 `prune()` 外层 catch 吞掉，表现为 **prune 静默失败**（不丢数据，但不回收）。
- **判定**：丢记录概率低但**机制真实存在**（writeIndex 的 read→rename 之间 append 到旧 inode）；Windows 上更可能的表现是 prune 静默失败而非丢数据。**串行化是对的**（用户已拍板），一并消除两个表现。

### P0-2 静默失败零观测 —— **属实**
`file-history.ts:349-352` catch 空块，无任何日志。prune 失败（上面 Windows 场景）也被同一个 catch 吞。加 logger.warn 即可。

### P1-1 shell 只读命令也快照 —— **属实**
`recordShellCommand`（file-history.ts:298-303）对命令里**任何**候选路径调 recordInner，`grep foo.ts` / `cat bar.md` 也留底。危害：污染 rewind 语义（可能把文件还原到比预期更早的版本）+ 白占配额。

### P1-2 白名单外文件被改零提示 —— **属实，且比子代理说的更准的定性**
search_replace 的 walk 不看扩展名（search-replace.ts:152-185），会真实改写 `.docx`；record 按白名单静默跳过（file-history.ts:309）→ 文件被改坏但 rewind 报"无记录"，用户不知道"这个文件本来就不受保护"。**定性：不是分类错误，是设计边界没有传达给用户**——修法是把边界显性化，不是扩大保护范围（保护范围是用户 2026-09-11 拍板的，不动）。

### registry.fileHistory（index.ts:295）—— **确认死代码**
全 src 只有写入（index.ts:295 一行），**零读取**——生产链路回滚走 assembly.ts:513-514 的构造注入（SessionAssets.fileHistory），不经过 registry 挂载。它是我在工具层图方便加的"便利出口"，实际没人用。**处置：删除**（违反 ADR-015 无死代码）。连带影响：file-history-integration.test.ts 里两处通过 registry 取实例的测试要改成从注入路径取（改为 createBuiltinTools({fileHistory: 外部实例}) 再用外部实例引用）。

### 子代理报告里言过其实/需修正的部分
- "50 并发全绿只能说明窗口小" —— 对，但结合 Node 单线程事实，实际丢失面比它暗示的小；真正的高频问题是 Windows prune 静默失败。
- "rewind 中途崩溃会不一致" —— 静态审查自己已纠正：索引删除在还原循环**之后**（file-history.ts:426），中途崩只是记录还在、可重试，无部分回滚窗口。**不修**。
- "prune 跨会话互踩（会话 A 踢会话 B）" —— 机制属实，但配额本来就是全局资源语义（对标 mimo-codex MAX_SNAPSHOTS=100 也是全局），且 2000 条上限下很难触发。**降级为 P2，本轮不修**，只在计划文档记录。
- "unbacked 条目被删索引 → 超限文件永久不可撤" —— 属实但无意义：超限文件本来就没有内容副本，留着记录也不能还原。**不修**。

## 1. 代码修复（P0-1 / P0-2 / P1-1 / P1-2 / 死代码）

### 1.1 P0-1：索引操作串行化（per-instance Promise 队列）

**位置**：`src/im/tools/file-history.ts`

**做法**：实例内加一个 `withIndexLock<T>(fn: () => Promise<T>): Promise<T>`——链式 Promise 队列（同 edit.ts withFileLock 思路，但**不需要**跨实例文件锁：实例是 per-session 的，同一实例内串行即可）。以下操作全部过锁：
- `recordInner` 的**索引写入部分**（appendIndex / 新建记录 append）——对象压缩等慢 IO 不必占锁，只锁"读-判-写索引"这段
- `prune`（readIndex → writeIndex → sweepObjects 整体）
- `rewind`（readIndex → 还原 → writeIndex 整体——还原文件本身的 IO 在锁内做，保证"读到的索引 ⇔ 还原动作 ⇔ 删记录"原子）

**不做**：跨进程文件锁（flock/lockfile）——当前是单进程多实例，跨实例冲突（两个会话同 workDir）窗口极小且后果只是少一条快照记录，不破坏一致性。若未来上多进程，再立 lockfile 项目。

**回归测试**：改造 `file-history-concurrency.test.ts` 的第三条断言——从 `≤20` 改为**精确断言零丢失**（并发 burst 后条数必须等于 maxEntries 或恰好记录数，不允许"少了几条但没坏"）。

### 1.2 P0-2：静默失败可观测

**位置**：`src/im/tools/file-history.ts`

**做法**：
- `recordInner` / `prune` / `rewind` 的 catch 块加 `logger.warn`（用 src/shared/logger.ts，NDJSON sink；快照组件名 `file-history`）。只 warn 不抛——旁路语义不变。
- `SnapshotContext.record` 仍返回 void，不改变工具层契约。

### 1.3 P1-1：shell 只读命令不快照（写类命令预判）

**位置**：`src/im/tools/file-history.ts`（recordShellCommand 入口）

**做法**：加纯函数 `isWriteLikeShellCommand(command): boolean`，只有判定为写类才抽路径：
- POSIX 写类动词（首 token 或分隔符后首 token）：`rm` `mv` `cp` `dd` `truncate` `tee` `sed -i` `install` `ln` `touch` `chmod` `chown` `> >>` 重定向、`patch` `git checkout --` `git restore`
- PowerShell 写类：`Remove-Item`（含别名 rm/del/rd/ri/erase）`Set-Content` `Add-Content` `Out-File` `Move-Item` `Copy-Item` `New-Item` `Clear-Content`
- 判定**复用 dangerous-command.ts 的 psSegments/stripPunct 前导剥离思路**（首 token 是 `do/then/else/{` 时剥掉），但不引入对分类器的依赖——file-history 自带一个小表（方言不分的保守集），避免两个模块耦合。
- **Fail-open**：判定不了的命令（含变量/管道复杂结构）**不快照也不报错**——宁可漏快照不可误快照（误快照会污染 rewind 语义，漏快照只是这条命令不可撤，与现状一致）。

**回归测试**：`grep foo.ts` / `cat bar.md` / `npm run build` → 0 条；`rm a.ts` / `sed -i s/a/b/ f.ts` / `echo x > out.md` → 快照生成。

### 1.4 P1-2：白名单外文件被改时显性告知

**位置**：`src/im/tools/write.ts` / `edit.ts` / `search-replace.ts` + `file-history.ts`

**做法**（选"告知"路线，不扩大保护范围——保护范围是用户拍板的设计）：
- `file-history.record` 增加返回值：`{ snapshotted: boolean; reason?: 'unprotected' | 'too-large' | 'sensitive' }`（原来 void）。
- 三个写类工具拿到结果后，在**成功返回的文本尾部**追加一句：`[snapshot: not protected (unprotected type) — this change cannot be undone via /rewind]`（英文，与工具返回风格一致）。只对"确实写了但没快照"的文件提示，不多不少。
- `search_replace` 逐文件提示太啰嗦 → 汇总一行：`[snapshot: N of M changed files are not undoable (unprotected types: .docx, …)]`。
- **不做**：把 docx 纳入保护（用户拍板放弃）；不做阻断。

### 1.5 死代码清理

- 删 `src/im/tools/index.ts:295` 的 `(r as ...).fileHistory = fileHistory` 挂载及 `as` 断言。
- `file-history-integration.test.ts` 两处从 registry 取实例的写法改为：外部 `createFileHistory(...)` → `createBuiltinTools({ cwd, dataDir, fileHistory })` → 直接用外部引用（这更贴近 assembly 的真实用法，测试反而更真）。

## 2. 前端「撤销更改」按钮（webapp）

**位置**：文档变化展示区 = `webapp/src/components/chat/ProducedFilesRow.tsx`（v0.24 的「产物」chips 行，数据源是 producedFilesOf 对 write/edit/search_replace 成功调用的机械提取）。

### 2.1 UI

- 在「查看工作区」按钮**左侧**加一个「撤销更改」按钮（样式与现有按钮一致：border + var(--bg-panel)）。
- 点击后：
  1. 按钮进入 loading 态（文字变「撤销中…」，禁用防重复点击）。
  2. 发 gate 命令 `{ kind: 'session.rewind', sessionId, entries: N }`。**N 的取法**：取该 turn 涉及的快照记录数——由后端在下一条（2.2）提供"最近一次 turn 的记录数"，前端不数。
  3. 展示结果：用现有 QuestionDialog 风格的**结果面板**（或就地 chips 行下方展开一个小面板），**按用户要求分三组显示**：
     - ✅ 撤销成功：`restored`（文件名列表，绿色/主色）
     - 🗑 已删除（AI 新建的文件被回滚删除）：`deleted`
     - ⚠️ 未能撤销：`unbacked`（灰色/警示色，附原因文案"该文件当时超出大小限制，未保留改动前内容"）
     - 无记录时显示"没有可撤销的改动"。
- 结果面板常驻到用户下一次操作或点关闭。

### 2.2 后端配套（两个小改动）

- **`session.rewind` 增加可选 `entries?: 'last-turn'` 语义**：加一个 gate 命令变体 `{ kind: 'session.rewind'; sessionId; entries: number | 'last-turn' }`——宿主收到 `'last-turn'` 时自己查索引算出"最近一个 turn 窗口的记录数"再执行。**避免前端数数**（前端只有 ToolTurn 视图，快照记录在宿主侧）。file-history 加 `countLastTurnRecords(sessionId): Promise<number>`（按 ts 簇聚类：间隔 > 10 分钟视为新 turn 的近似实现，诚实标注这是近似）。
- **通道（已核实，2026-09-12）**：webapp 的 `command()`（webapp/src/api/token.ts:18，POST /api/v1/cmd）→ webshell server 的 `commandFromBody`（server.ts:194-205）→ `gate.command(cmd)`。server 端**只校验 kind 字段存在，无 kind 白名单**（未知 kind 由 gate 的 switch 干净报错）——因此 `session.rewind`（已在 gate 命令 union，gate.ts:261-270）**天然可达，后端通道零改动**。前端只需在按钮 onClick 里发命令即可。

### 2.3 CLI —— **明确不做（用户裁定 2026-09-12：本功能只在网页端上线）**

- CLI 不加 `/rewind` slash 命令。信号关链路照旧保留（后端能力不受前端范围影响）；将来若要 CLI 入口，只是加一个 slash 命令调同一条 gate 命令，届时另立计划。

## 5. 明确不做（本轮）

- 跨进程文件锁（多进程冲突窗口极小，后果仅丢单条记录）
- prune 按会话分组回收（P2，配额是全局资源语义）
- unbacked 记录保留（无内容副本，留着也不能还原）
- rewind 中途崩溃一致性（已确认无部分回滚窗口，不修）
- docx 等纳入保护（用户拍板放弃）

### 6.3 实现期发现（计划未预见）

1. **目录必须显式拒收**：`record(<目录>)` 若按"新建"登记（`existedBefore:false`），rewind 会 `rm` 掉整个目录。名字过不了白名单的目录会早退，但名字**像**受保护文件的目录（如 `docs.md/`）会走到 `stat`——因此实现里显式 `!prior.isFile → return`，并加测试钉住两条路径。
2. **`prune` 期间的索引守恒**：计划要求把并发测试的 `≤20` 改成"精确断言零丢失"，但 prune **本身就要按配额裁记录**，所以那条断言只能钉"不失控"。**真正的零丢失断言另立一条**：`rewind` 与 20 条并发 record 竞争后 B 会话必须一条不少（rewind 不裁别人的记录）。
3. **happy-dom 基建是齐的**：本仓库 webapp 自带 `node_modules` + `happy-dom` + `@testing-library/react`（v0.25.1 用户拍板），但必须用 **webapp 自己的** vitest 跑（用根目录的 vitest 会解不到 webapp 的依赖，两个既有测试文件会静默不收集）。因此 §2.1 的交互测试是真 DOM 点击测试，不是 SSR 冒烟。
