# v0.10.1 — Foundation Plan Index

> **Historical plan — implemented in commit `c377e2c`.**
> This plan shipped the v0.10.1 foundation (narrowed Databus, Mailbox, system-agent factory, 7 new tools). It is retained as a historical implementation record. Note: the v0.10.1 landing introduced a **split-store prompt-assembly defect** (ConversationMemory holds user/assistant, Databus turns appended separately to the working prompt). That defect is the target of the v0.10.4 correction plan ([`v0.10.4-system-agent-autodrive.md`](./v0.10.4-system-agent-autodrive.md)). Read this document as history, not as the current target architecture.

> **Scope**: the three foundation pieces that v0.10.2 (`StateLine`) and v0.10.3
> (context injection) sit on top of. Nothing in v0.10.2 / v0.10.3 can compile
> without these three landing first.
>
> **Hard implementation order** (compile-time dependencies):
>
> 1. **§A. Databus narrowing** — `Databus` accepts `role: 'tool'` only;
>    `role: 'user' / 'assistant'` moves to a new `ConversationMemory` type.
> 2. **§B. Mailbox** — depends on §A's narrowed `Databus` (mailbox items
>    reference `agentId` and `stamp` shapes that §A also defines).
> 3. **§C. `createSystemAgent` factory + 7 new tools + working-agent wiring** —
>    depends on §A (factory reuses `Databus`), §B (factory exposes
>    `mailbox_send` / `mailbox_read` tools).

## 1. Why three pieces, why in this order

ADR-016 splits v0.10 into three v0.10.X releases, but does not split v0.10.1
itself. The dependency graph at the type level:

```
Databus.narrow()                  ─┐
                                   ├─► ConversationMemory  (introduced by §A)
                                   │
Mailbox(hasUnread, send, read)    ─┤
                                   │
createSystemAgent(name, ...)      ─┴─► depends on §A + §B
        │
        └─► exposes 7 new tools to working agent
                │
                └─► IMLoopOptions gets 1 new field (systemAgents)
```

The hard order is enforced by **TypeScript's import graph**, not by
discipline. If you try to write §C before §A, the import
`./databus.js` (returning `Databus`) will not match the §C factory's
expectation that `Databus` only holds `role: 'tool'`.

## 2. What is in scope for v0.10.1 (the whole release)

- `Databus` narrowed to `role: 'tool'` only
- New `ConversationMemory` type for `role: 'user' / 'assistant'` turns
- 3 existing `runIMLoop` call sites of `databus.append` migrated to
  `conversationMemory.append`
- 1 existing `runIMLoop` call site of `databus.turns()` split into
  two projections (databus for tool events, conversationMemory for
  user/assistant)
- `Mailbox` class with `send` / `readOwnInbox` / `hasUnread`
- `createSystemAgent` factory
- 7 new system tools registered to the working agent's `ToolRegistry`:
  `databus_query`, `databus_subscribe`, `state_query`, `compress_block`,
  `ask_recall`, `mailbox_send`, `mailbox_read`
- 3 system-agent instances (warehouse / compressor / recall) instantiated
  via the factory and registered
- `IMLoopOptions.systemAgents` field (new) — the working agent's view of
  the 3 system agents
- Tests: 200 → 230+ (+30 tests)

## 3. What is explicitly out of scope for v0.10.1

- `StateLine` filesystem — v0.10.2. `state_query` tool exists in v0.10.1
  but its `execute` body is a TODO stub that throws "not yet implemented
  in v0.10.1; see ADR-016 §8 v0.10.2"
- `scripts/embed.py` integration — v0.10.2
- Working-agent context injection (the 3-step pipeline from ADR-016 §1.2) —
  v0.10.3. `mailbox_hasUnread` exists but is not yet called from
  `runIMLoop`; the system-prompt-tail hint is wired in v0.10.3
- L3 RAG — v0.10.2
- >950K email handoff — v0.10.3 (warehouse agent's `mailbox_send` to
  working agent's `mailbox_read`)

## 4. Cross-piece contract (the 3 files must agree on these)

These are the **shared shapes** the three pieces import from each other.
Locking them in this index (not in any single piece) prevents drift.

```ts
// From §A. Used by §B (mailbox.send's `to`) and §C (system agent naming).
export type AgentId = string  // 'main' | 'warehouse' | 'compressor' | 'recall'

// From §A. The narrowed databus entry. Used by §B and §C as the
// `sourceAgentId` / `stamp` join key. Note: NO `metadata` field (ADR-016 §2.2).
export type ToolTurn = {
  id: string
  role: 'tool'
  toolCallId: string
  content: string
  isError?: true
  sourceAgentId: AgentId    // which agent's runIMLoop produced this
  at: number
}

// From §A. The new home for user / assistant turns. Replaces the v0.9
// `Turn` union for these two roles. The working agent's own `runIMLoop`
// is the only writer; the system agents never see these.
export type ConversationMemory = {
  append(turn: { role: 'user'; content: string; at: number } |
                { role: 'assistant'; content: string | null; toolCalls?: ToolCall[]; at: number }): void
  turns(): readonly ConversationTurn[]
  last(): ConversationTurn | undefined
}
export type ConversationTurn = /* see §A for the full union */

// From §B. The mailbox's wire shape. Used by §C's `mailbox_send` /
// `mailbox_read` tool wrappers.
export type MailItem = {
  id: string
  from: AgentId
  to: AgentId
  subject: string
  body: string
  replyTo?: string
  sentAt: number
  read: boolean
}

// From §C. The 7 new tool names. Listed in the order they appear in
// the working agent's ToolRegistry. ADR-016 §3.4 locks the I/O shapes.
export const NEW_V010_TOOL_NAMES = [
  'databus_query',
  'databus_subscribe',
  'state_query',        // stub in v0.10.1
  'compress_block',
  'ask_recall',
  'mailbox_send',
  'mailbox_read',
] as const
```

## 5. Migration risks (call out before any piece is implemented)

| Risk | Mitigation |
|---|---|
| `loop.ts:238` `append(assistantTurn)` — where does it go? | New `ConversationMemory` instance owned by `runIMLoop`. `IMLoopOptions.conversationMemory: ConversationMemory` (new field, required). |
| `loop.ts:262` `append(toolResult)` — the tool result is `role: 'tool'`, but v0.9 wrote it to the same databus as user/assistant | Now it goes to the narrowed `Databus`. Two appends per round, to two different stores. |
| `loop.ts:167` `databus.turns()` injects all roles into the prompt | Becomes `databus.turns()` (tool only) + `conversationMemory.turns()` (user/assistant) in the prompt parts list. The order in the final prompt is preserved. |
| `tests/im/databus.test.ts` tests 1 + 3 use `role: 'user'` | Tests must be rewritten to use `ConversationMemory` for those cases; the `Databus` tests shrink to `role: 'tool'` only. |
| `examples/minimal.ts` `databus.append({ role: 'user', ... })` | Example must split into two: a `ConversationMemory` for the user message, an empty `Databus`. The example is a regression test of the public API; this is the canary. |
| `IMLoopOptions` 3 new required fields (`conversationMemory`, `mailbox`, `systemAgents`) | Caller breakage is unavoidable. Provide a `createMinimalIM(opts)` factory in v0.10.1 that wires defaults so the existing `examples/minimal.ts` keeps working after a one-line change. |
| `scripts/embed.py` (already exists) is referenced in §C's RAG stub | No action — embed.py is unused until v0.10.2 |

## 6. Tests strategy (applies to all 3 pieces)

Each sibling document lists 3 test categories:

1. **Pure-function tests** for the new module
2. **Integration tests** with stub `Databus` / `Mailbox` / `runIMLoop`
3. **End-to-end tests** via `runIMLoop` with the new fields populated, asserting on
   `finalPrompt.messages` (captured via the test-only `streamChat` adapter that
   already exists in `tests/im/loop.test.ts`)

**Total target**: 200 → 230+ tests (≥ 30 new). Split roughly:
- §A: 8 tests
- §B: 9 tests
- §C: 15 tests (factory API + 7 new tools + 1 end-to-end with system agents)
