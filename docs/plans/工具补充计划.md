## 1. 调研发现：值得补充的工具

### 第一优先级（高频刚需，实现成本低）

#### 1.1 search_replace — 跨文件批量替换

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/search_replace.rs` |
| **功能** | 跨多文件的一次性查找替换（项目级重命名），默认字面量匹配，`regex:true` 走正则 + 捕获组，`glob` 限定范围 |
| **我们的痛点** | 只有单文件 `edit`，做一次"把全项目 `oldName` 改成 `newName`"得让模型逐文件 edit，慢且易遗漏 |
| **实现方式** | glob 匹配文件 → 逐文件读改写 → 敏感文件检测复用现有 `sensitive-path.ts` → 审批走现有 `approval-hook.ts` |
| **实现难度** | 低-中（核心是 glob + 读改写循环，约 150 行） |
| **安全约束** | 走 SystemSecurityHook 审批，写操作需 grant |

#### 1.2 ast_grep — AST 结构化搜索

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/ast_grep.rs` |
| **功能** | 基于 AST 的结构化代码搜索，用元变量 `$NAME`/`$_`/`$$$` 匹配语法节点而非文本。精确找"所有 `.unwrap()` 调用"、"某类函数签名" |
| **我们的痛点** | `grep` 是纯正则，"找所有 `.unwrap()` 调用"会误匹配注释、字符串、同名标识符 |
| **实现方式** | shell out 到 `ast-grep`/`sg` 二进制（仿 rg-resolver 模式做 resolver + 缺二进制友好提示），只读无安全负担 |
| **实现难度** | 低（约 200 行，与 grep 共享 resolver 模式） |
| **依赖** | 用户机器装 `ast-grep`（可选，缺失时回退到 grep） |

#### 1.3 fetch_output — 截断输出分段回读

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/output_artifact.rs` |
| **功能** | 工具输出被截断时，完整内容存入按内容寻址的 artifact store，返回截断标记 + `artifact_id`；模型可调 `fetch_output(artifact_id, offset, limit)` 分段读取 |
| **我们的痛点** | `bash`/`read`/`grep` 大输出只能一次性截断，模型想看后半段只能重跑命令 |
| **实现方式** | session 级 ArtifactStore（内容 hash → 文件），`put(id, content)` / `get(id, offset, limit)`；改造 bash/read/grep 的截断路径接入 store |
| **实现难度** | 中（store + hash + 切片读取简单，需改造 3 个工具的输出路径） |
| **存储** | session 级临时目录，session 结束自动清理 |

### 第二优先级（能力缺口，中等实现成本）

#### 1.4 web_fetch — 带 SSRF 防护的网页抓取

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/web_fetch.rs` + Kimi Code `web/fetch-url.ts` |
| **功能** | 抓取 http(s) 页面转纯文本/markdown（保留标题/链接/代码） |
| **我们的痛点** | 完全无联网能力，模型查文档/库 API 只能靠用户喂或 bash+curl |
| **SSRF 防护**（AtomCode 范本）：解析 IP → 禁 localhost/私网/云元数据 → 手动跟随重定向每跳复检 → curl 兜底 |
| **实现难度** | 中（Node.js `fetch` + 手动重定向 + IP 校验 + HTML→MD 转换） |
| **依赖** | 可选 `turndown` 或 `html-to-md` 做 HTML→MD |

#### 1.5 request_user_input — 结构化用户提问

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/request_user_input.rs` + Kimi Code `collaboration/ask-user.ts` |
| **功能** | 向用户提结构化问题（single/multiple/text 模式，2-4 选项），等待回答后继续 |
| **我们的痛点** | 模型需要"在分支决策点征求用户偏好"时只能写散文，易误解 |
| **实现方式** | 复用现有 approval-store 通道（reverse-RPC），前端渲染选项卡片 |
| **实现难度** | 中（后端逻辑简单，需前端配合渲染） |
| **降级** | 无前端时降级为纯文本提示 |

#### 1.6 memory — 跨会话记忆

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/memory.rs` |
| **功能** | 模型持久化"非显然的学习"到 `memory.md`（项目级或全局），action=remember/forget/list；会话开始注入 |
| **实现方式** | 纯文件 store（`.agent-shell/memory.md`），写 memory.md + 会话起始注入钩子 |
| **实现难度** | 低（约 100 行） |

### 第三优先级（架构级，高实现成本）

#### 1.7 web_search — 网络搜索

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/web_search.rs` |
| **功能** | 关键词 web 搜索，返回标题/URL/片段 |
| **实现方式** | 接搜索 provider（Exa/DuckDuckGo/自托管 SearXNG） |
| **实现难度** | 中（需 API key + provider 选择） |

#### 1.8 parallel_edit_files — 并行多文件编辑

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/parallel_edit.rs` |
| **功能** | fork 子代理并行编辑多个独立文件，合并后跑构建探针 |
| **实现难度** | 高（依赖子代理调度 + 合并 + 构建探针） |

#### 1.9 task — 子代理派发

| 维度 | 内容 |
|---|---|
| **来源** | AtomCode `tools/task.rs` + Kimi Code `collaboration/agent-swarm.ts` |
| **功能** | 派发子任务到隔离子代理（explore 只读 / worker 改文件），并行运行 |
| **实现难度** | 高（架构级，需完整子代理调度 + 隔离 + 上下文管理） |

## 2. 浏览器集成方案

### 调研结论

| 方案 | 来源 | 模式 | 适合我们的场景 |
|---|---|---|---|
| **Kimi WebBridge** | Kimi Code | daemon + 浏览器扩展 + CDP 驱动用户真实浏览器 | ❌ 需要用户真实浏览器 + 扩展 |
| **Playwright MCP** | Microsoft | MCP stdio/SSE，Playwright 驱动 headless 浏览器 | ✅ 最佳方案 |
| **browser-use** | Python 社区 | Python + Playwright agent 循环 | ❌ Python 生态 |

### 推荐方案：`@playwright/mcp` 作为 MCP server

**理由**：
1. agent-shell 已有 MCP 扩展系统（v0.13），加 Playwright MCP = 配置里加一个 MCP server，**零代码改动**
2. TypeScript 原生，与 agent-shell 技术栈一致
3. 工具集完整：navigate/click/type/screenshot/snapshot/evaluate/pdf
4. 无障碍树优于截图（token 消耗低）

**Playwright MCP 暴露的工具**：

| 工具 | 功能 |
|---|---|
| `browser_navigate` | 打开 URL |
| `browser_snapshot` | 无障碍树快照（主要交互方式） |
| `browser_click` | 点击元素 |
| `browser_fill` / `browser_type` | 填写/输入 |
| `browser_take_screenshot` | 截图 |
| `browser_pdf_save` | 页面渲染为 PDF |
| `browser_evaluate` | 执行 JS |
| `browser_tabs` | tab 管理 |
| `browser_network` | 网络请求监控（opt-in） |

**集成方式**：
```json
// config 中新增
{
  "name": "playwright",
  "transport": "stdio",
  "command": "npx",
  "args": ["-y", "@playwright/mcp@latest"]
}
```

**开发难度**：极低（纯配置，1-2 小时）

### 备选方案：自建 Playwright 封装

如果需要更细粒度的控制（如复用用户登录态、自定义工具集），可以自己写 Playwright 封装：
- 开发难度：中等（2-3 天）
- 需要自己写工具 schema + Playwright 封装 + 截图/PDF 逻辑

## 3. MD 文档渲染方案

### 调研结论

| 项目 | MD 渲染能力 | 输出格式 |
|---|---|---|
| Kimi Code | `marked@18.0.5` TUI 终端渲染 | ANSI 文本 |
| AtomCode | `marked@^12.0.2` webui + vscode 扩展 | HTML |
| DeepSeek Harness | `rich.markdown` CLI 终端 | ANSI 文本 |

**三个项目都没有独立的 MD→PDF 渲染工具**——MD 渲染只是前端组件，PDF 是浏览器能力的副产品。

### 推荐方案：`marked` + Playwright

| 步骤 | 工具 | 依赖 |
|---|---|---|
| MD → HTML | `marked`（零依赖） | `marked` npm 包 |
| HTML → PDF | `browser_pdf_save`（Playwright MCP） | 浏览器集成就绪后 |
| HTML → PNG | `browser_take_screenshot`（Playwright MCP） | 浏览器集成就绪后 |

**实现路径**：
1. `render_md` 工具：`marked(content)` → HTML string → 可选写 `.html` 文件
2. `render_pdf` 工具：先 `render_md` → 临时 HTML 文件 → Playwright 打开 → `page.pdf()` → 返回 PDF 路径
3. `render_png` 工具：类似，用 Playwright screenshot

**开发难度**：
- MD→HTML：极低（1 小时，`marked` 一个函数调用）
- MD→PDF/PNG：低（依赖浏览器集成，Playwright MCP 就绪后 2-3 小时）

## 4. grep 原生方案调研

### 当前实现

shell out 到系统 `rg` 二进制 + 解析 `--json` 输出。每次搜索 fork 子进程（~50ms 启动开销）。

### 四种方案对比

| 方案 | in-process? | 能力对等 | 启动开销 | 零依赖哲学 | 实现难度 | 体积 | 性能 |
|---|---|---|---|---|---|---|---|
| ① `@vscode/ripgrep` | 否（仍 spawn） | 是 | 50ms | 违背 | 低 | +2-3MB/平台 | =现状 |
| ② `ripgrep` WASM | **是** | 是（真 rg 编译） | ~0 | 轻微违背 | 低-中 | +~750KB | 小中库优/大库存疑 |
| ③ 纯 Node 内置 | 是 | **否**（gitignore/SIMD/线性正则缺失） | ~0 | 完全符合 | 高 | 0 | 慢 5-20× |
| ④ napi-rs Rust addon | 是 | 是（最优） | ~0 | 违背 | 高 | +2-4MB/平台 | 最优 |

### 推荐：方案 ② ripgrep WASM 包

**理由**：唯一同时满足"in-process"+"能力对等"+"实现难度低"+"体积可控"的方案。

**风险点**：
- 包极年轻（2026-04-06 发布，0.3.1），生产可信度存疑
- WASM 单线程 + WASI I/O 代理在大仓库下可能慢于原生 rg
- 需实测验证

**回退策略**：若 WASM 大仓库性能不达标，维持 shell out（可选叠加方案①解决分发）。

## 6. 新增工具对现有机制的影响

| 机制 | 影响 |
|---|---|
| **并发限制** | 新工具按类别归入 read/write/command，自动继承并发上限 |
| **安全钩子** | 写操作工具（search_replace）走 SystemSecurityHook 审批；读操作工具（ast_grep/web_fetch）放行 |
| **报错机制** | 所有新工具走 `wrapTool`，报错格式统一为 `Tool "X" failed: <msg>` |
| **MCP 注册** | Playwright MCP 通过 `bootstrapExtensions` 注册，走 MCP 安全壳子 |
| **reason 必填** | 所有新工具 schema 含 `reason` 字段，`requireReason` 校验 |
