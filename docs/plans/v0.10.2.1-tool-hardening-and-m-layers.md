## 1. Constraints (hard rules, do not violate)

[已验证 against ef67968 + ADR-016]:

1. **User-mandated naming (2026-08-28), supersedes ADR-016 §1.1/§2.2 vocabulary**:
   - **M0** = 0–200K tokens, **no compression** — full turns straight from `Databus` + `ConversationMemory`.
   - **M1** = 200–500K, **fill-in-template (填字板) compression** — 11-field `CuratedMemory`.
   - **M2** = 500–900K, **summary (摘要) compression** — 11-field `CuratedMemory` **for now** (M1/M2 identical schema; divergence is deferred slack).
   - **M3** = >900K, **archived/indexed** — `index.jsonl` + `vectors/chroma/` RAG, reached via email hint (never injected).
2. **M1 and M2 share one schema in v0.10.2.1** — user decision: "M2、M1 暂时保持一致，等待后续看看是否需要迭代，留一个冗余空间，这一点写到注释里". Do **not** build a second schema. Do **not** add a discriminator field beyond the layer tag.
3. **Tool registration = hardening point** (user decision): every tool registered via `ToolRegistry.registerSystemTool` must go through the same wrap path that enforces `reason` validation + error conversion. The 8 v0.9 tools already do this via `wrap()` in [tools/index.ts:38](../../../agent-shell/src/im/tools/index.ts#L38); the 7 v0.10 tools must match.
4. **Fuse accounting must be uniform** (user decision: "并行上限报错熔断也需要同步"): tool failures and call counts feed the existing `errorRate` / `toolRate` guards ([guards.ts:24-32](../../../agent-shell/src/shell/guards.ts#L24)). Verified the 7 new tools **already** flow through `executeToolCalls`'s `try/catch` ([loop.ts:142-166](../../../agent-shell/src/im/loop.ts#L142)) so fuse counting works — but the wrap layer must not double-count or bypass it.
5. **ADR-016 must be revised, not silently diverged** — the `200K/950K` two-threshold model (§1.1) and `L1/L2/L3` names (§2.2, §4.2) change to `200K/500K/900K` and `M0–M3`. ADR-016 is `Active (draft)` so revision is expected; update it in this same change.
6. **Shell layer must not import IM** (ADR-003 layering): [registry.ts:9](../../../agent-shell/src/shell/registry.ts#L9) currently does `import type { ToolContext } from '../im/state-line/types.js'` — direction reversed. `ToolContext` moves to a shell/shared-owned location.
7. **No new runtime dependency** (AGENTS.md §2.5). No new guard type. No new metric field (ADR-015: every metric needs a producer + reader; the existing 5 guards are reused).
8. **`reason` stays OUT of the JSON-schema `required` array** (ADR-013) — strict-schema coding-plan services reject schema deviations; enforcement is runtime via `requireReason`, same as v0.9.
9. **append-only jsonl untouched** — the M-rename changes the *layer tag string* written to `stamps.jsonl` / matched in queries, not the file layout or the append-only invariant.

## 3. Architecture (the M-layer model + tool hardening boundary)

### 3.1 The four memory intervals (user-mandated)

```
Token size of working context
  0 ─────────────── 200K ─────────────── 500K ─────────────── 900K ──────►
  │     M0           │      M1           │      M2           │   M3
  │  no compression  │  fill-in-template │  summary compress │  archived
  │  full turns      │  11-field block   │  11-field block   │  RAG index
  │  (Databus +      │  curatedMemory.   │  curatedMemory.   │  index.jsonl +
  │   ConvMemory)    │  jsonl            │  jsonl            │  vectors/chroma
  │                  │                   │                   │
  │  INJECTED raw    │  INJECTED as      │  INJECTED as      │  NEVER injected;
  │                  │  curated blocks   │  curated blocks   │  email hint only
  └──────────────────┴───────────────────┴───────────────────┘
        storage: in-memory        └──────────── filesystem (state-line) ────────────
```

| Layer | Interval | Compression | Schema | File | In context? |
|---|---|---|---|---|---|
| **M0** | 0–200K | none | raw `ToolTurn` / `ConversationTurn` | (in-memory) | yes, raw |
| **M1** | 200–500K | fill-in-template (填字板) | 11-field `CuratedMemory` | `curatedMemory.jsonl` | yes, injected |
| **M2** | 500–900K | summary (摘要) | 11-field `CuratedMemory` (**same as M1 for now**) | `curatedMemory.jsonl` | yes, injected |
| **M3** | >900K | archived/indexed | `L3Summary` (→ rename `M3Summary`) | `index.jsonl` + `vectors/chroma/` | **no** — email hint |

**M1/M2 slack note (must appear as a code comment, per constraint #2)**:
> `// M1 and M2 currently share the 11-field CuratedMemory schema. M2 (summary compression)
>  // is expected to diverge into a shorter form later; the layer tag distinguishes them so a
>  // future schema split does not require a data migration. Do not assume M1 === M2 forever.`

### 3.2 Tool hardening boundary

```
                 registerSystemTool(toolDef)
                            │
                            ▼
              ┌───────────────────────────────┐
              │  shared tool-helpers module   │   ← NEW (src/im/tools/helpers.ts)
              │  • wrapTool(executor, name)  │     - reason validation (requireReason)
              │  • requireReason             │     - throw → "Tool X failed: ..." sentence
              │  • toSchema / reasonField    │     - shared by 8 v0.9 + 7 v0.10 tools
              └───────────────────────────────┘
                            │
            ┌───────────────┴────────────────┐
            ▼                                 ▼
   v0.9 builtin tools (8)            v0.10 system tools (7)
   createBuiltinTools                databus_query / databus_subscribe /
   (read/write/edit/ls/find/grep/    state_query / compress_block / ask_recall /
    bash/powershell)                 mailbox_send / mailbox_read
            │                                 │
            └───────────────┬─────────────────┘
                            ▼
              executeToolCalls (loop.ts)
              • Promise.all batch (parallel)
              • try/catch → isError turn → errorCount
              • errorRate guard  (consecutive error turns > 10 → Tripped)
              • toolRate guard   (total tool calls > 500 → Tripped)
```

**Key**: the wrap layer does **reason validation + error sentence conversion**; the **fuse** is the loop's `errorRate`/`toolRate` guards (unchanged). wrap must NOT do its own circuit-breaking — that would double-count. The "parallel cap" the user references maps to the existing `toolRate` guard (total calls) plus `errorRate` (consecutive failures); a per-round concurrency cap is **not** added (see §7 open question #1).

## 4. Design principles (plan-specific)

1. **One registration path, one hardening shape.** The 8 v0.9 and 7 v0.10 tools must be indistinguishable at the `ToolRegistry` boundary — same `reason` enforcement, same error sentence format, same fuse feeding. The current split (v0.9 wrapped, v0.10 bare) is the defect this fixes.
2. **Extract, don't rewrite.** `wrap`/`requireReason`/`toSchema`/`reasonField` already exist and are tested. Move them to a shared module; change call sites to import. No behavioural change to the v0.9 tools (their tests stay green unmodified).
3. **Naming is a find-and-replace of layer *tags*, not a storage migration.** `'L2'`→`'M2'`, `'L3'`→`'M3'`, etc. The jsonl files, the 11-field schema, the chromadb collection are all unchanged. Old on-disk records with `L*` tags are out of scope (v0.10.2 is pre-release; `~/.databus` is dev data).
4. **M1/M2 schema identity is deliberate slack, documented not built.** Leaving them identical now avoids speculative abstraction (AGENTS.md: don't build for the future); the layer tag preserves the option to split later.
5. **Fuse stays in the loop, not in the tools.** Tools report failures (throw / `isError`); the loop counts; the guard trips. Putting a circuit-breaker inside each tool would duplicate the errorRate guard and violate ADR-015 (no redundant mechanism).
6. **Layering direction is a compile error, not a convention.** Moving `ToolContext` to the shell layer makes "shell imports im" impossible at the type level — same philosophy as the v0.10.1 databus narrowing.

### 5.9 Memory-layer thresholds + dispatch signal (NEW, user-mandated)

The M-layer ranges live in code now (not just ADR prose), as a **pure range table + an if-else classifier that emits a signal**. The signal decouples "which layer are we in" from "what business code runs for that layer" — v0.10.3 wires the signal to injection/compression; v0.10.2.1 only ships the classifier + extension points.

NEW `src/im/memory-layers.ts` (pure, no I/O, no LLM):
```ts
export type MemoryLayer = 'M0' | 'M1' | 'M2' | 'M3'

// Token thresholds (user-mandated 2026-08-28). M0 needs no constant for its
// lower bound (it is the < M1_MIN default branch).
export const MEMORY_LAYER_THRESHOLDS = {
  M1_MIN_TOKENS: 200_000,   // < 200K  → M0: no compression, raw turns
  M2_MIN_TOKENS: 500_000,   // 200–500K → M1: fill-in-template compression
  M3_MIN_TOKENS: 900_000,   // 500–900K → M2: summary compression
                            // > 900K  → M3: archived/RAG, email hint only
} as const

// Pure classifier — an if-else range check. Returns the layer for a context size.
export function classifyMemoryLayer(contextTokens: number): MemoryLayer

// Dispatch signal: the if-else only EMITS a signal; it does not run business
// logic. v0.10.3 registers handlers; v0.10.2.1 ships the emitter + a no-op
// default so the shape is stable. Handlers are keyed by layer, so adding a
// business action later = registering a handler, NOT editing the classifier.
export type LayerSignal =
  | { layer: 'M0'; contextTokens: number }
  | { layer: 'M1' | 'M2' | 'M3'; contextTokens: number; threshold: number }
export type LayerHandler = (signal: LayerSignal) => void | Promise<void>
export function onLayerEnter(layer: MemoryLayer, handler: LayerHandler): () => void  // unsubscribe
export function emitLayerSignal(contextTokens: number): Promise<LayerSignal>          // classifies + fires handlers
```

Design notes (the user's decoupling principle):
- `classifyMemoryLayer` is a plain if-else: `<200K → M0`, `<500K → M1`, `<900K → M2`, else `M3`. No abstraction, no strategy objects — one function, four branches.
- The classifier **returns a signal**; it never calls compress/inject/email itself. Business code subscribes via `onLayerEnter`. This keeps "range judgement" separate from "what to do" — extension means adding a handler, not touching the if-else.
- M0 needs no jsonl/type/tag (it is the `<200K` no-compression branch) — confirmed by user.
- M1/M2 share the 11-field schema for now (§3.1 slack comment); the layer tag on the signal distinguishes them so a future split needs no data migration.

### 5.10 Tool concurrency cap = 2 (NEW, user-mandated)

[verified] `executeToolCalls` ([loop.ts:123](../../../agent-shell/src/im/loop.ts#L123)) currently does `Promise.all(toolCalls.map(...))` — **all tool calls in one round run concurrently with no cap**. Several v0.10 tools (`databus_query`, `state_query`, `compress_block`, `ask_recall`) trigger a full inner system-agent LLM session, so N parallel calls = N concurrent LLM calls.

Cap to **2 in-flight tool calls per round**:
- Replace the unbounded `Promise.all(map)` with a 2-worker pool (simple sequential batches of 2, or a tiny semaphore — one helper, no dependency).
- Results stay in the same order as the input `toolCalls` (the turns array must align with tool_call ids).
- Constant `MAX_CONCURRENT_TOOL_CALLS = 2` in `memory-layers.ts` (or loop.ts) with comment:
  > `// v0.10.2.1: hard-coded cap of 2 concurrent tool calls per round. Tunable later;
  >  // a per-layer / per-tool concurrency policy is future work (v0.10.3+).`
- This is NOT a guard (does not Trip the session); it is a scheduling limit inside `executeToolCalls`. The existing errorRate/toolRate guards are unchanged and still count every call.
- Document in IM-GUIDE + the tool-registration comment (§5.8): tool calls run at most 2-at-a-time; failures still feed the fuses.
