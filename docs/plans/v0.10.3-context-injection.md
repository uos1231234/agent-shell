# Code Plan: Working-Agent Context Injection Pipeline (v0.10.3)

> **⚠️ Historical plan — partially superseded by v0.10.4.**
> This plan was implemented in commit `3427e9f` (2026-08-28) and documents the v0.10.3 context-injection pipeline **as it was actually landed**. However, v0.10.3's prompt assembly still uses the **split-store pattern** (ConversationMemory holds user/assistant turns, Databus turns are appended separately to the working prompt). That split-store ordering is a protocol-level defect: it can interleave tool results and assistant messages in a way OpenAI's API does not guarantee. The v0.10.4 plan ([`v0.10.4-system-agent-autodrive.md`](./v0.10.4-system-agent-autodrive.md)) is the correction contract — it makes ConversationMemory the single canonical ordered sequence and demotes Databus to a pure tool-only projection copy that is never appended to the working prompt. Read this document as **historical implementation record**, not as the current target architecture.

> **Depends on**: v0.10.1 `c377e2c` (narrowed Databus + Mailbox + system-agent factory), v0.10.2 `ef67968` (StateLine filesystem + embed.py bridge), v0.10.2.1 `67e9654` (M0–M3 classifier + signal dispatch + tool hardening + concurrency=2)
> **Blocks**: nothing yet — this is the last piece of the v0.10 information-flow architecture. After v0.10.3 the working agent's context is a true dynamic projection.
> **Plan structure**: 7 sections per AGENTS.md §5. Rewritten 2026-08-28 to match the actual landed code (the earlier draft predated v0.10.2/v0.10.2.1 and assumed L1/L2/L3 + a 200K/950K model).

## 0. Goal (one paragraph)

[已验证 against `67e9654` source]:

Wire the three information flows into the working agent's `FinalPrompt` so the context is a **dynamic projection that changes shape at the M0/M1/M2/M3 boundaries** (ADR-016 §1.1, thresholds 200K / 500K / 900K). Today `runIMLoop` ([loop.ts](../../../agent-shell/src/im/loop.ts)) composes its prompt from: system prompt + userTemplate + tool refs + the agent's own `conversationMemory` turns + `databus` turns. It does **not** read the StateLine, does **not** append the mailbox unread hint, and does **not** consult the memory layer. v0.10.3 adds a pure `context-projection.ts` that — given databus + conversationMemory + stateLine + mailbox + current token estimate — produces the extra `PromptPart`s and the mailbox hint, and `runIMLoop` splices them in. The M-layer decision **calls the already-shipped `classifyMemoryLayer` directly per round** (a per-round pull); `emitLayerSignal`/`onLayerEnter` stay reserved for *proactive* cross-agent business (the warehouse's >900K email), not for injection.

## 1. Constraints (hard rules, do not violate)

[已验证 against landed code]:

1. **Injection lives in `src/im/`, never `src/shell/`** (ADR-003). `compose()` stays a pure `PromptPart[] → FinalPrompt` mapper ([compose.ts:32](../../../agent-shell/src/shell/compose.ts#L32)); v0.10.3 prepares parts, it adds zero logic to `compose.ts`.
2. **The `PromptPart` union is closed** ([compose.ts:19-25](../../../agent-shell/src/shell/compose.ts#L19)): `system | userTemplate | systemTool | mcp | skill | turn`. No 7th variant. State-line projects as a `system` part; mailbox hint is appended to the existing system prompt string; databus already maps to `turn` parts.
3. **M3 never enters the context** (ADR-016 §1.4). The projection reads M1/M2 blocks only (`stateLine.query({ layer: 'M1' | 'M2' })`). M3 reaches the agent solely via the warehouse email — already handled by the mailbox, not by injection.
4. **The mailbox is a hint, not content** (ADR-016 §1.3). Build `"\n\n[mailbox] you have N unread"` where `N = mailbox.readOwnInbox(workingAgentId).length` (strict unread count; `readOwnInbox` defaults to `!read`); never inject message bodies.
5. **Reuse the shipped M-layer classifier** — do **not** re-implement range logic. Import `classifyMemoryLayer`, `MEMORY_LAYER_THRESHOLDS` from [memory-layers.ts](../../../agent-shell/src/im/memory-layers.ts). v0.10.3 calls `classifyMemoryLayer(estimatedTokens)` directly each round (per-round pull); it does **not** register injection handlers — `emitLayerSignal`/`onLayerEnter` stay reserved for proactive cross-agent business (the warehouse >900K email).
6. **`stateLine` becomes a required `IMLoopOptions` field in v0.10.3** (it shipped optional in v0.10.2 per the v0.10.2 plan §7.2 #4, with JSDoc "Will be required in v0.10.3"). Remove the `?`; `createMinimalIM` must supply a real or no-op StateLine explicitly.
7. **No new metric / guard / config field** (ADR-015). Token estimation reads existing `metrics`; it does not add a field. The concurrency cap (`MAX_CONCURRENT_TOOL_CALLS = 2`) and the 5 guards are untouched.
8. **No shell state in the prompt** (ADR-004): `IMLoopResult`, `State`, `GuardHit[]` stay caller-only. The projection reads `metrics` for a token estimate only.
9. **Tools stay wrapped** — v0.10.3 adds no tool; it does not touch `helpers.ts` / the 15 registered tools.

## 3. Architecture (the dynamic projection)

### 3.1 What the working agent sees at each layer

```
context token estimate (last round's promptTokens, chars/4 fallback)
  │
  ├─ M0  (< 200K)
  │    system prompt (+ mailbox hint if unread)
  │    userTemplate
  │    tool refs (systemTool/mcp/skill)
  │    conversationMemory turns (user/assistant)   ← always-on base
  │    databus turns (role:'tool', recent, capped) ← M0 raw window
  │    （no state-line part）
  │
  ├─ M1  (200K–500K)
  │    all of M0  +  one `system` part: M1 curatedMemory blocks (jsonl)
  │
  ├─ M2  (500K–900K)
  │    all of M1  +  M2 curatedMemory blocks (same 11-field schema; M1/M2 both injected)
  │
  └─ M3  (>900K)
       state-line projection DROPPED (too large); mailbox hint still applies.
       system prompt gets the passive backstop line:
       "[context overflow] M3 available via state_query/ask_recall".
       M3 content itself is NEVER injected; proactive notice is the warehouse email.
```

### 3.2 The injection maps onto the closed 6-slot union

```ts
parts = [
  { type: 'system',       content: systemPrompt + systemSuffix },  // system + mailbox hint + M3 overflow line
  { type: 'userTemplate', content: opts.userTemplate },
  ...(stateLinePart ? [stateLinePart] : []),                       // system part, M1/M2 only
  ...systemToolRefs, ...mcpRefs, ...skillRefs,                     // unchanged
  ...conversationMemoryTurns,                                       // turn (user/assistant)
  ...databusTurns,                                                  // turn (role:'tool')
]
```

- **State-line → one `system` part** placed after userTemplate, before tool refs. A single `system` message with stable headers (`### M1 block stamp=…` / `### M2 block stamp=…`), so the agent's identity prompt stays at the head.
- **Passive hints → string append** to the head system prompt (`systemSuffix`): the mailbox unread line (when N>0) and, in M3 only, the overflow backstop line. Appending — not new messages — keeps the union at 6 slots (ADR-005) and keeps "hints, not content" (ADR §1.3).
- **Databus → `turn` parts** (already present in `runIMLoop`; v0.10.3 caps them by the M0 window + `databusMaxTurns`).

### 3.3 Token estimation

No exact count exists pre-`shellCall`. Reuse the locked heuristic: after `compose()` returns, `estimateTokensFromText = Math.ceil(allMessageContents.join('\n').length / 4)` (±20%). Feed that to `classifyMemoryLayer`. The estimate only drives the **binary** "inject M1/M2 blocks or not" + "drop at M3" decision — wide tolerance is fine; the hard ceiling is the existing `tokenGuard` (`maxTokens`).

## 4. Design principles (plan-specific)

1. **Projection is a pure function; the loop wires it.** `buildContextProjection(input)` returns parts + hint and does no I/O beyond the injected StateLine/Mailbox reads. `runIMLoop` calls it once per round and splices. Same shape as v0.9's `compose` boundary.
2. **Use the shipped signal, don't fork the range logic.** v0.10.2.1 already built `classifyMemoryLayer` + `emitLayerSignal`/`onLayerEnter`. v0.10.3 is where the M1/M2-inject and M3-drop **handlers get registered** (or, simpler and sufficient for injection: call `classifyMemoryLayer` directly each round — the handler registry is for *proactive* cross-agent business like the warehouse email; injection is a per-round pull, so a direct call is the thinner path). Decision: call `classifyMemoryLayer` directly in the projection; reserve `onLayerEnter` for the warehouse's proactive email (later).
3. **M3 drops the largest block, keeps the freshest.** When the estimate crosses 900K, the state-line `system` part is omitted (it is the biggest); conversationMemory + recent databus stay. This mirrors ADR-016 §1.1.
4. **M1/M2 share one read path.** Both live in `curatedMemory.jsonl` behind `stateLine.query({ layer })`; the projection queries them together and tags headers by the stamp record's layer. No M1-vs-M2 schema fork (the v0.10.2.1 slack comment holds).
5. **No defensive fallback stack.** If `stateLine` is absent the loop should not run (hence required field); the projection trusts its inputs. The no-op case is a test double, not a production `if (!stateLine)`.

## 5. Module guidance

### 5.1 NEW `src/im/context-projection.ts` (pure)

```ts
export type ContextProjectionConfig = {
  databusMaxTurns: number        // default 50 — cap on role:'tool' turns projected
  stateLineMaxBlocks: number     // default 20 — cap on M1/M2 blocks projected
}
export const DEFAULT_CONTEXT_PROJECTION_CONFIG: ContextProjectionConfig

export type ProjectionInput = {
  databus: Databus
  stateLine: StateLine
  mailbox: Mailbox
  workingAgentId: AgentId
  estimatedTokens: number
  config?: ContextProjectionConfig
}

// Pure. Returns the parts to splice in + the mailbox hint suffix.
export function buildContextProjection(input: ProjectionInput): {
  stateLinePart: PromptPart | null      // a `system` part (M1/M2 blocks), or null in M0/M3
  databusTurns: readonly PromptPart[]   // `turn` parts, capped to M0 window + maxTurns
  systemSuffix: string                   // mailbox hint AND/OR M3 overflow line, appended to head system prompt
  layer: MemoryLayer                    // M0/M1/M2/M3 as classified
}
```

Private helpers (file-local, signatures only):
- `estimateTokensFromText(text: string): number` — `Math.ceil(len/4)`.
- `selectDatabusTurns(databus, maxTurns): ToolTurn[]` — most recent `role:'tool'` turns, capped. (Databus is already narrowed to tool-only, so no role filter needed.)
- `selectStateLineBlocks(stateLine, layer, maxBlocks): StateLineEntry[]` — `stateLine.query({ layer: layer==='M2' ? ['M1','M2'] : ['M1'], limit: maxBlocks })`; returns `[]` for M0/M3.
- `formatStateLinePrompt(blocks): string` — join with stable `### M1 block stamp=…` / `### M2 block stamp=…` headers.
- `buildSystemSuffix(mailbox, agentId, layer): string` — two passive hint lines appended to the head system prompt:
  - **Mailbox**: `N = mailbox.readOwnInbox(agentId).length` (strict unread count — `readOwnInbox` defaults to `!read`); if N > 0 append `\n\n[mailbox] you have N unread`.
  - **M3 overflow**: when `layer === 'M3'`, append `\n\n[context overflow] M3 available via state_query/ask_recall`.
  - Returns `''` in M0/M1/M2 with no unread mail. Never injects message bodies.

### 5.2 MODIFIED `src/im/loop.ts`

- `IMLoopOptions.stateLine?: StateLine` → **`stateLine: StateLine` (required)**. Remove the optional JSDoc.
- In the per-round `parts` assembly ([loop.ts:195](../../../agent-shell/src/im/loop.ts#L195) area): after building the base parts, call `buildContextProjection({ databus, stateLine, mailbox, workingAgentId, estimatedTokens, config })`; splice `stateLinePart` after userTemplate; append `projection.systemSuffix` (mailbox hint + optional M3 overflow line) to `opts.systemPrompt`; use the projection's capped `databusTurns` for the tool-turn parts.
- `estimatedTokens`: compute from the previous round's `metrics.promptTokens` if present, else `estimateTokensFromText` of the current assembled messages.
- Pass `stateLine` through — already threaded to system agents via `createSystemAgent` in v0.10.2; no factory change.

### 5.3 MODIFIED `src/im/minimal.ts`

- `createMinimalIM` currently defaults a no-op stateLine implicitly; with the field now required, either require the caller to pass one or construct an explicit in-memory/no-op `StateLine` (one that returns `[]` from `query`). Recommendation: keep the convenience default but make it a **named** `createNoopStateLine()` in state-line so the no-op is visible, not implicit.

### 5.4 Tests `tests/im/context-projection.test.ts` (NEW) + loop.test.ts extensions

Pure-function:
- M0 (tokens < 200K): `stateLinePart === null`, databus turns present, suffix `''` when no mail.
- M1 (200K–500K): stateLinePart present, contains M1 header; M3 blocks never present.
- M2 (500K–900K): stateLinePart contains both M1 and M2 headers.
- M3 (>900K): `stateLinePart === null` (dropped); databus still present; systemSuffix contains `[context overflow]`.
- databus capped to `databusMaxTurns`; blocks capped to `stateLineMaxBlocks`.
- Mailbox hint: suffix `''` when `readOwnInbox(id).length === 0`; `[mailbox] you have N unread` with the correct N when unread exist (uses unread count, not inbox total).
- `formatStateLinePrompt` headers are greppable/stable.

End-to-end (scriptedStreamChat, capture request body):
- Loop with unread mail (readOwnInbox returns N) → `messages[0]` (system) ends with `[mailbox] you have N unread`.
- Loop with a stub StateLine returning one M1 block and an M1-range estimate → a `role:'system'` message after userTemplate contains `### M1`.
- Loop in M3 estimate → no state-line system message; head system message contains `[context overflow]`.

## 7. Decisions

### 7.1 Resolved (locked by landed code / user)

| Decision | Basis |
|---|---|
| Thresholds 200K/500K/900K, layers M0–M3 | user-mandated, in `MEMORY_LAYER_THRESHOLDS` |
| **M1/M2 share one read path + one schema** — both in `curatedMemory.jsonl`, 11-field, distinguished by stamp layer tag + header; no schema fork | user-confirmed; slack comment already in types.ts/index.ts; future M2 divergence needs no data migration |
| **State-line projects as ONE `system` part after userTemplate; mailbox hint appended to head system prompt tail; no 7th PromptPart** | user-confirmed; keeps the 6-slot union closed (ADR-005), identity prompt at head |
| Reuse `classifyMemoryLayer`; projection calls it directly per round (pull), NOT via SignalBus | user-confirmed; per-round pull is a straight line; `SignalBus`/`onLayerEnter` reserved for proactive push business (warehouse M3 email). v0.10.2.2 `a449a5f` made SignalBus instance-scoped, so the two paths don't pollute each other |
| **Mailbox hint uses `readOwnInbox(id).length` for the unread count N** (`'\n\n[mailbox] you have N unread'`) | user-confirmed (option a): strictly the *unread* count (readOwnInbox defaults to `!read`), not `inboxSize` which counts read+unread. No message bodies injected |
| **M3 passive overflow line included** — at >900K, append `[context overflow] M3 available via state_query/ask_recall` to the system prompt | user-confirmed: passive backstop to the warehouse's proactive email; M3 content itself still never injected |
| stateLine required in v0.10.3 | v0.10.2 plan §7.2 #4 + JSDoc already in code |

### 7.2 No open questions (all resolved 2026-08-28)

The five confirmation points are settled: (1) M1/M2 one read path/no schema fork; (2) one system part + mailbox tail hint, 6 slots unchanged; (3) mailbox unread count via `readOwnInbox(id).length`; (4) M3 overflow hint line included; (5) injection is a per-round pull via `classifyMemoryLayer`, SignalBus reserved for proactive push.
