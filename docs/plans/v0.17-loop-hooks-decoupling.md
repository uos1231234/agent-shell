# v0.17 — Loop Hooks 解耦（KimiCode 风格介入点）

> **Depends on**: HEAD 当前（v0.12.4 + v0.15 工具安全 + v0.16 security router + session isolation + Q1-Q4 修正已落地，1211 tests 绿）。
> **Blocks**: v0.17+ loop 单测覆盖率提升、动态压缩编排、可观察性事件流。
> **Plan status**: implementation plan. Code changes must be approved before landing.
> **Design reference**: `本地对标仓库`

---

## 0. 功能定位

**一句话**：把 `runIMLoop` 里 600+ 行的 while 循环拆成"驱动 + 5 个 await 阶段钩子"，钩子返回**显式决策对象**改变控制流（block / synthetic / retry / stopTurn），让循环主体 ≤ 150 行，且钩子是纯函数可直接单测。

**解决什么问题**：
1. `runIMLoop` 633 行，编排层与 try/catch 异常处理、重试退避、guards 终止决策、tool 调用副作用、driveCoordinator tick 全部耦合
2. 单元测试必须构造完整 harness（ToolRegistry + ShellConfig + Databus + Mailbox + StateLine + scripted streamChat），无法隔离测试单个分支（如 shell-terminated 终止协议、protocol-error 可重试退避）
3. `try { shellCall } catch { ... }` 散落在 loop 里，3 类异常的处理不可被外部扩展（如未来想加"网络抖动慢重试"，必须改 loop）

**不做什么**：
- 不改变 `IMLoopOptions` 现有字段语义（新增 `hooks?: LoopHooks`，向后兼容）
- 不改变 `IMLoopResult` 现有 reason 集合
- 不改变 v0.16 security router / door 流程（hooks 是**编排层**的解耦，不碰 registry 层）
- 不引入新的 guard / metric / config 字段（ADR-015）
- 不重写事件分发系统（events.ts 与 hooks.ts 共存：events 观察、hooks 介入）

## 1. 设计哲学（来自 KimiCode `loop/`）

KimiCode 把"控制流介入"和"事件观察"严格分开，**两套独立机制各司其职**：

| 机制 | 职责 | 能否改变控制流 | 函数签名 |
|---|---|---|---|
| **Events** | 观察者 / 日志 / 转写持久化 | ❌ 只能 dispatch | `(event) => void \| Promise<void>` |
| **Hooks** | 介入决策点 | ✅ 返回决策对象（block / synthetic / retry / stopTurn） | `(ctx) => Promise<Result \| undefined>` |

### 单向 vs 双向：为什么这是正交的两套机制（不是演进关系）

**Events 是单向**：dispatcher 把事件广播出去就完了，订阅者只读，**dispatcher 不等订阅者返回**。

**Hooks 是双向**：调用方传 ctx 进 hook，hook 返回 Result 对象给调用方，**调用方根据 Result 改变自己的控制流**（block / retry / synthetic / stopTurn）。

KimiCode 在设计之初就刻意拆开这两种耦合方向，**不是因为 event 加了校验就变成 hook**。如果硬把"双向校验"塞进 event 必然产生混乱：
- dispatcher 同步阻塞 → 失去并发派发
- 订阅者失败语义污染派发方 → 派发方不知道该用哪个订阅者的决策
- 订阅者调用顺序未定义 → 决策不可重现

KimiCode 的注释（`events.ts:155`）明确：
> Hooks can affect control flow at deterministic transcript points. Event listeners observe output and cannot change turn behavior.

因此**event 不加校验，hook 不被滥用为事件总线**——两者在抽象层面正交，不是同一个机制的"加强版"。

### events 内部仍分两类（KimiCode §137-152，正交于 hooks）

事件分 **recorded**（持久化到 transcript，必须写下来，async dispatch）与 **live-only**（仅通知 UI，丢了无所谓，sync dispatch）。这是"丢了无所谓 vs 必须写下来"的区分，与"单向/双向"完全正交。

### 我们的选择

落盘**只引入 hooks 机制**（5 个阶段钩子）。事件分发用现有 `log.*`（v0.10+ 已落地）。hooks 是这一阶段的全部收益。如果未来需要事件流（订阅者聚合、可观察性），是 v0.18 的独立工作。

### 5 个阶段钩子（KimiCode 风格）

KimiCode 6 个钩子：beforeStep / afterStep / prepareToolExecution / authorizeToolExecution / finalizeToolResult / shouldContinueAfterStop。

我们的循环有 5 个**真正的 await 阶段**，映射到：

| 钩子 | 触发点 | 可返回决策 |
|---|---|---|
| `beforeShellCall` | shellCall 之前 | `{ block, reason }` |
| `afterShellCall` | shellCall 之后（result 或 error） | `{ retry?, syntheticResult?, transformedResponse? }` |
| `afterGuards` | runGuards 之后（命中或未命中） | `{ forceTerminate?, reason? }` |
| `beforeToolExecution` | executeToolCalls 之前 | `{ block, syntheticResult }` |
| `afterToolExecution` | executeToolCalls 之后 | `{ transformedResults? }` |

### 决策对象是数据，不是异常

```
return { block: true, reason: '...' }  // 阻止
return { retry: true, delayMs: 5000 }   // 重试
return { syntheticResult: {...} }       // 替换
return undefined                       // 不介入，默认行为
```

## 2. 约束

本节 N 条硬约束，违反即不合格。

1. **`runIMLoop` 主体 ≤ 150 行**（当前 633 行）`[用户决策]`
2. **5 个钩子的返回类型全部是显式数据对象**，不抛异常、不返回 void + 副作用 `[KimiCode §251-260]`
3. **钩子函数签名是 async `(ctx) => Promise<Result | undefined>`**，`undefined` 表示不介入 `[KimiCode §231-249]`
4. **`hooks` 是 `IMLoopOptions` 新增的可选字段**，缺省时循环行为与当前完全一致（向后兼容，无破坏性）
5. **钩子的异常被 catch 并转化为"默认行为 + log.warn"**，不向上抛（避免 hook 故障拖垮整个循环）`[KimiCode §491-501]`
6. **每个钩子都有 ctx 类型定义**（不是 `unknown`），所有 ctx 都含 `turnId` / `stepNumber` / `signal` / 共享元数据 `[KimiCode §166-208]`
7. **钩子串行执行**（不并发），await 完一个再下一个 `[KimiCode §256-259 注释]`
8. **不引入 module-level 注册表**：hooks 通过 `IMLoopOptions.hooks` 一次性传入，与 v0.16 `securityRouter` 同模式
9. **不引入新事件类��**：钩子是"控制流介入点"，观察/日志走现有 `log.*`，需要事件流时再单独做 v0.18
10. **现有 3 类异常处理语义保持**：ShellTerminatedError / 不可重试 ProtocolError / 可重试 ProtocolError 的退出与重试逻辑必须在重构后 100% 等价（test 覆盖）

## 4. 架构

### 4.1 信息流

```
runIMLoop(opts) {
  state ← 'Running'
  while (true) {
    // [HOOK 1] beforeShellCall — 可 block
    if (await callHook(hooks?.beforeShellCall, { turnId, stepNumber, signal, llm })) continue/return

    // shellCall
    let result
    try { result = await shellCall(deps, finalPrompt) }
    catch (e) {
      if (e is ShellTerminatedError) → return terminated
      if (e is ProtocolError) {
        // [HOOK 2] afterShellCall with error — 可 retry / synthetic / transformed
        if (hook says retry) → continue (with backoff)
      }
    }

    // [HOOK 2b] afterShellCall with result — 可 transformedResponse

    // runGuards
    const hits = runGuards(metrics, config)
    // [HOOK 3] afterGuards — 可 forceTerminate
    if (hits.length > 0 || hook.terminate) → return terminated

    // append assistant turn, 写入 databus
    // if no toolCalls → 'completed' return

    // [HOOK 4] beforeToolExecution — 可 block / synthetic
    // executeToolCalls
    // [HOOK 5] afterToolExecution — 可 transformedResults
    // append tool results

    // driveCoordinator.tick fire-and-forget
  }
}
```

## 5. 设计原则

1. **钩子结果是数据，不是异常**：抛错只用于"系统级不可恢复"（如 shell 编程错误），业务级介入走 `Result { block / retry / synthetic }`
2. **钩子串行 + 确定性顺序**：beforeShellCall → afterShellCall → afterGuards → beforeToolExecution → afterToolExecution，便于单元测试覆盖每个分支
3. **`undefined` = 不介入**：钩子返回 undefined 等于"按默认行为走"，无需写空壳
4. **ctx 类型精确**：每个钩子的 ctx 是该阶段的真实数据子集，不共享一个大 context
5. **失败安全**：单个 hook 抛错被 catch，转化为"按默认行为走 + log.warn"，**单个 hook 故障不影响 turn 继续**
6. **hooks 是 per-loop 注入**，与 v0.16 `securityRouter` / v0.15 `securityHooks` 同模型——**没有 module-level 注册表**

```typescript
// src/im/loop-hooks.ts (no implementation, signature only)

export type LoopHook<TContext, TResult> =
  (ctx: TContext) => Promise<TResult | undefined>;

export interface BeforeShellCallContext {
  readonly turnId: string;
  readonly stepNumber: number;
  readonly signal: AbortSignal;
  readonly promptTokens: number;
}
export interface BeforeShellCallResult {
  readonly block?: boolean | undefined;
  readonly reason?: string | undefined;
  readonly substituteMessages?: ReadonlyArray<unknown> | undefined;  // synthetic
}
export type BeforeShellCallHook = LoopHook<BeforeShellCallContext, BeforeShellCallResult>;

export interface AfterShellCallContext {
  readonly turnId: string;
  readonly stepNumber: number;
  readonly signal: AbortSignal;
  readonly error?: ShellTerminatedError | ProtocolError | undefined;
  readonly result?: ShellCallResult | undefined;
}
export interface AfterShellCallResult {
  readonly retry?: boolean | undefined;
  readonly retryDelayMs?: number | undefined;
  readonly syntheticResult?: ShellCallResult | undefined;
  readonly overrideTerminate?: { reason: 'shell-terminated' | 'protocol-error' } | undefined;
}
export type AfterShellCallHook = LoopHook<AfterShellCallContext, AfterShellCallResult>;

export interface AfterGuardsContext {
  readonly turnId: string;
  readonly stepNumber: number;
  readonly signal: AbortSignal;
  readonly hits: ReadonlyArray<GuardHit>;
}
export interface AfterGuardsResult {
  readonly forceTerminate?: boolean | undefined;
  readonly reason?: 'completed' | 'guard-tripped' | 'protocol-error' | 'shell-terminated' | undefined;
}
export type AfterGuardsHook = LoopHook<AfterGuardsContext, AfterGuardsResult>;

export interface BeforeToolExecutionContext {
  readonly turnId: string;
  readonly stepNumber: number;
  readonly signal: AbortSignal;
  readonly toolCalls: ReadonlyArray<ToolCall>;
}
export interface BeforeToolExecutionResult {
  readonly block?: boolean | undefined;
  readonly reason?: string | undefined;
  readonly syntheticToolResults?: ReadonlyArray<ToolTurn> | undefined;
}
export type BeforeToolExecutionHook = LoopHook<BeforeToolExecutionContext, BeforeToolExecutionResult>;

export interface AfterToolExecutionContext {
  readonly turnId: string;
  readonly stepNumber: number;
  readonly signal: AbortSignal;
  readonly toolResults: ReadonlyArray<ToolTurn>;
  readonly errorCount: number;
}
export interface AfterToolExecutionResult {
  readonly transformedResults?: ReadonlyArray<ToolTurn> | undefined;
}
export type AfterToolExecutionHook = LoopHook<AfterToolExecutionContext, AfterToolExecutionResult>;

export interface LoopHooks {
  readonly beforeShellCall?: BeforeShellCallHook | undefined;
  readonly afterShellCall?: AfterShellCallHook | undefined;
  readonly afterGuards?: AfterGuardsHook | undefined;
  readonly beforeToolExecution?: BeforeToolExecutionHook | undefined;
  readonly afterToolExecution?: AfterToolExecutionHook | undefined;
}
```

```typescript
// 安全调用钩子，失败时返回 undefined 并 log.warn
export async function callHook<TContext, TResult>(
  hook: LoopHook<TContext, TResult> | undefined,
  ctx: TContext,
  hookName: string,
): Promise<TResult | undefined>;
```
