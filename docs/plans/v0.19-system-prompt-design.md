# v0.19 系统提示词设计 + Hook 化上下文注入

> 语言：纯中文
> 行动导向：均衡（明确指令直接执行，架构变更或破坏性操作时停下来确认）
> 架构描述：运行时功能（LLM 扫描用户代码库后动态生成，不是静态段落）

---

## 1. 系统提示词模板

### 1.1 完整模板（full 模式）

```
你是 {agent_name}，一个 AI 编程助手。你通过工具调用完成编程任务。

# 安全规则
- 不要删除 .env、.git、node_modules 等关键目录
- 不要执行 sudo 命令
- 不要访问 ~/.ssh、~/.aws/credentials 等敏感路径
- 不要在未经用户确认的情况下修改生产配置
- 文件操作前先确认目标路径是否正确

# 编码原则
- 高内聚、低耦合：同一模块内职责集中，模块间通过明确接口通信
- 新增功能优先在现有模块内扩展，不新建模块（除非确有必要）
- 修改一个模块时，检查是否有同模式的问题在其他模块中存在
- 只写正确的代码，不为了兜底写好几层防御性代码

# 基于代码信息编程
- 遇到不确定的 API 行为，先用 grep 或 read 查看源码，不猜测
- 遇到不确定的类型定义，先读类型文件，不假设
- 遇到不确定的调用关系，先用 grep 找引用，不凭记忆
- 每次修改代码前，先 read_file 看过原文，不凭印象编辑
- commit 前必须跑 tsc --noEmit 和 vitest run，不凭"应该可以"

# 工具使用指南
{tooling_section}

# 行动导向
- 对于明确的指令，直接执行，不要反复确认
- 遇到架构变更、文件删除、生产配置修改等破坏性操作时，停下来确认
- 每次修改都附"为什么改 + 改了什么 + 影响范围"三句话总结
- 遇到阻塞时，不要原地打转，写清楚原因给用户两个选项

{dynamic_sections}
```

### 1.2 dynamic_sections 的组成

`{dynamic_sections}` 是运行时通过 hook 注入的内容，按顺序：

```
{runtime_context}      — 工作目录、session ID（每轮变化）
{temporal_context}     — 日期、时区（每轮变化）
{mcp_server_summary}   — 可用 MCP server 和 skill 列表（v0.18 已实现）
{loaded_dynamic_tools} — 已加载的动态工具 schema（v0.18 已实现）
{architecture_desc}    — 用户代码库的架构描述（运行时扫描生成）
{memory_context}       — Auto Memory 索引摘要（跨会话记忆）
```

### 1.3 minimal 模式（子代理）

```
你是 {agent_name}，一个子代理。你通过工具调用完成特定任务。

# 安全规则
- 同主代理

# 编码原则
- 同主代理

# 基于代码信息编程
- 同主代理

{dynamic_sections}
```

省略：工具使用指南、行动导向、架构描述。子代理只看到安全规则 + 编码原则 + 动态内容。

### 1.4 none 模式

```
你是 {agent_name}。
```

仅身份行。

## 2. 架构描述的运行时生成

### 2.1 设计思路

架构描述**不是静态段落**，而是运行时功能：

```
用户启动会话 → LLM 扫描代码库 → 生成架构描述 → 注入上下文
```

**扫描方式**：通过 `scan_codebase` 工具（v0.13.1 已规划），LLM 自主决定扫描哪些目录和文件。

**注入时机**：扫描完成后，架构描述作为 `role: 'system'` 消息注入对话历史（与 v0.18 的动态 schema 注入模式一致）。

### 2.2 与 v0.13.1 scan_codebase 的关系

v0.13.1 的 `scan_codebase` 工具扫描代码库并生成卡片（6 种类型：module/interface/function/class/pattern/concept）。架构描述是它的**摘要视图**：

```
scan_codebase 扫描完整卡片 → 提取架构骨架 → 生成架构描述
```

**架构描述模板**（由 LLM 生成，不是硬编码）：

```markdown
## 项目架构

### 模块结构
- src/module-a/ — {功能描述}
- src/module-b/ — {功能描述}

### 核心依赖
- module-a → module-b（{依赖原因}）
- module-b → shared-types（纯类型）

### 可升级点
- {接口名} 可替换为 {替代方案}
- {配置项} 可覆盖为 {新值}

### 可扩展点
- {位置} 可新增 {类型} 实现
```

### 2.3 注入方式

与 v0.18 的动态 schema 注入保持一致：

```typescript
// 在 scan_codebase 工具执行后
// 将架构描述作为 DynamicToolSchemaMessage 类似的消息注入
const archMessage = {
  role: 'system',
  content: architectureDescription,
  origin: { kind: 'injection', variant: 'architecture_desc' },
}
// 追加到 conversation history
```

## 3. Hook 化上下文注入

### 3.1 问题：当前的 loop.ts 拥挤度

当前 loop.ts 在每轮 compose 时硬编码注入多种动态内容：

```
loop.ts compose 路径：
  → system prompt（固定）
  → mcpServerSummary（v0.18 新增）
  → dynamicMcpSchema（v0.18 新增）
  → stateLine projection（v0.10 新增）
  → mailbox unread hint（v0.10 新增）
  → context projection（v0.10 新增）
```

每新增一种动态内容，就要改 loop.ts 的 compose 逻辑。**违背了"不补丁式插入"的原则**。

### 3.2 解决：ContextInjectionHook

将所有动态内容的注入**从 loop.ts 中抽出**，改为 hook 驱动：

```typescript
// src/im/hooks/context-injection.ts

export type ContextInjectionSource = {
  name: string              // 注入源名称（如 'mcp_summary'、'architecture'）
  priority: number          // 注入顺序（小的在前）
  stable: boolean           // 是否每轮变化
  inject: (ctx: InjectionContext) => Promise<string | null>
  // 返回 null = 不注入（本轮无内容）
  // 返回 string = 作为 system message 注入
}

export type InjectionContext = {
  conversationHistory: readonly unknown[]
  registry: ToolRegistry
  sessionId?: string
  agentId?: string
  round: number             // 当前轮次
}

export class ContextInjector {
  private sources: ContextInjectionSource[] = []

  register(source: ContextInjectionSource): void {
    this.sources.push(source)
    this.sources.sort((a, b) => a.priority - b.priority)
  }

  async inject(ctx: InjectionContext): Promise<string[]> {
    const messages: string[] = []
    for (const source of this.sources) {
      const content = await source.inject(ctx)
      if (content) messages.push(content)
    }
    return messages
  }
}
```

### 3.3 内置注入源

| 注入源 | priority | stable | 内容 |
|---|---|---|---|
| `runtime_context` | 10 | ❌ | 工作目录、session ID |
| `temporal_context` | 20 | ❌ | 日期、时区 |
| `mcp_server_summary` | 30 | ✅ | 可用 MCP server 和 skill 列表 |
| `loaded_dynamic_tools` | 40 | ❌ | 已加载的动态工具 schema |
| `architecture_desc` | 50 | ✅ | 用户代码库架构描述 |
| `memory_context` | 60 | ❌ | Auto Memory 索引摘要 |

**每个注入源都是独立的文件**，通过 `ContextInjector.register()` 注册。loop.ts 只调用 `injector.inject(ctx)` 获取消息列表，不关心具体注入了什么。

### 3.4 与现有注入机制的关系

| 现有注入 | 当前位置 | 迁移后 |
|---|---|---|
| `mcpServerSummary` | loop.ts compose 硬编码 | → `McpSummaryInjection` 注入源 |
| `dynamicMcpSchema` | loop.ts compose 硬编码 | → `DynamicSchemaInjection` 注入源 |
| `stateLine projection` | context-projection.ts | → `StateLineInjection` 注入源 |
| `mailbox unread hint` | context-projection.ts | → `MailboxInjection` 注入源 |
| `architecture_desc` | 无（新增） | → `ArchitectureInjection` 注入源 |
| `memory_context` | 无（新增） | → `MemoryInjection` 注入源 |

**迁移原则**：逐个迁移，每迁移一个注入源，跑一次回归测试。不一次性重写 loop.ts。

### 3.5 loop.ts 改造后

```typescript
// loop.ts compose 路径（改造后）

// 构建 system prompt（静态段落）
const staticPrompt = buildStaticPrompt(opts)

// 通过 ContextInjector 获取动态注入内容
const dynamicMessages = await opts.contextInjector.inject({
  conversationHistory: conversation.turns(),
  registry: opts.registry,
  sessionId: opts.sessionId,
  agentId: opts.workingAgentId,
  round: metrics.stepCount,
})

// 组装最终 messages
const messages = [
  { role: 'system', content: staticPrompt },
  ...dynamicMessages.map(content => ({ role: 'system', content })),
  ...conversation.turns(),
]
```

**loop.ts 不再硬编码任何特定的注入逻辑**。新增注入源 = 新增一个 `ContextInjectionSource` 文件 + `register()` 注册，不改 loop.ts。

## 5. 决策总结

| 决策 | 选择 | 理由 |
|---|---|---|
| 语言风格 | 纯中文 | 用户选择 |
| 架构描述 | 运行时扫描生成，不是静态段落 | 用户澄清：这是 harness 的功能，不是描述 agent-shell 自身 |
| 行动导向 | 均衡 | 直接执行明确指令，破坏性操作时确认 |
| 上下文注入 | Hook 化（ContextInjector） | 不塞进 loop.ts，保持状态机简洁 |
| 现有注入迁移 | 逐个迁移，每迁移一个跑回归 | 避免一次性重写导致大规模回归 |
