## 1. 约束（Constraints）

本段是 **11 段约束**。

1. **[已验证] 核心状态机仍受 AGENTS.md 最高铁律约束。** 本计划只落盘设计，不修改 `loop.ts`、guard、上下文组装顺序、Goal judge 语义或默认 guard 阈值。后续实现如果需要在工具结果落地处区分 raw archive 与 model-visible projection，必须先向用户列出精确修改点并得到直接批准。

2. **[用户已明确授权设计方向] 20K 是模型可见工具结果的预算，不是静默丢弃。** 完整工具结果继续进入 Databus 或对应的 raw/artifact 存储；模型看到的是带有原始 token 数、保留 token 数、省略范围、stamp 和下一步读取方式的显式投影。marker 本身计入 20K 预算，不能先生成 20K 正文再额外追加说明。

3. **[已验证] 当前工具级折叠不能替代本计划。** `history-tool-table.ts` 只折叠热窗口外的旧工具回合，默认结果阈值为 2000 token；`databus-query.ts` 当前没有 token range、cursor 或单次输出预算，召回结果会直接返回完整数组。因此新保护必须覆盖普通工具输出、`databus_query`、`state_query` 和临时召回子代理的工具结果。

4. **[用户已明确授权设计方向] 所有模型可见工具结果使用同一个 token budget 口径。** 20K、200K、300K、900K 不能由不同模块各自估算。计划采用现有 `src/shared/token-estimate.ts` 作为第一版运行时 token-equivalent 事实源，并在结果元数据中记录 counter 名称；provider 返回的 usage 只作为观测数据，不能反过来改变已经切好的范围。

5. **[已决定] 直接召回预算为 200K token-equivalent。** `databus_query` 对同一原始工具字段或同一连续召回范围维护服务端预算。一次请求声明的 token range 超过 200K，或者同一 stamp 的连续分页累计超过 200K，都不能继续把原文交给主代理，必须转交临时只读召回子代理。不能只靠提示词提醒，否则模型可以通过许多小请求绕过限制。

6. **[已决定] 超过 200K 使用现有 recall system agent 的临时运行能力。** 不新增一类全局智能体，不创建后台进程，不改变默认 provider。临时运行继承 `sessionId`、AgentTree 身份、SecurityRouter/SecurityDoor 和 workDir 边界；运行期 toolRefs 只允许读取 Databus/raw archive 所需的工具，不允许写文件、shell、递归派代理、网络或 mailbox。

7. **[已验证] 900K 不是子代理摘要默认值。** `src/im/system-agent.ts` 的 handoff compaction 默认在 `promptTokens > 0.85 * config.maxTokens` 时触发，摘要转录预算默认 `300_000` token-equivalent；`src/im/system-agents/index.ts` 与 `configured-subagent.ts` 通过 `compaction: {}` 启用这套机制。900K 是 M3/context memory layer 的阈值，不是“所有子代理在 900K 时生成摘要”的阈值。compressor 的固定输入仍不装普通 handoff compaction。

8. **[已决定] 召回子代理自身也受 20K 工具投影和 300K handoff transcript 约束。** 它可以分页阅读完整 raw 内容，但每次工具结果都必须有可见边界；它的最终结果仍是一个带证据 stamp、token 范围和盲区说明的短报告，不把超过 200K 的原文转移到主代理上下文。

9. **[已决定] Baseline 不是一次性长会话。** 每个 scout 按 `inventory -> evidence -> synthesis` 三阶段执行；每阶段有 checkpoint、原始事件记录和结构化结果。阶段完成后，后续阶段只消费 evidence ledger 与必要的证据戳，不重新把所有原始工具结果灌入上下文。

10. **[已决定] 解析失败必须保留原文并可诊断。** Baseline 报告允许“说明文字 + fenced JSON”、纯 JSON、不同 fenced 标识和非核心字段缺失；核心字段无法解析时才是 `invalid-report`。任何 warning、extractionMode、缺失字段和 raw output 路径都必须落盘，不能把解析失败伪装成 scout 成功。

11. **[已决定] 普通模式、Goal 模式和工作流插件按 session 隔离。** 召回预算、分页 cursor、临时子代理、baseline checkpoint 和 skill 状态都绑定 `sessionId` 与 agent identity；关闭工作流只关闭其 hook/injection，不删除 conversation、Databus、StateLine 或 raw archive。前端仍只能通过 SignalGate 发命令、收事件。

## 3. 架构信息（Architecture）

### 3.1 四个阈值的职责

| 阈值 | 名称 | 作用 | 谁使用 | 是否互相替代 |
|---:|---|---|---|---|
| 20K | `modelVisibleToolTokens` | 单次模型可见工具结果上限，含 marker | 所有工作代理、子代理、系统智能体 | 否 |
| 200K | `directRecallSpanTokens` | 主代理对同一工具字段/连续范围的直接召回预算 | `databus_query` 路由器 | 否 |
| 300K | `handoffTranscriptTokens` | handoff compaction 摘要请求的时间线预算 | 子代理、warehouse、recall | 否 |
| 900K | `m3MinTokens` | 主会话记忆层进入 M3、归档和索引的压力阈值 | drive coordinator / StateLine | 否 |

这四个数字回答不同问题：20K 问“这一轮最多给模型看多少工具结果”；200K 问“主代理是否应该继续亲自读同一份大材料”；300K 问“压缩智能体生成交接笔记时最多整理多少时间线”；900K 问“主会话是否进入 M3 归档区”。不能把 900K 当成子代理摘要触发点，也不能把 20K 当成 Databus 的存储上限。

### 3.2 工具结果的信息流

```text
工具执行
   │
   ├── 完整结果 ──> Databus / raw archive / ArtifactStore
   │                  │
   │                  └── stamp + token metadata + sourceAgentId
   │
   └── model-visible projector
          │
          ├── <= 20K：完整投影
          └── > 20K：保头/保尾 + 显式 marker + 下一段读取指引
                              │
                              ▼
                         主代理上下文
```

投影不是对 Databus 原文的覆盖写入。它只改变当前模型看到的 tool turn；后端完整结果、args、stamp 和 raw archive 必须保持可审计。模型必须能从 marker 获得 `stamp`、原始 token 数、当前范围和下一次 `read`/`databus_query` 所需参数。

### 3.3 Databus token range 与 200K 路由

```text
主代理 databus_query
        │
        ├── 请求 token range <= 200K
        │       │
        │       └── 直接分页读取
        │             每页 <= 20K，返回 cursor / range / total
        │
        └── 请求 > 200K，或同一 stamp 累计直接读取 > 200K
                │
                └── temporary recall agent
                      │
                      ├── 分页读取 Databus/raw archive
                      ├── 自己受 20K 工具投影和 300K handoff 约束
                      ├── 记录已读范围、未读范围和证据 stamp
                      └── 返回 <= 20K 的结构化摘要给主代理
```

直接召回的预算由运行时 ledger 计算，而不是由模型自报。ledger 至少按 `sessionId + agentId + source stamp + query fingerprint` 记录已交付的非重叠 token 区间；相邻或重叠分页合并后再计数。这样模型把一个 250K 请求拆成 13 个小请求时，仍会在累计超过 200K 后进入临时召回路径。

实现时保留现有时间 `range` 参数的含义，新增独立的 token 范围字段，避免把时间戳范围误当成内容 token 范围。建议公开字段如下：

```ts
type DatabusTokenRange = {
  startToken: number
  endToken: number
}

type DatabusRecallRequest = {
  stamp?: string
  toolName?: string
  keyword?: string
  sourceAgentIds?: string[]
  timeRange?: [number, number]
  tokenRange?: DatabusTokenRange
  cursor?: string
  reason: string
}

type DatabusRecallPage = {
  records: ToolTurn[]
  stamp?: string
  returnedRange: DatabusTokenRange
  totalTokens: number
  nextCursor?: string
  mode: 'direct' | 'delegated'
  evidenceStamps: string[]
}
```

第一版可以保留既有参数的兼容别名，但新分页响应必须明确 `returnedRange`、`totalTokens`、`nextCursor` 和 `mode`，不能返回一个模型无法判断是否完整的裸数组。

### 3.4 临时 recall agent 的职责边界

临时召回代理只做“阅读、整理、举证”，不做代码修改和任务决策。它的运行边界如下：

| 能力 | 临时 recall agent |
|---|---|
| 读取 | `databus_query`、必要时 `state_query` 的 raw/archive 读取 |
| 记录 | 原始 stamp、token range、缺口、冲突和证据位置 |
| 输出 | 结构化摘要，带 `facts`、`evidenceStamps`、`coveredRanges`、`openQuestions` |
| 禁止 | `write`、`edit`、`search_replace`、`bash`、`powershell`、`run_subagent`、网络、mailbox |
| 生命周期 | 单次临时 run，结束后释放本次 conversation；不建立后台进程 |
| 权威来源 | `SystemAgent.run()` 返回值；Mailbox/AgentTree/Databus 只做补充和审计 |

现有 recall agent 的默认 toolRefs 包含 mailbox，这是系统智能体历史协作需要；大召回路径不能把这个宽权限原样复制给临时代理。实现应使用调用级 policy/toolRefs 收窄，而不是修改全局 recall 默认行为。若现有工厂暂时不支持调用级收窄，应先新增最小的运行时参数，再接入路由。

### 3.5 Baseline 的阶段式信息流

```text
workflow.baseline
      │
      ├── structure scout ── inventory ──> checkpoint
      │                       evidence  ──> ledger + raw jsonl
      │                       synthesis ─> structure.json
      │
      ├── verification scout ─ inventory ─> checkpoint
      │                         evidence  ─> ledger + raw jsonl
      │                         synthesis ─> verification.json
      │
      └── risk scout ─────── inventory ─> checkpoint
                              evidence  ─> ledger + raw jsonl
                              synthesis ─> risk.json
                                      │
                                      ▼
                                baseline.json
```

三个角色仍可并行，但每个角色内部必须按阶段推进。`inventory` 建立文件和行范围清单；`evidence` 分页读取并登记事实；`synthesis` 只消费 ledger、必要的 stamp 和 checkpoint，不回放全部原文。进程中断后，已完成阶段不重复读取，未完成阶段从 checkpoint 继续。

### 3.6 普通、Goal 和工作流插件的边界

```text
session A
  conversation / goal / workflow state / recall ledger / AgentTree A

session B
  conversation / goal / workflow state / recall ledger / AgentTree B

workflow off
  workflow hooks = no-op
  ordinary mode and goal mode keep using the same existing history
```

本计划不改变 Goal judge 的“读完整 canonical”语义。20K 工具投影约束的是工具结果进入 canonical/model-visible prompt 的形式；Goal judge 是否消费 raw/full canonical 必须保持当前语义，若未来要让 judge 读取独立 raw archive，必须另立 ADR，不在本计划偷换。

## 4. 设计原则（Principles）

1. **存储完整，投影有界。** 压缩和分页解决模型视野问题，不能让 Databus/raw archive 失去证据。所有省略都必须能由 stamp、cursor 或 raw archive 路径复原。

2. **预算在运行时强制。** 20K 和 200K 不能只写在 system prompt；结果投影器和 recall ledger 必须在工具执行层拒绝或路由超限请求。

3. **单一 token 口径。** 范围切片、分页、marker 和统计统一使用同一 `TokenCounter`。provider usage 作为实验报告字段保留，不用来事后篡改已交付范围。

4. **大召回转交，不是把上限搬家。** 临时 recall agent 可以读超过 200K 的原文，但它只把结构化结论和证据戳交给主代理；不能把 200K 原文再包成一个更大的工具结果返回。

5. **Baseline 的压缩服务于工作流，而不是安全拒绝。** 通过 inventory、ledger、checkpoint 和 synthesis 控制重复阅读；只有真正越权或违反边界时才由权限机制拒绝。

6. **复用现有身份和安全壳。** 不新增绕过 SecurityDoor 的快捷路径，不用 Mailbox 或 AgentTree 冒充最终报告，不用提示词替代 `toolRefs` 和运行时 policy。

7. **先可观测再调阈值。** 每次投影、分页、转交、摘要和恢复都记录原始 token 数、可见 token 数、范围、stamp、agentId、sessionId 和失败原因，后续实验才可以判断压缩是否提升连续性。

## 5. 模块化引导（Module Guidance）

以下是实现阶段的公开 API 方向。这里只写接口和职责，不写实现伪代码。

### 5.1 统一工具结果投影

目标文件：`src/im/tools/result-budget.ts`。

```ts
export type TokenCounter = {
  id: string
  count(text: string): number
  slice(text: string, startToken: number, endToken: number): string
}

export type ToolResultProjection = {
  visibleContent: string
  originalTokens: number
  visibleTokens: number
  omittedRanges: DatabusTokenRange[]

  stamp: string
```

它只负责生成模型可见的 20K 投影和 marker，不负责写 Databus，不负责决定是否调用 recall agent。marker 至少包含：原始 token 数、可见 token 数、被省略范围、stamp、下一页 cursor 或 `read` 的范围建议、`databus_query` 的精确召回方式，以及“当前内容不是全文”的明确说明。

### 5.2 Databus token range 与预算 ledger

目标文件：`src/im/tools/databus-recall.ts`，并由 `databus-query.ts` 消费。

```ts
export type DirectRecallLedger = {

  exceeds(limitTokens: number): boolean

export type DatabusRecallPlanner = {

export function createDatabusRecallPlanner(options: {
```

`databus-query.ts` 继续负责 Databus 过滤和读取；planner 负责 token range、cursor、累计预算和 direct/delegated 路由。原有的时间 `range`、stamp、toolName、keyword、sourceAgentIds 过滤语义不变。

### 5.3 临时大召回运行器

## 7. 决策信息（Decisions）

### 已决定

1. 20K 是所有模型可见工具结果的统一默认上限，marker 计入预算；完整原文留在后端。
2. Databus 支持 token range + cursor，按同一 token counter 分页。
3. 单次或累计同一源范围超过 200K 时转临时 recall agent；运行时 ledger 防止拆小请求绕过。
4. 复用现有 recall system agent 的执行内核，但大召回使用调用级只读工具权限。
5. 临时 recall agent 的最终结果受 20K 投影约束，返回事实、证据戳、覆盖范围和未覆盖范围。
6. Baseline 改成 inventory/evidence/synthesis 三阶段，阶段结果和 raw 证据可恢复。
7. 报告解析宽容消费、严格记录 warning；真正无法消费才失败。
8. 900K 只表示 M3/context memory layer，不表示子代理摘要默认值；子代理 compaction 仍按自身 `maxTokens * 0.85`，摘要 transcript 默认 300K。
9. 不改前端旁路、不新建后台进程、不改默认 provider、不破坏 SecurityDoor。

### 实现前仍需逐点确认

1. **[需要用户直接批准]** `loop.ts` 是否允许增加“完整工具结果写 Databus、20K 投影写 canonical/model-visible turn”的分流接线。这是信息流核心修改，不能以“用户同意 20K”推断为已批准具体代码改动。
2. **[需要用户直接批准]** `databus_query` 的响应是否从当前裸数组升级为带 `records`、`returnedRange`、`nextCursor` 的对象。对象更可审计，但可能影响现有 fixture 和外部调用者。
3. **[实现选择，默认按本计划执行]** 第一版 token range 使用 `estimateTokens` 的 token-equivalent，不引入 provider-specific tokenizer；报告同时记录 provider usage，避免把两种口径混为一谈。
4. **[实现选择，默认按本计划执行]** 200K ledger 按同一 stamp 和连续/重叠 range 聚合；不同 stamp 的独立事实不合并为一个不可解释的全局阈值。
