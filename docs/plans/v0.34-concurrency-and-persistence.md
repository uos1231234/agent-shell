## 1. 约束（Constraints）

**本节共 9 段约束，全部为已核实事实或用户拍板决定，不可违反。**

1. **用户拍板 2026-09-10：C1 并发防线坐在 GATE 层。** 理由——`src/signals/gate.ts` 是唯一的前后端中转站，所有前端（CLI / webapp / headless）都从它过，在此处串行化可一口气解决所有前端对同一会话的并发问题。不在 CLI 或 webapp 各自补守卫。

2. **用户拍板 2026-09-10：C1 语义 = 方案 A 排队。** 同会话第二条 `user.prompt` 不丢弃、不顶替，压入队列，当前 turn 结束后按序执行。用户主动取消当前 turn 时**清空该会话队列**（取消 = 用户意图是停）。

3. **用户拍板 2026-09-10：C2 语义 = 用户大过天，说停就立刻停。** `src/host/assembly.ts:754-762` 的 `detachSession` 现有顺序（`wiring.dispose()` → `cancelSignals.get(id)?.abort()` → `await handle.close()`）**是正确的，顺序不改**。禁止引入"等 in-flight turn 写完"的逻辑。

4. **用户拍板 2026-09-10：mailbox 邮件读完不删除，3 天后过期自动删除。** 与 `src/im/session/session-store.ts` 的 `DEFAULT_TTL_DAYS = 3` 同策略。

5. **用户拍板 2026-09-10：压缩是后台静默且实时的，无需向用户广播任何内容。** 本计划**不含**"压缩中…"提示类工作项。

6. **用户拍板 2026-09-10：HookSystem 暂不接线。** HookSystem 是信号关（Signal Gate）的低配版，有了信号关其作用已小。已在 `src/im/hooks/hook-system.ts` 文件头留下备注（定位 / 生产现状 / 为何无用户可见后果 / 未来接线 4 步 / 三个 handler 工厂是否重复的核实结论）。本计划**不含** HookSystem 接线工作项。

7. **最高铁律（`AGENTS.md`）：任何状态机修改——尤其 guard、上下文组装顺序、loop 主循环——必须先获得用户明确、直接、有针对性的同意。** 本计划涉及 gate（中转站）与写入路径，实施前须逐项取得用户对精确改动内容的确认。**不准因为前端动后端。**

8. **已核实事实（主代理亲自 grep + 读码，非转述）**：
   - `src/signals/gate.ts:120-122` 的 `user.prompt` 处理**直接调用** `handlers.runPrompt(...)`，按 sessionId **无锁、无队列、无在途检查**。
   - `src/host/assembly.ts:775-776`：每次 `runPromptOnce` 新建 `AbortController` 并 `cancelSignals.set(sessionId, controller)`，无条件覆盖；`:815-817` 的 `finally` 中 `cancelSignals.delete(sessionId)` —— **先完成者会删掉后到者的登记**。

### 3.2 C2：写入与关闭的时序（现状缺陷 vs 目标）

```
现状（缺陷）：
  detachSession: dispose() → abort()（仅通知，不等）→ handle.close() 关句柄
  runIMLoop:     ... 正在 appendJsonl(写 conversation/databus.jsonl) ...
                 写已关闭句柄 ──► 抛错

目标（用户大过天）：
  detachSession: dispose() → abort() → handle.close()      ← 顺序不变，不等
  runIMLoop:     ... abort 已置位 / 句柄已关 ...
                 写入前判断 ──► 安全丢弃本次写入（no-op，不抛错、不补写、不重试）
```

关键定性：会话正在被关闭/删除，**丢掉最后一笔未写完的数据是正确的**——用户说了停。

### 3.3 mailbox 生命周期（改造后）

```

        ▼

```

## 4. 设计原则（Principles）

1. **一处设防，全局受益。** 串行化只做在 gate 一处，不在各前端重复实现。前端已有的 `running` 守卫（`Composer.tsx:32`）保留不动，作为体验层的第一道快速反馈，不作为正确性保证。
2. **gate 的定位升级要在代码里写明。** gate 原自我定位为"纯路由"（见 `src/signals/types.ts:107`、`:110` 的注释）。加串行化后其定位变为"纯路由 + 会话级并发控制"。这是一次**明确的定位升级**，必须同步修订这些注释，不允许留下自相矛盾的文档。
3. **停止是丢弃，不是等待。** C2 的修法必须是"让在途写入安全失败/丢弃"，绝不引入 await/重试/补写。用户关闭会话是最高优先级意图。
4. **排队对用户可见、可解释。** 排队不是静默行为——前端应能知道"这条在排队"。本计划先定义信号契约，前端展示可作为后续增量；但契约本身必须在本计划内定型。
5. **mailbox 落盘格式与既有 jsonl 对齐。** 复用 `appendJsonl` 的原子行追加与 per-line 容错读取（`readJsonl` 的 try-catch 跳过损坏行），不发明第二套持久化机制。
6. **红灯比假绿有价值。** `tests/im/concurrency/session-lifecycle.test.ts` 现有 2 个 `it.todo` 是本计划的两个验收靶子。本计划完成后它们必须转成真实通过（而非删除或继续 todo）。若实施中发现无法达成，明确记录原因，不允许悄悄降级为 todo。
7. **不做未要求的事。** 本计划不含 HookSystem 接线、不含压缩广播、不含孤儿 hook 的删除（后者见 §7 待决）。

## 7. 决策信息（Decisions）

### 已决（用户拍板，2026-09-10）

| # | 决策 | 依据 |
|---|---|---|
| D1 | C1 防线位于 **gate 层** | 唯一中转站，一处解决所有前端 |
| D2 | C1 语义 = **排队（方案 A）** | 不丢消息，符合"用户大过天" |
| D3 | 取消当前 turn 时 **清空该会话队列** | 取消 = 用户意图是停 |
| D4 | C2 = **立刻停止，不等待**；写入走安全丢弃 | 用户大过天 |
| D5 | mailbox **读后不删**，**3 天过期** | 与 session snapshot TTL 同策略 |
| D6 | 压缩 **不做任何广播** | 后台静默且实时，无内容可播 |

| D8 | 三个孤儿 hook 工厂 **保留**，并在代码备注中写明「**为可观测性保留**」 | 用户拍板 2026-09-10；它们是 v0.19 hook 体系唯一的 e2e 验证资产，且 `getLogs()` 是唯一记录工具耗时的面 |

### 9.2 C1 实现要点（与计划的差异，均为修正计划错误）

1. **信号从 `turn.queued` 改为 `turn.queue`（权威广播 `pending` 条数）**。原设计只播"入队"，但 `turn.cancel` 丢弃队列后前端无从得知，`turn.end` 的 reducer 会误判"还有后继"而把 UI 永远停在 streaming。改为每次队列状态变化都广播权威值，前端只镜像。
2. **`startTurn` 补失败推进**。宿主装配层只在成功后 emit `turn.end`（`assembly.ts` 的 runPrompt handler），失败路径没有任何信号 → 不补推进则会话永久卡在 busy、后续消息永不执行。测试覆盖了"首个回合失败"与"排队回合失败"两条路径。
3. **`session.close/delete` 的 `emitQueueState` 必须先于 `sessions.delete`**。`dispatch` 会把 `sessionId` 记入观察集合，顺序颠倒会让刚关闭的会话被自己的队列信号"复活"（现有 `gate.test.ts` 的 snapshot 用例抓到）。
4. **CLI 不加 idle 守卫**（与计划 §8.1.4 相反）。选了方案 A（排队）后，拦消息等于把用户消息吞掉，违反 D2/D9。CLI 的正事是显示排队状态。
5. **webapp `Composer` 移除 `|| running` 拦截**。否则网页端根本发不出第二条消息，排队功能在 webapp 上等于死的。

### 9.3 mailbox 实现要点

- **「读后不删」原本就满足**：`markRead` 只置 `read`/`readAt`，从无删除逻辑。本次只补**落盘**与 **TTL**。
- TTL 复用 `store.ttlDays`（宿主传入，单一事实源），缺省 `DEFAULT_MAIL_TTL_DAYS = 3`。
- 三处执行：写入前回收过期容量（否则过期邮件占满 `MAX_INBOX_SIZE` 把新邮件挡在 "is full" 之外）／恢复时 `restore` 跳过过期／读取时惰性过滤。
- 落盘端口 `append` 返回 void（发送 API 是同步的），实现方内部处理异步与错误，失败 `console.warn` 留痕。
