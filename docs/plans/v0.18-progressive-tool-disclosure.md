# v0.18 — 渐进式工具披露（MCP + Skill + 文本 skill 不变）

> Depends on: v0.17 已实现（多会话 + 历史恢复，1402 tests 绿）
> Blocks: 无（独立功能）
> Status: 计划中

---

## 设计动机

当前 agent-shell 的 MCP 工具暴露方式是**全量披露**：`bootMcpServers` 注册所有工具到 registry，`mcpRefs` 白名单决定哪些进入 LLM 的顶层 `tools[]`。问题：

1. **token 浪费**：一个 MCP server 可能有 20+ 工具，每个工具的 schema（name + description + JSON schema）占 200-800 tokens。全量披露 = 每轮多花数千 token。
2. **无法区分 MCP server**：工具名是 `server__tool` 格式，但 LLM 看不到"这些工具属于哪个 server"的分组信息。
3. **Skill 工具同理**：module skill 也全量披露，没有按需加载机制。

**参考**：KimiCode 的 `select_tools` + `tools-diff.ts` + `dynamic-tools.ts`（共 330 行）实现了两阶段渐进式披露。本计划适配 agent-shell 的 MCP 分组特性。

## §1 约束

### 1.1 注册时序不可变

`registry.registerMCP(server, tools)` 在启动时一次性调用（`boot.ts`），运行时不增删。渐进式披露只影响**LLM 看到什么**（compose 阶段），不影响 registry 内部。

> 参考：`src/shell/registry.ts:6` "Registration is startup-time only. No runtime add/remove."

### 1.2 不新增 guard/metric/config 字段

工具披露是 compose 层行为，不引入新的 guard（熔断）、metric（度量）、config（配置）字段。

### 1.3 MCP 工具必须标注 server 归属

LLM 看到的工具名格式保持 `server__tool`（向后兼容），但**server 描述**必须作为独立信息源注入，让 LLM 知道"哪些工具属于哪个 MCP server"。

### 1.4 已注册但未披露的工具仍然可被 registry.execute()

未被 LLM 选中的 MCP 工具仍注册在 registry 中——如果 LLM 后续通过 `load_mcp_tools` 加载了它们，`registry.execute()` 直接可用，不需要重新注册。

### 1.5 `mcpRefs` 角色收缩为注册侧门控

`mcpRefs` 不再决定 LLM 看到什么。它只决定 `bootMcpServers` 注册哪些工具到 registry（安全门控）。所有已注册的 MCP 工具和 module skill 统一走 `load_tools` 渐进式披露，不分支、不回退。

### 1.6 子代理与主代理同一套披露机制

`loop.ts` 的 compose 路径不区分调用者身份。主代理和子代理走完全相同的 `load_tools` + 动态 schema 注入路径。子代理的差异化通过 `ToolContext.toolPolicy` 实现——`load_tools` 在 execute 时按 policy 过滤，不在 compose 层区分。

### 1.7 子代理 policy 运行时检查

子代理的 `SubAgentToolPolicy` 从配置加载时的静态检查（`validateSubAgentConfig` 检查 `toolRefs`），扩展为运行时检查：`load_tools` 的 execute 中对每个目标工具调用 `applyToolPolicy`。这样子代理可以调 `load_tools`，但只能加载它 policy 允许的工具。

### 1.8 并发安全

`runIMLoop` 支持异步并发（多个子代理并行运行）。并发隔离依赖：
- 每个 agent 的 `ConversationMemory` + `Databus` 独立（`system-agent.ts:102` 每次 `run()` 新建）
- `ToolRegistry` 共享但启动后只读（写操作仅在 `bootMcpServers` / `registerSystemAgentTools` 期间）
- `load_tools` 的动态 schema 注入通过 `ToolContext` 传递到各自 agent 的 loop，不跨 agent 共享

## §3 架构

### 核心思路

```
启动时:
  bootMcpServers → registry 注册 MCP 工具（mcpRefs 门控）
  + registry 存储 server metadata（description + tool names）
  + registry 存储 loadable skill metadata（name, description）

每轮 compose:
  → systemToolRefs 全量推入 tools[]（系统工具不变）
  → load_tools 推入 tools[]（始终存在）
  → server/skill 摘要注入 system message
  → 已加载的动态 schema 注入对话历史

LLM 调用 load_tools({ sources: [{type:'mcp', server:'wiki'}, {type:'skill', name:'ast-grep'}] }):
  → 将选中 server 的全部工具 schema + 选中 skill 的工具 schema 注入 role:system 消息
  → 下一步 LLM 可直接调用这些工具
```

## §4 设计原则

### P1: server 是披露粒度

MCP 工具按 server 分组披露，不是按单个工具。一个 server 的全部工具一次性加载。理由：同一 server 的工具通常是协作的（搜索→获取→编辑），按需拆分单个工具会导致 LLM 反复调用 `select_mcp_servers`。

### P2: 动态 schema 注入对话历史，不注入顶层 tools[]

已加载的 MCP 工具 schema 通过 `role: 'system'` 消息注入（携带 `tools` 字段），而非放入顶层 `tools[]`。这样 compaction 后 schema 自然消失，LLM 需要重新 select。与 KimiCode 的 `DYNAMIC_TOOL_SCHEMA_VARIANT` 模式一致。

### P3: server 描述写入系统提示词

MCP server 的 `description`（来自 config 或推断）在系统提示词中以 `<mcp_servers>` 块注入，让 LLM 知道有哪些 server 可用及其用途。

### P4: MCP 和 module skill 统一走 `load_tools`

`load_tools` 接受混合 sources——MCP server 名和 module skill 名都可以。这样 LLM 一轮调用同时加载需要的 MCP server 工具和 skill 工具。文本 skill 不受影响（仍走预注入路径）。

### P5: `load_tools` 是唯一始终在 tools[] 中的动态披露工具

当渐进式模式激活时，顶层 `tools[]` 只包含 `load_tools` + 系统工具。MCP 工具和 module skill 全部走动态加载。

### P6: 动态 schema 参与 compaction 输入

与 KimiCode 选 B（strip）不同，我们选 A——动态 schema 消息参与 compressor 的输入。理由：我们的压缩通过 compressor SystemAgent（LLM）做摘要，LLM 需要看到工具定义才能写出有意义的 curated memory。KimiCode 的 compaction 是 in-memory 折叠，不需要 LLM 参与，所以可以 strip。

### P7: 工具来源归属

`load_tools` 加载的 MCP 工具在 schema 注入时标注 `source: { kind: 'mcp', server }`，module skill 标注 `source: { kind: 'skill' }`。这与 registry 内部的 `RefSource` 类型一致，方便 debug 和 telemetry。

```typescript
export function createLoadToolsTool(
  registry: ToolRegistry,
): SystemTool
```

- name: `load_tools`
- parameters: `{ sources: Array<{ type: 'mcp'; server: string } | { type: 'skill'; name: string }>, reason: string }`

## §7 决策

### 已决定

| 决策 | 理由 | ADR |
|---|---|---|
| server 是最小披露粒度（MCP 侧） | 同一 server 的工具协作紧密，单工具选择会导致反复调用 | — |
| MCP + module skill 统一走 `load_tools` | LLM 一轮调用同时加载 MCP server 工具和 skill 工具，减少 round-trip | — |
| 动态 schema 注入对话历史 | compaction 后自然丢失，无需额外清理逻辑 | 参考 KimiCode dynamic-tools.ts |
| `load_tools` 是系统工具 | 不走 MCP/Skill 注册路径，无 security hook 额外开销 | — |
| `mcpRefs` 只管注册侧门控 | 决定哪些工具被注册到 registry，不决定 LLM 看到什么。所有已注册工具统一走渐进式披露，无分支无回退 | — |
| server description 来自 config 或推断 | `McpServerConfig` 可选 `description` 字段，缺省用 `"MCP server: {name}"` | — |
| 子代理与主代理同一套披露路径 | `loop.ts` compose 不区分调用者身份。子代理差异化通过 `ToolContext.toolPolicy` 运行时过滤 | — |
| 子代理 policy 运行时检查 | `load_tools` execute 时对每个目标工具调用 `applyToolPolicy`。子代理可调 `load_tools`，但只能加载 policy 允许的工具 | — |
| 并发安全依赖既有隔离 | 每个 agent 独立 ConversationMemory + Databus；ToolRegistry 共享但启动后只读。不需要额外锁 | — |
| Q1: 需要 reason 字段 | 与所有 MCP 工具一致 | — |
| Q2: server description 注入 system message 块 | 集中、可缓存、与 text skill 预注入模式一致 | — |
| **Q3: skill 分组披露在本版本实现** | `load_tools` 接受 `{ type: 'skill', name }` sources，module skill 按 name 加载 | — |
| **Q4: 动态 schema 参与 compaction 输入** | 我们的压缩通过 compressor SystemAgent（LLM）做摘要，需要看到工具定义才能写出有意义的 curated memory。与 KimiCode（in-memory 折叠，不需要）不同 | — |
